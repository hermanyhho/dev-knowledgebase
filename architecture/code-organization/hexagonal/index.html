Architecture notes

Hexagonal Architecture

Also called Ports and Adapters. Described by Alistair Cockburn in 2005.

What it is

A way to organise the code inside one application. The business rules sit in the middle, in a part called the core. The core does not know about the web framework, the database or any other outside tool.

The core talks to the outside world only through interfaces it defines itself. These interfaces are the ports. Code that connects a real tool to a port is an adapter.

The shape is a hexagon only because six sides give room to draw many ports. The number six has no meaning.

It describes code structure, not deployment. You can use it inside a monolith or inside each microservice.

TermMeaningIn the example
CoreBusiness rules and use cases. Plain code with no framework imports.Order, PlaceOrderService
Input portInterface for what the app can do. Outside code calls it.PlaceOrder
Output portInterface for what the app needs from outside. The core calls it.OrderRepository
Driving adapterStarts an action by calling an input port.HTTP endpoint, CLI, test
Driven adapterImplements an output port with a real tool.Postgres, in-memory list
The one rule: source code dependencies point inward. Adapters import the core. The core never imports an adapter.

What happens on POST /orders

  1. The HTTP endpoint receives the request.
  2. The endpoint calls the PlaceOrder input port.
  3. PlaceOrderService creates an Order. The Order checks its own rules.
  4. The service calls save on the OrderRepository output port.
  5. The adapter that was plugged in at startup runs. In production that is Postgres.
  6. The endpoint sends 201 with the new order ID.

Problems it solves

  • Slow, fragile testsBusiness rules run in tests with an in-memory adapter. No database or server to start.
  • Locked to one toolTo move from Postgres to MongoDB, write one new adapter. The core does not change.
  • Logic spread across layersRules live in the core only. Endpoints and SQL stay thin, so you know where to look.
  • Many entry pointsHTTP, CLI and a queue consumer can all call the same use case without copying it.
  • Early tool decisionsYou can build and test the core before you choose a database.

Problems it introduces

  • More files per featureOne feature here needs 9 files. A plain endpoint with inline SQL needs 1. For simple CRUD apps the cost is higher than the gain.
  • Conversion codeThe domain Order, the database row and the JSON body are separate shapes. You write code to convert between them.
  • Harder to follow a call"Go to definition" opens the interface, not the code that runs. You must check the wiring file to see which adapter is used.
  • Interfaces with one implementationMany ports only ever get one adapter. Each one is extra code to read.
  • Needs team agreementThe team must agree what belongs in the core. Without a check, such as an import lint rule or a separate core project, adapter code moves into the core over time.
  • No help with scaling or deploysIt changes how code is organised, not how it runs. It is still one deployable app.
Corecore/domain/Order.tsBusiness rules. No imports from Express or Postgres.
export type OrderItem = { productId: string; price: number; quantity: number };

export class Order {
  constructor(
    readonly id: string,
    readonly customerId: string,
    readonly items: OrderItem[],
  ) {
    if (items.length === 0) {
      throw new Error("An order needs at least one item.");
    }
  }

  total(): number {
    return this.items.reduce((sum, item) => sum + item.price * item.quantity, 0);
  }
}
Corecore/PlaceOrderService.tsThe use case. It knows the ports, not the tools behind them.
import { randomUUID } from "node:crypto";
import { Order } from "./domain/Order";
import { PlaceOrder, PlaceOrderInput } from "./ports/PlaceOrder";
import { OrderRepository } from "./ports/OrderRepository";

export class PlaceOrderService implements PlaceOrder {
  constructor(private readonly orders: OrderRepository) {}

  async execute(input: PlaceOrderInput): Promise<string> {
    const order = new Order(randomUUID(), input.customerId, input.items);
    await this.orders.save(order);
    return order.id;
  }
}

Driving adapteradapters/http/orderRoutes.tsTurns an HTTP request into a call on the input port.
import { Router } from "express";
import { PlaceOrder } from "../../core/ports/PlaceOrder";

export function orderRoutes(placeOrder: PlaceOrder): Router {
  const router = Router();

  router.post("/orders", async (req, res) => {
    const orderId = await placeOrder.execute(req.body);
    res.status(201).json({ orderId });
  });

  return router;
}
Driving adapteradapters/cli/placeOrderCommand.tsA second entry point. It calls the same input port as the HTTP route.
import { PlaceOrder } from "../../core/ports/PlaceOrder";

export async function placeOrderCommand(placeOrder: PlaceOrder, args: string[]): Promise<void> {
  const [customerId, productId, price, quantity] = args;

  const orderId = await placeOrder.execute({
    customerId,
    items: [{ productId, price: Number(price), quantity: Number(quantity) }],
  });

  console.log(`Created order ${orderId}`);
}

Driven adapteradapters/db/PostgresOrderRepository.tsImplements the output port with SQL.
import { Pool } from "pg";
import { Order } from "../../core/domain/Order";
import { OrderRepository } from "../../core/ports/OrderRepository";

export class PostgresOrderRepository implements OrderRepository {
  constructor(private readonly db: Pool) {}

  async save(order: Order): Promise<void> {
    await this.db.query(
      "INSERT INTO orders (id, customer_id, total) VALUES ($1, $2, $3)",
      [order.id, order.customerId, order.total()],
    );
  }
}
Driven adapteradapters/db/InMemoryOrderRepository.tsSame port, no database. Used in tests.
import { Order } from "../../core/domain/Order";
import { OrderRepository } from "../../core/ports/OrderRepository";

export class InMemoryOrderRepository implements OrderRepository {
  readonly saved: Order[] = [];

  async save(order: Order): Promise<void> {
    this.saved.push(order);
  }
}

Coresrc/Shop.Core/Domain/Order.csBusiness rules. The Shop.Core project has no reference to ASP.NET or Npgsql, so the compiler blocks those imports.
namespace Shop.Core.Domain;

public record OrderItem(string ProductId, decimal Price, int Quantity);

public class Order
{
    public Guid Id { get; }
    public string CustomerId { get; }
    public IReadOnlyList<OrderItem> Items { get; }

    public Order(Guid id, string customerId, IReadOnlyList<OrderItem> items)
    {
        if (items.Count == 0)
            throw new ArgumentException("An order needs at least one item.");

        Id = id;
        CustomerId = customerId;
        Items = items;
    }

    public decimal Total() => Items.Sum(item => item.Price * item.Quantity);
}

using Shop.Core.Domain;

namespace Shop.Core;

public class PlaceOrderService(IOrderRepository orders) : IPlaceOrder
{
    public async Task<Guid> ExecuteAsync(PlaceOrderInput input)

Driving adaptersrc/Shop.Adapters/Http/OrderEndpoints.csTurns an HTTP request into a call on the input port.
using Shop.Core.Ports;

namespace Shop.Adapters.Http;

public static class OrderEndpoints
{
    public static void MapOrderEndpoints(this WebApplication app)
    {
        app.MapPost("/orders", async (PlaceOrderInput input, IPlaceOrder placeOrder) =>
        {
            var orderId = await placeOrder.ExecuteAsync(input);
            return Results.Created($"/orders/{orderId}", new { orderId });
        });
    }
}

Driven adaptersrc/Shop.Adapters/Db/PostgresOrderRepository.csImplements the output port with SQL through Npgsql.
using Npgsql;
using Shop.Core.Domain;
using Shop.Core.Ports;

namespace Shop.Adapters.Db;

public class PostgresOrderRepository(NpgsqlDataSource db) : IOrderRepository
{
    public async Task SaveAsync(Order order)
    {
        await using var command = db.CreateCommand(
            "INSERT INTO orders (id, customer_id, total) VALUES ($1, $2, $3)");
        command.Parameters.AddWithValue(order.Id);
        command.Parameters.AddWithValue(order.CustomerId);
        command.Parameters.AddWithValue(order.Total());

        await command.ExecuteNonQueryAsync();
    }
}
Driven adaptersrc/Shop.Adapters/Db/InMemoryOrderRepository.csSame port, no database. Used in tests.
using Shop.Core.Domain;
using Shop.Core.Ports;

namespace Shop.Adapters.Db;

public class InMemoryOrderRepository : IOrderRepository
{
    public List<Order> Saved { get; } = [];

    public Task SaveAsync(Order order)
    {
        Saved.Add(order);
        return Task.CompletedTask;
    }
}
Wiringsrc/Shop.Api/Program.csThe only project that references every other one. The dependency injection setup picks which adapter goes into which port.
using Npgsql;
using Shop.Adapters.Db;
using Shop.Adapters.Http;
using Shop.Core;
using Shop.Core.Ports;

var builder = WebApplication.CreateBuilder(args);

builder.Services.AddSingleton(NpgsqlDataSource.Create(builder.Configuration.GetConnectionString("Orders")!));
builder.Services.AddScoped<IOrderRepository, PostgresOrderRepository>();
builder.Services.AddScoped<IPlaceOrder, PlaceOrderService>();

var app = builder.Build();
app.MapOrderEndpoints();
app.Run();
