Architecture / System topology

Monolith

Also called a single-deployment application. The default way most applications start.

What it is

An application that is built, tested and deployed as one unit. All features live in one codebase and run in one process. In most cases they also share one database.

"Monolith" describes how the app is deployed and run. It does not say how good the code is. The code inside can be well organised, for example with hexagonal architecture, or it can be hard to follow.

A monolith can still run on many servers. You start several identical copies behind a load balancer. Every copy contains every feature.

The opposite is microservices: each feature is a separate app with its own deploy and usually its own database.

TermMeaningIn the example
Deployable unitThe thing you build and ship to a server.One Docker image of the shop app
ModuleA folder or namespace for one business area.Orders, Users, Payments, Notifications
In-process callA plain function call inside the same running program. No network.users.getById(...)
Shared databaseOne database that every module reads and writes.Postgres with all tables
TransactionA group of database writes that all succeed or all fail.Insert order and payment together
Horizontal scalingRunning more copies of the app behind a load balancer.3 copies behind nginx
The one rule: everything ships together. A change to any module means you build, test and deploy the whole application.

Example flow: POST /orders

Press Play to follow one request through the diagram, step by step.

  1. The load balancer sends the request to one of the 3 copies.
  2. The HTTP route calls OrderService.
  3. OrderService calls UserService to load the customer from the database. This is a function call in the same process.
  4. PaymentService charges the card through Stripe. This is the first network call.
  5. One database transaction saves the order row and the payment row. Both are saved, or neither is.
  6. NotificationService sends the confirmation email, and the route returns 201.

Problems it solves

  • Slow start on a new projectOne repo, one build, one deploy. You run the whole app on your laptop with one command.
  • Network failures between featuresModules call each other as functions. No timeouts, retries or API versions between them.
  • Keeping data consistentOne database transaction covers the order and the payment. Both are saved, or neither is.
  • Hard debuggingOne stack trace and one log stream show the full request from route to database.
  • Risky changes across featuresRenaming a method updates every caller in the IDE. The compiler finds every place that breaks.
  • High running costOne kind of server to run and monitor. No service discovery or message broker needed.

Problems it introduces

  • Every change redeploys everythingA one-line fix in Notifications means building and deploying Payments and Orders too.
  • Scaling is all or nothingIf only Orders is busy, you still start more copies of every module.
  • One fault can stop every featureA memory leak or crash in one module stops the process, so all features go down with it.
  • Module boundaries wear awayNothing stops OrderService from reading the users table directly. Cross-module foreign keys make a later split harder.
  • One tech stack for allEvery module uses the same language and framework version. A framework upgrade touches the whole app.
  • Large teams wait on each otherOne build, one test suite and one release schedule. Build and test time grow with the app.
Databasedb/schema.sqlEvery module keeps its tables in one database. Foreign keys can point from one module's table to another's.
CREATE TABLE users (
  id          UUID PRIMARY KEY,
  email       TEXT NOT NULL UNIQUE
);

CREATE TABLE orders (
  id          UUID PRIMARY KEY,
  user_id     UUID NOT NULL REFERENCES users(id),
  total       NUMERIC(10, 2) NOT NULL
);

CREATE TABLE payments (
  id          UUID PRIMARY KEY,
  order_id    UUID NOT NULL REFERENCES orders(id),
  amount      NUMERIC(10, 2) NOT NULL,
  provider_id TEXT NOT NULL
);

import express from "express";
import { Pool } from "pg";
import Stripe from "stripe";
import nodemailer from "nodemailer";
import { UserService } from "./modules/users/UserService";
import { PaymentService } from "./modules/payments/PaymentService";
import { NotificationService } from "./modules/notifications/NotificationService";
import { OrderService } from "./modules/orders/OrderService";
import { routes } from "./http/routes";

const db = new Pool();
const users = new UserService(db);
const payments = new PaymentService(new Stripe(process.env.STRIPE_KEY!));
const notifications = new NotificationService(nodemailer.createTransport(process.env.SMTP_URL));
const orders = new OrderService(db, users, payments, notifications);

express()
  .use(express.json())
  .use(routes(orders))
  .listen(3000);
Entry pointsrc/http/routes.tsTurns an HTTP request into a call on the Orders module.
import { Router } from "express";
import { OrderService } from "../modules/orders/OrderService";

export function routes(orders: OrderService): Router {
  const router = Router();

  router.post("/orders", async (req, res) => {
    const { userId, items, paymentMethodId } = req.body;
    const orderId = await orders.placeOrder(userId, items, paymentMethodId);
    res.status(201).json({ orderId });
  });

  return router;
}
Modulesrc/modules/orders/OrderService.tsCalls three other modules as plain function calls. The order and payment rows are saved in one transaction.
import { randomUUID } from "node:crypto";
import { Pool } from "pg";
import { UserService } from "../users/UserService";
import { PaymentService } from "../payments/PaymentService";
import { NotificationService } from "../notifications/NotificationService";

export type OrderItem = { productId: string; price: number; quantity: number };

export class OrderService {
  constructor(
    private readonly db: Pool,
    private readonly users: UserService,
    private readonly payments: PaymentService,
    private readonly notifications: NotificationService,
  ) {}

  async placeOrder(userId: string, items: OrderItem[], paymentMethodId: string): Promise<string> {
    const user = await this.users.getById(userId);
    const total = items.reduce((sum, item) => sum + item.price * item.quantity, 0);
    const providerId = await this.payments.charge(total, paymentMethodId);
    const orderId = randomUUID();

    const transaction = await this.db.connect();
    try {
      await transaction.query("BEGIN");
      await transaction.query(
        "INSERT INTO orders (id, user_id, total) VALUES ($1, $2, $3)",
        [orderId, user.id, total],
      );
      await this.payments.record(transaction, orderId, total, providerId);
      await transaction.query("COMMIT");
    } catch (error) {
      await transaction.query("ROLLBACK");
      throw error;
    } finally {
      transaction.release();
    }

    await this.notifications.sendOrderConfirmation(user.email, orderId);
    return orderId;
  }
}
Modulesrc/modules/users/UserService.tsOwns the users table. Other modules call it instead of reading the table.
import { Pool } from "pg";

export type User = { id: string; email: string };

export class UserService {
  constructor(private readonly db: Pool) {}

  async getById(userId: string): Promise<User> {
    const result = await this.db.query("SELECT id, email FROM users WHERE id = $1", [userId]);
    if (result.rowCount === 0) {
      throw new Error("The user does not exist.");
    }
    return result.rows[0];
  }
}
Modulesrc/modules/payments/PaymentService.tsCharges the card through Stripe, then saves the payment row inside the caller's transaction.
import { randomUUID } from "node:crypto";
import { PoolClient } from "pg";
import Stripe from "stripe";

export class PaymentService {
  constructor(private readonly stripe: Stripe) {}

  async charge(amount: number, paymentMethodId: string): Promise<string> {
    const paymentIntent = await this.stripe.paymentIntents.create({
      amount: Math.round(amount * 100),
      currency: "eur",
      payment_method: paymentMethodId,
      confirm: true,
    });
    return paymentIntent.id;
  }

  async record(transaction: PoolClient, orderId: string, amount: number, providerId: string): Promise<void> {
    await transaction.query(
      "INSERT INTO payments (id, order_id, amount, provider_id) VALUES ($1, $2, $3, $4)",
      [randomUUID(), orderId, amount, providerId],
    );
  }
}

namespace Shop.Http;

public record PlaceOrderRequest(Guid UserId, List<OrderItem> Items, string PaymentMethodId);

public static class OrderEndpoints
{
    public static void MapOrderEndpoints(this WebApplication app)
    {
        app.MapPost("/orders", async (PlaceOrderRequest request, OrderService orders) =>
        {
            var orderId = await orders.PlaceOrderAsync(request.UserId, request.Items, request.PaymentMethodId);
            return Results.Created($"/orders/{orderId}", new { orderId });
        });
    }
}
Modulesrc/Shop/Modules/Orders/OrderService.csCalls three other modules as plain method calls. The order and payment rows are saved in one transaction. Uses Dapper for SQL.
using Dapper;
using Npgsql;
using Shop.Modules.Notifications;
using Shop.Modules.Payments;
using Shop.Modules.Users;

namespace Shop.Modules.Orders;

public record OrderItem(string ProductId, decimal Price, int Quantity);

public class OrderService(
    NpgsqlDataSource db,
    UserService users,
    PaymentService payments,
    NotificationService notifications)
{
    public async Task<Guid> PlaceOrderAsync(Guid userId, IReadOnlyList<OrderItem> items, string paymentMethodId)
    {
        var user = await users.GetByIdAsync(userId);
        var total = items.Sum(item => item.Price * item.Quantity);
        var providerId = await payments.ChargeAsync(total, paymentMethodId);
        var orderId = Guid.NewGuid();

        await using var connection = await db.OpenConnectionAsync();
        await using var transaction = await connection.BeginTransactionAsync();

        await connection.ExecuteAsync(
            "INSERT INTO orders (id, user_id, total) VALUES (@orderId, @userId, @total)",
            new { orderId, userId = user.Id, total },
            transaction);
        await payments.RecordAsync(connection, transaction, orderId, total, providerId);

        await transaction.CommitAsync();

        await notifications.SendOrderConfirmationAsync(user.Email, orderId);
        return orderId;
    }
}
Modulesrc/Shop/Modules/Users/UserService.csOwns the users table. Other modules call it instead of reading the table.
using Dapper;
using Npgsql;

namespace Shop.Modules.Users;

public record User(Guid Id, string Email);

public class UserService(NpgsqlDataSource db)
{
    public async Task<User> GetByIdAsync(Guid userId)
    {
        await using var connection = await db.OpenConnectionAsync();
        var user = await connection.QuerySingleOrDefaultAsync<User>(
            "SELECT id, email FROM users WHERE id = @userId", new { userId });

        return user ?? throw new KeyNotFoundException("The user does not exist.");
    }
}
Modulesrc/Shop/Modules/Payments/PaymentService.csCharges the card through Stripe, then saves the payment row inside the caller's transaction.
using System.Data;
using Dapper;
using Stripe;

namespace Shop.Modules.Payments;

public class PaymentService(PaymentIntentService stripePayments)
{
    public async Task<string> ChargeAsync(decimal amount, string paymentMethodId)
    {
        var paymentIntent = await stripePayments.CreateAsync(new PaymentIntentCreateOptions
        {
            Amount = (long)Math.Round(amount * 100),
            Currency = "eur",
            PaymentMethod = paymentMethodId,
            Confirm = true,
        });
        return paymentIntent.Id;
    }

    public Task RecordAsync(IDbConnection connection, IDbTransaction transaction, Guid orderId, decimal amount, string providerId) =>
        connection.ExecuteAsync(
            "INSERT INTO payments (id, order_id, amount, provider_id) VALUES (@id, @orderId, @amount, @providerId)",
            new { id = Guid.NewGuid(), orderId, amount, providerId },
            transaction);
}
