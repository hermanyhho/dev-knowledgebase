Architecture / System topology

Microservices

Also called a microservice architecture. Named and described by James Lewis and Martin Fowler in 2014.

What it is

An application split into small, separate apps called services. Each service covers one business area, runs in its own process, is deployed on its own and owns its own database.

Services talk to each other over the network. This page shows the three most common ways: REST, gRPC and events.

This page uses the same shop as the monolith page. There, Orders, Users, Payments and Notifications were modules in one process. Here, each one is its own service, and an Analytics service is added to show one event reaching two services.

TermMeaningIn the example
ServiceA separate app for one business area, with its own deploy and its own data.Order service, User service
API gatewayThe one public address. It sends each outside request to the service that handles it.nginx routing /orders
Service discoveryHow a service finds the network address of another service.Docker DNS turns user-service into an address
ContractThe agreed shape of a request, reply or message. Both sides depend on it.payments.proto, OrderPlaced
Exchange and queueIn RabbitMQ, the exchange receives a message and copies it into every queue that asked for it. Each listening service reads its own queue.orders exchange, 2 queues
Database per serviceEach service has its own database. No other service reads it.Orders DB, Users DB, Payments DB
Eventual consistencyData in different services matches after a short delay, not at the same moment.Sales totals update just after the order is saved
The one rule: each service owns its data. Other services never read its database. They call its API or listen to its events.

How services talk

WayCaller waits?FormatGood forIn the example
RESTYesJSON over HTTPSimple requests. Easy to test with a browser or curl.Order service gets the customer from the User service
gRPCYesBinary Protocol Buffers over HTTP/2Fast calls between services, with a strict contract and generated code.Order service asks the Payment service to charge the card
EventNoMessage through a brokerTelling any number of services that something happened.Order service publishes OrderPlaced

REST and gRPC calls go straight from one service to another. They do not pass through the API gateway, which only handles requests from outside.

Diagram

Example flow:

Pick a flow and press Play to follow it through the diagram, step by step.

  1. The gateway sends POST /orders to one of the 3 copies of the order service.
  2. REST: the order service asks the user service for the customer and waits for the reply.
  3. gRPC: the order service asks the payment service to charge the card and waits. The payment service calls Stripe and saves the payment in its own database.
  4. The order service saves the order in its own database. No transaction covers both the payment and the order, because they are in different databases.
  5. Event: the order service publishes OrderPlaced and returns 201. It does not wait for anyone to read the event.
  6. RabbitMQ puts a copy of the event in each queue. The notification service sends the email and the analytics service updates the sales totals, each at its own speed.
  1. The order service reads USER_SERVICE_URL from its config: http://user-service:3000.
  2. It looks up the name user-service. Docker DNS returns the address of a user service copy. The request GET /users/42 goes straight there, not through the gateway.
  3. The user service reads the user from its own database.
  4. It replies 200 OK with JSON: { "id": "42", "email": "..." }. If the user does not exist, it replies 404.
  5. The order service checks the status code. A timeout or a 5xx status means the user service is down or slow, and the order service must decide what to do.
  1. Both services use the same payments.proto file. It defines the Charge method and its messages. A tool generates client and server code from it in each language.
  2. The order service calls the generated client: Charge(ChargeRequest). gRPC sends it as binary Protocol Buffers over HTTP/2 to payment-service:5000.
  3. The payment service runs Charge: it calls Stripe and saves the payment in its own database.
  4. It replies with a ChargeReply message. Errors come back as gRPC status codes, such as UNAVAILABLE or DEADLINE_EXCEEDED.
  1. The order service publishes OrderPlaced to the orders exchange with the routing key order.placed. Then it moves on.
  2. The exchange copies the message into every queue bound to order.placed. Each listening service has its own queue.
  3. The notification service reads its queue and sends the email. It confirms with ack, and RabbitMQ deletes that copy.
  4. The analytics service reads its own copy and adds the sale to its totals. If it is down, its messages wait in its queue until it starts again.

Problems it solves

  • Every change redeploys everythingA fix in the notification service deploys only that service. The others keep running.
  • Scaling is all or nothingRun 3 copies of the busy order service and 1 copy of the user service.
  • One fault stops every featureIf the notification service is down, orders still go through. The events wait in its queue.
  • Large teams wait on each otherEach team owns one service: its code, database and release schedule.
  • One tech stack for allEach service can use its own language, framework version or database type.
  • Adding a feature means changing existing codeThe analytics service listens to OrderPlaced. The order service did not change to support it.

Problems it introduces

  • Network calls can failEvery REST or gRPC call needs a timeout and a plan for when the other service is down or slow.
  • No transaction across servicesIf the order insert fails after the payment is saved, the payment must be refunded with extra code. Patterns such as saga and outbox handle this.
  • Data is split upNo joins or foreign keys across services. A report that needs orders and users must copy data into one place.
  • Harder debuggingOne request runs in several processes. You need a shared request ID and distributed tracing to follow it.
  • Much more to runA gateway, a broker, several databases, and a build, deploy and monitoring setup for each service.
  • Changes to contracts need coordinationChanging payments.proto or OrderPlaced breaks the services that use it, unless the change keeps old fields working.

Serviceorder-service/src/orderRoutes.tsUses all three ways: REST to get the user, gRPC to charge the card, and an event to tell everyone else.
import { randomUUID } from "node:crypto";
import { Router } from "express";
import { Pool } from "pg";
import { Channel } from "amqplib";
import { OrderPlaced } from "../../contracts/OrderPlaced";
import { getUser } from "./userClient";
import { charge } from "./paymentClient";

type OrderItem = { productId: string; price: number; quantity: number };

export function orderRoutes(db: Pool, events: Channel): Router {
  const router = Router();

  router.post("/orders", async (req, res) => {
    const { userId, paymentMethodId } = req.body;
    const items: OrderItem[] = req.body.items;

    const user = await getUser(userId);
    if (!user) {
      return res.status(422).json({ error: "The user does not exist." });
    }

    const orderId = randomUUID();
    const total = items.reduce((sum, item) => sum + item.price * item.quantity, 0);
    await charge(orderId, Math.round(total * 100), paymentMethodId);

    await db.query("INSERT INTO orders (id, user_id, total) VALUES ($1, $2, $3)", [orderId, userId, total]);

    const event: OrderPlaced = { orderId, userId, email: user.email, total };
    events.publish("orders", "order.placed", Buffer.from(JSON.stringify(event)));

    res.status(201).json({ orderId });
  });

  return router;
}
REST clientorder-service/src/userClient.tsA plain HTTP request with a JSON reply. USER_SERVICE_URL is http://user-service:3000, and Docker DNS turns user-service into the address of a copy. The timeout stops the order service from waiting forever.
export type User = { id: string; email: string };

export async function getUser(userId: string): Promise<User | null> {
  const response = await fetch(`${process.env.USER_SERVICE_URL}/users/${userId}`, {
    signal: AbortSignal.timeout(2000),
  });

  if (response.status === 404) return null;
  if (!response.ok) throw new Error(`The user service replied ${response.status}.`);

  return response.json();
}
gRPC clientorder-service/src/paymentClient.tsThe call reads like a local function, but runs on the payment service over HTTP/2. The method and message shapes come from payments.proto. The deadline stops it from waiting forever.
import { promisify } from "node:util";
import * as grpc from "@grpc/grpc-js";
import * as protoLoader from "@grpc/proto-loader";

const definition = protoLoader.loadSync("contracts/payments.proto", { longs: Number });
const paymentsPackage = grpc.loadPackageDefinition(definition).payments as any;
const paymentsClient = new paymentsPackage.Payments(
  process.env.PAYMENT_SERVICE_ADDRESS,
  grpc.credentials.createInsecure(),
);
const chargeCall = promisify(paymentsClient.charge.bind(paymentsClient));

export async function charge(orderId: string, amountCents: number, paymentMethodId: string): Promise<string> {
  const reply = await chargeCall(
    { orderId, amountCents, paymentMethodId },
    { deadline: Date.now() + 5000 },
  );
  return reply.providerId;
}
Serviceuser-service/src/userRoutes.tsA REST endpoint. Other services get user data here, never from the users table.
import { Router } from "express";
import { Pool } from "pg";

export function userRoutes(db: Pool): Router {
  const router = Router();

  router.get("/users/:id", async (req, res) => {
    const result = await db.query("SELECT id, email FROM users WHERE id = $1", [req.params.id]);
    if (result.rowCount === 0) {
      return res.status(404).json({ error: "The user does not exist." });
    }
    res.json(result.rows[0]);
  });

  return router;
}
Servicepayment-service/src/paymentsServer.tsA gRPC server for the Payments service in payments.proto. Errors go back to the caller as a gRPC status code.
import { randomUUID } from "node:crypto";
import * as grpc from "@grpc/grpc-js";
import * as protoLoader from "@grpc/proto-loader";
import { Pool } from "pg";
import Stripe from "stripe";

const definition = protoLoader.loadSync("contracts/payments.proto", { longs: Number });
const paymentsPackage = grpc.loadPackageDefinition(definition).payments as any;

export function startPaymentsServer(db: Pool, stripe: Stripe): void {
  const server = new grpc.Server();

  server.addService(paymentsPackage.Payments.service, {
    async charge(call: any, callback: grpc.sendUnaryData<{ providerId: string }>) {
      const { orderId, amountCents, paymentMethodId } = call.request;
      try {
        const paymentIntent = await stripe.paymentIntents.create({
          amount: amountCents,
          currency: "eur",
          payment_method: paymentMethodId,
          confirm: true,
        });

        await db.query(
          "INSERT INTO payments (id, order_id, amount, provider_id) VALUES ($1, $2, $3, $4)",
          [randomUUID(), orderId, amountCents / 100, paymentIntent.id],
        );

        callback(null, { providerId: paymentIntent.id });
      } catch {
        callback({ code: grpc.status.INTERNAL, message: "The payment failed." });
      }
    },
  });

  server.bindAsync("0.0.0.0:5000", grpc.ServerCredentials.createInsecure(), () => {});
}
Servicenotification-service/src/orderPlacedConsumer.tsCreates its own queue and binds it to order.placed on the orders exchange. A message is deleted only after ack, so a crash before that means it is read again.
import { Channel } from "amqplib";
import { Transporter } from "nodemailer";
import { OrderPlaced } from "../../contracts/OrderPlaced";

const queueName = "notifications.order-placed";

export async function consumeOrderPlaced(events: Channel, mailer: Transporter): Promise<void> {
  await events.assertQueue(queueName);
  await events.bindQueue(queueName, "orders", "order.placed");

  await events.consume(queueName, async (message) => {
    if (!message) return;
    const event: OrderPlaced = JSON.parse(message.content.toString());

    await mailer.sendMail({
      from: "shop@example.com",
      to: event.email,
      subject: "Order received",
      text: `Your order ${event.orderId} has been received.`,
    });

    events.ack(message);
  });
}

Serviceorder-service/OrderEndpoints.csUses all three ways: REST to get the user, gRPC to charge the card, and an event to tell everyone else.
using Contracts;
using Dapper;
using MassTransit;
using Npgsql;

namespace OrderService;

public record OrderItem(string ProductId, decimal Price, int Quantity);
public record PlaceOrderRequest(Guid UserId, List<OrderItem> Items, string PaymentMethodId);

public static class OrderEndpoints
{
    public static void MapOrderEndpoints(this WebApplication app)
    {
        app.MapPost("/orders", async (
            PlaceOrderRequest request,
            UserClient users,
            PaymentClient payments,
            NpgsqlDataSource db,
            IPublishEndpoint events) =>
        {
            var user = await users.GetUserAsync(request.UserId);
            if (user is null)
                return Results.UnprocessableEntity(new { error = "The user does not exist." });

            var orderId = Guid.NewGuid();
            var total = request.Items.Sum(item => item.Price * item.Quantity);
            await payments.ChargeAsync(orderId, (long)Math.Round(total * 100), request.PaymentMethodId);

            await using var connection = await db.OpenConnectionAsync();
            await connection.ExecuteAsync(
                "INSERT INTO orders (id, user_id, total) VALUES (@orderId, @userId, @total)",
                new { orderId, userId = request.UserId, total });

            await events.Publish(new OrderPlaced(orderId, request.UserId, user.Email, total));

            return Results.Created($"/orders/{orderId}", new { orderId });
        });
    }
}

gRPC clientorder-service/PaymentClient.csPayments.PaymentsClient, ChargeRequest and ChargeReply are generated from payments.proto by Grpc.Tools. The deadline stops the call from waiting forever.
using Contracts.Payments;

namespace OrderService;

public class PaymentClient(Payments.PaymentsClient payments)
{
    public async Task<string> ChargeAsync(Guid orderId, long amountCents, string paymentMethodId)
    {
        var reply = await payments.ChargeAsync(
            new ChargeRequest
            {
                OrderId = orderId.ToString(),

Servicepayment-service/PaymentsGrpcService.csOverrides the Charge method generated from payments.proto. An unhandled exception reaches the caller as a gRPC error status.
using Contracts.Payments;
using Dapper;
using Grpc.Core;
using Npgsql;
using Stripe;

namespace PaymentService;

public class PaymentsGrpcService(PaymentIntentService stripePayments, NpgsqlDataSource db) : Payments.PaymentsBase
{
    public override async Task<ChargeReply> Charge(ChargeRequest request, ServerCallContext context)
    {
        var paymentIntent = await stripePayments.CreateAsync(new PaymentIntentCreateOptions
        {
            Amount = request.AmountCents,
            Currency = "eur",
            PaymentMethod = request.PaymentMethodId,
            Confirm = true,
        });

        await using var connection = await db.OpenConnectionAsync();
        await connection.ExecuteAsync(
            "INSERT INTO payments (id, order_id, amount, provider_id) VALUES (@id, @orderId, @amount, @providerId)",
            new
            {
                id = Guid.NewGuid(),
                orderId = Guid.Parse(request.OrderId),
                amount = request.AmountCents / 100m,
                providerId = paymentIntent.Id,
            });

        return new ChargeReply { ProviderId = paymentIntent.Id };
    }
}
