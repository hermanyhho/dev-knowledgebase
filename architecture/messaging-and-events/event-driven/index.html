Architecture / Messaging and events

Event-Driven Architecture

Often shortened to EDA. Services react to events instead of calling each other.

What it is

A way to connect services where each one publishes events: records of things that happened, such as "order placed". Other services read those events and act on them. The service that publishes an event does not know who reads it.

Events go through a broker, a server that stores them until consumers read them. This page uses Kafka. The microservices page uses RabbitMQ, and the comparison below shows how the two differ.

When each service reacts to events on its own, with no central service giving orders, the flow is called choreography. The saga page shows the other option, orchestration.

TermMeaningIn the example
EventA record of something that happened, named in past tense.OrderPlaced, PaymentCaptured
ProducerA service that publishes events.Order service
ConsumerA service that reads events and acts on them.Inventory service
TopicA named list of events in Kafka. Producers add to the end, consumers read in order.orders, payments
PartitionA topic is split into partitions so several consumers can read in parallel. Events with the same key always go to the same partition.3 partitions, key = order ID
OffsetThe position of an event in a partition. Each consumer group stores how far it has read."Inventory has read up to offset 1041"
Consumer groupThe copies of one service that share the work of reading a topic. Each group gets every event once.inventory-service
At-least-once deliveryThe broker may deliver the same event more than once, but never zero times.A restart can resend OrderPlaced
Idempotent consumerA consumer that gives the same result when it handles the same event twice.The processed_events table
Dead-letter topicWhere events go after they fail too many times, so they do not block later events.shipping.dead-letter
Main rule: a producer publishes what happened and does not know who reads it. Each consumer decides on its own what to do, and must handle the same event arriving twice.

How a RabbitMQ queue differs from a Kafka topic

RabbitMQ queueKafka topic
After a consumer reads a messageThe message is deletedThe event stays until its retention period ends, for example 7 days
Several services read the same eventsOne queue per service, each bound to the same exchangeOne consumer group per service, all reading the same topic
Reading old events againNot possible after deletionMove the consumer group's offset back
Order of eventsKept per queueKept per partition only
Common useTask queues and routing rulesHigh-volume event streams that can be read again

Diagram

Example flow:

Pick a flow and press Play to follow it through the diagram, step by step.

  1. The order service saves the order and publishes OrderPlaced to the orders topic, with the order ID as key. It replies 202 Accepted at once, without waiting for the other services.
  2. Inventory and Notification both read OrderPlaced. Each has its own consumer group, so each gets every event.
  3. Notification emails "order received". Inventory reserves the stock and publishes StockReserved to the inventory topic.
  4. Payment reads StockReserved, charges the card and publishes PaymentCaptured to the payments topic.
  5. Shipping books a pickup with the carrier. Notification sends a receipt, using the email it saved from OrderPlaced.
  6. No service called another. The order of the steps comes only from which service reads which topic. This is choreography.
  1. Inventory reads OrderPlaced, reserves the stock and commits its database transaction. Then the service stops, before Kafka records that the event was read.
  2. When Inventory starts again, Kafka sends the same OrderPlaced again. Kafka delivers at least once, not exactly once.
  3. Inventory tries to insert the event ID into its processed_events table. The ID is already there, so it skips the event. The stock is reserved only once.
  1. Shipping reads PaymentCaptured, but the carrier's API is down and the call fails.
  2. Shipping tries 3 times, waiting a little longer each time.
  3. It still fails, so Shipping copies the event to shipping.dead-letter with the error in a header, and moves on. Events for other orders are not blocked.
  4. A developer reads the dead-letter topic, fixes the cause and sends the event to Shipping again.

Problems it solves

  • Services waiting on each otherThe order service replies at once. Stock, payment and shipping happen after, at their own speed.
  • Adding a feature means changing the producerA new service subscribes to a topic. The order service does not change.
  • One slow service holds up the othersEvents wait in the topic until that service catches up. The other services keep working.
  • Traffic spikesKafka stores the events. Consumers work through them at the speed they can handle.
  • History is lost after processingKafka keeps events for the retention period. A new consumer can read from the start.
  • Services tied to each other's APIsServices share only event shapes, not endpoints or addresses.

Problems it introduces

  • The whole flow is hard to seeNo single file shows the order process. It is spread across five consumers, so you need tracing and diagrams.
  • Data is out of date for a momentThe order shows as placed before stock is reserved. The user interface must show states such as "processing".
  • The same event can arrive twiceEvery consumer must handle duplicates, for example with a processed_events table.
  • Order only within a partitionEvents with the same key stay in order. Events with different keys, or in different topics, can be read in any order.
  • Failed events need a planRetries, dead-letter topics and a way to send events again all need code and tools.
  • Event shapes are hard to changeOld events stay in the topic, so consumers must read old and new versions of each event.

import { randomUUID } from "node:crypto";
import { Producer } from "kafkajs";
import { Pool } from "pg";
import { OrderPlaced } from "../../contracts/orders";

export type PlaceOrderRequest = {
  customerEmail: string;
  items: { productId: string; quantity: number }[];
  total: number;
  paymentMethodId: string;
};

export async function placeOrder(db: Pool, producer: Producer, request: PlaceOrderRequest): Promise<string> {
  const orderId = randomUUID();
  await db.query(
    "INSERT INTO orders (id, customer_email, total, status) VALUES ($1, $2, $3, 'placed')",
    [orderId, request.customerEmail, request.total],
  );

  const event: OrderPlaced = {
    eventId: randomUUID(),
    type: "OrderPlaced",
    occurredAt: new Date().toISOString(),
    orderId,
    ...request,
  };
  await producer.send({
    topic: "orders",
    messages: [{ key: orderId, value: JSON.stringify(event) }],
  });

  return orderId;
}

If stock is short, the savepoint undoes only the reservation. If the service stops after the commit but before the reply is sent, the reply is lost, because a resend is skipped. The outbox page fixes this.
import { Kafka, Producer } from "kafkajs";
import { Pool, PoolClient } from "pg";
import { OrderPlaced } from "../../contracts/orders";
import { InventoryEvent } from "../../contracts/inventory";

async function reserveStock(transaction: PoolClient, items: OrderPlaced["items"]): Promise<boolean> {
  for (const item of items) {
    const updated = await transaction.query(
      "UPDATE stock SET reserved = reserved + $2 WHERE product_id = $1 AND on_hand - reserved >= $2",
      [item.productId, item.quantity],
    );
    if (updated.rowCount === 0) return false;
  }
  return true;
}

async function reserveOnce(db: Pool, event: OrderPlaced): Promise<InventoryEvent | null> {
  const transaction = await db.connect();
  try {
    await transaction.query("BEGIN");
    const firstDelivery = await transaction.query(
      "INSERT INTO processed_events (event_id) VALUES ($1) ON CONFLICT DO NOTHING",
      [event.eventId],
    );
    if (firstDelivery.rowCount === 0) {
      await transaction.query("ROLLBACK");
      return null;
    }

    await transaction.query("SAVEPOINT reserve");
    const reserved = await reserveStock(transaction, event.items);
    if (!reserved) await transaction.query("ROLLBACK TO SAVEPOINT reserve");
    await transaction.query("COMMIT");

    const occurredAt = new Date().toISOString();
    return reserved
      ? { eventId: `stock-reserved-${event.eventId}`, type: "StockReserved", occurredAt, orderId: event.orderId, total: event.total, paymentMethodId: event.paymentMethodId }
      : { eventId: `stock-unavailable-${event.eventId}`, type: "StockUnavailable", occurredAt, orderId: event.orderId };
  } finally {
    transaction.release();
  }
}

export async function startOrderPlacedConsumer(kafka: Kafka, db: Pool, producer: Producer): Promise<void> {
  const consumer = kafka.consumer({ groupId: "inventory-service" });
  await consumer.connect();
  await consumer.subscribe({ topic: "orders" });

  await consumer.run({
    eachMessage: async ({ message }) => {
      const event: OrderPlaced = JSON.parse(message.value!.toString());
      const reply = await reserveOnce(db, event);
      if (!reply) return;

      await producer.send({
        topic: "inventory",
        messages: [{ key: event.orderId, value: JSON.stringify(reply) }],
      });
    },
  });
}
Consumerpayment-service/src/stockReservedConsumer.tsThe event ID is passed to Stripe as an idempotency key, so a second delivery does not charge the card twice. The new event's ID is built from the old one, so a resend produces the same ID.
import { Kafka, Producer } from "kafkajs";
import Stripe from "stripe";
import { InventoryEvent, StockReserved } from "../../contracts/inventory";
import { PaymentEvent } from "../../contracts/payments";

async function chargeCard(stripe: Stripe, event: StockReserved): Promise<PaymentEvent> {
  const occurredAt = new Date().toISOString();
  try {
    const paymentIntent = await stripe.paymentIntents.create(
      { amount: Math.round(event.total * 100), currency: "eur", payment_method: event.paymentMethodId, confirm: true },
      { idempotencyKey: event.eventId },
    );
    return { eventId: `payment-captured-${event.eventId}`, type: "PaymentCaptured", occurredAt, orderId: event.orderId, amount: event.total, providerId: paymentIntent.id };
  } catch (error) {
    if (error instanceof Stripe.errors.StripeCardError) {
      return { eventId: `payment-failed-${event.eventId}`, type: "PaymentFailed", occurredAt, orderId: event.orderId, reason: error.message };
    }
    throw error;
  }
}

export async function startStockReservedConsumer(kafka: Kafka, stripe: Stripe, producer: Producer): Promise<void> {
  const consumer = kafka.consumer({ groupId: "payment-service" });
  await consumer.connect();
  await consumer.subscribe({ topic: "inventory" });

  await consumer.run({
    eachMessage: async ({ message }) => {
      const event: InventoryEvent = JSON.parse(message.value!.toString());
      if (event.type !== "StockReserved") return;

      const outcome = await chargeCard(stripe, event);
      await producer.send({
        topic: "payments",
        messages: [{ key: event.orderId, value: JSON.stringify(outcome) }],
      });
    },
  });
}
Consumershipping-service/src/paymentCapturedConsumer.tsTries 3 times, waiting longer each time. After that, it copies the event to the dead-letter topic and returns, so the next event in the partition is not blocked.
import { setTimeout as sleep } from "node:timers/promises";
import { Kafka, Producer } from "kafkajs";
import { PaymentEvent } from "../../contracts/payments";

export type CarrierClient = { bookPickup(orderId: string): Promise<void> };

const maxAttempts = 3;

export async function startPaymentCapturedConsumer(kafka: Kafka, carrier: CarrierClient, producer: Producer): Promise<void> {
  const consumer = kafka.consumer({ groupId: "shipping-service" });
  await consumer.connect();
  await consumer.subscribe({ topic: "payments" });

  await consumer.run({
    eachMessage: async ({ message }) => {
      const event: PaymentEvent = JSON.parse(message.value!.toString());
      if (event.type !== "PaymentCaptured") return;

      for (let attempt = 1; attempt <= maxAttempts; attempt++) {
        try {
          await carrier.bookPickup(event.orderId);
          return;
        } catch (error) {
          if (attempt === maxAttempts) {
            await producer.send({
              topic: "shipping.dead-letter",
              messages: [{
                key: message.key,
                value: message.value,
                headers: { error: String(error), "failed-at": new Date().toISOString(), attempts: String(attempt) },
              }],
            });
            return;
          }
          await sleep(attempt * 1000);
        }
      }
    },
  });
}

export async function startNotificationConsumer(kafka: Kafka, db: Pool, mailer: Transporter): Promise<void> {
  const consumer = kafka.consumer({ groupId: "notification-service" });
  await consumer.connect();
  await consumer.subscribe({ topics: ["orders", "payments"] });

  await consumer.run({
    eachMessage: async ({ message }) => {
      const event: OrderPlaced | PaymentEvent = JSON.parse(message.value!.toString());

      if (event.type === "OrderPlaced") {
        await db.query(
          "INSERT INTO order_contacts (order_id, email) VALUES ($1, $2) ON CONFLICT DO NOTHING",
          [event.orderId, event.customerEmail],
        );
        await mailer.sendMail({ to: event.customerEmail, subject: "Order received", text: `Order ${event.orderId} is received.` });
      }

      if (event.type === "PaymentCaptured") {
        const contact = await db.query("SELECT email FROM order_contacts WHERE order_id = $1", [event.orderId]);
        await mailer.sendMail({ to: contact.rows[0].email, subject: "Payment received", text: `We received ${event.amount} EUR.` });
      }
    },
  });
}

Consumersrc/InventoryService/OrderPlacedConsumer.csIdempotent: the event ID and the stock change are saved in one transaction, so a second delivery is skipped. The offset is committed only after the work is done, which is what makes delivery at-least-once. If the service stops after the commit but before the reply is sent, the reply is lost, because a resend is skipped. The outbox page fixes this.
using System.Text.Json;
using Confluent.Kafka;
using Dapper;
using Npgsql;
using Shop.Contracts;

namespace InventoryService;

public class OrderPlacedConsumer(
    IConsumer<string, string> consumer,
    IProducer<string, string> producer,
    NpgsqlDataSource db) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        await Task.Yield();
        consumer.Subscribe("orders");

        while (!stoppingToken.IsCancellationRequested)
        {
            var result = consumer.Consume(stoppingToken);
            var orderPlaced = JsonSerializer.Deserialize<OrderPlaced>(result.Message.Value)!;

            var reply = await ReserveOnceAsync(orderPlaced);
            if (reply is not null)
            {
                await producer.ProduceAsync("inventory", new Message<string, string>
                {
                    Key = orderPlaced.OrderId.ToString(),
                    Value = JsonSerializer.Serialize(reply, reply.GetType()),
                });
            }

            consumer.Commit(result);
        }
    }

    private async Task<object?> ReserveOnceAsync(OrderPlaced orderPlaced)
    {
        await using var connection = await db.OpenConnectionAsync();
        await using var transaction = await connection.BeginTransactionAsync();

        var firstDelivery = await connection.ExecuteAsync(
            "INSERT INTO processed_events (event_id) VALUES (@EventId) ON CONFLICT DO NOTHING",
            new { orderPlaced.EventId }, transaction);
        if (firstDelivery == 0) return null;

        await transaction.SaveAsync("reserve");
        var reserved = await ReserveStockAsync(connection, transaction, orderPlaced.Items);
        if (!reserved) await transaction.RollbackAsync("reserve");
        await transaction.CommitAsync();

        return reserved
            ? new StockReserved($"stock-reserved-{orderPlaced.EventId}", DateTimeOffset.UtcNow, orderPlaced.OrderId, orderPlaced.Total, orderPlaced.PaymentMethodId)
            : new StockUnavailable($"stock-unavailable-{orderPlaced.EventId}", DateTimeOffset.UtcNow, orderPlaced.OrderId);
    }

    private static async Task<bool> ReserveStockAsync(NpgsqlConnection connection, NpgsqlTransaction transaction, List<OrderItem> items)
    {
        foreach (var item in items)
        {
            var updated = await connection.ExecuteAsync(
                "UPDATE stock SET reserved = reserved + @Quantity WHERE product_id = @ProductId AND on_hand - reserved >= @Quantity",
                item, transaction);
            if (updated == 0) return false;
        }
        return true;
    }
}
Consumersrc/PaymentService/StockReservedConsumer.csThe event ID is passed to Stripe as an idempotency key, so a second delivery does not charge the card twice. The new event's ID is built from the old one, so a resend produces the same ID.
using System.Text.Json;
using Confluent.Kafka;
using Shop.Contracts;
using Stripe;

namespace PaymentService;

public class StockReservedConsumer(
    IConsumer<string, string> consumer,
    IProducer<string, string> producer,
    PaymentIntentService stripePayments) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        await Task.Yield();
        consumer.Subscribe("inventory");

        while (!stoppingToken.IsCancellationRequested)
        {
            var result = consumer.Consume(stoppingToken);
            using var document = JsonDocument.Parse(result.Message.Value);

            if (document.RootElement.GetProperty("Type").GetString() == nameof(StockReserved))
            {
                var stockReserved = document.Deserialize<StockReserved>()!;
                var outcome = await ChargeCardAsync(stockReserved);
                await producer.ProduceAsync("payments", new Message<string, string>
                {
                    Key = stockReserved.OrderId.ToString(),
                    Value = JsonSerializer.Serialize(outcome, outcome.GetType()),
                });
            }

            consumer.Commit(result);
        }
    }

    private async Task<object> ChargeCardAsync(StockReserved stockReserved)
    {
        try
        {
            var paymentIntent = await stripePayments.CreateAsync(
                new PaymentIntentCreateOptions
                {
                    Amount = (long)Math.Round(stockReserved.Total * 100),
                    Currency = "eur",
                    PaymentMethod = stockReserved.PaymentMethodId,
                    Confirm = true,
                },
                new RequestOptions { IdempotencyKey = stockReserved.EventId });

            return new PaymentCaptured($"payment-captured-{stockReserved.EventId}", DateTimeOffset.UtcNow,
                stockReserved.OrderId, stockReserved.Total, paymentIntent.Id);
        }
        catch (StripeException error) when (error.StripeError?.Type == "card_error")
        {
            return new PaymentFailed($"payment-failed-{stockReserved.EventId}", DateTimeOffset.UtcNow,
                stockReserved.OrderId, error.Message);
        }
    }
}
Consumersrc/ShippingService/PaymentCapturedConsumer.csTries 3 times, waiting longer each time. After that, it copies the event to the dead-letter topic and commits the offset, so the next event in the partition is not blocked.
using System.Text;
using System.Text.Json;
using Confluent.Kafka;
using Shop.Contracts;

namespace ShippingService;

public interface ICarrierClient
{
    Task BookPickupAsync(Guid orderId);
}

public class PaymentCapturedConsumer(
    IConsumer<string, string> consumer,
    IProducer<string, string> producer,
    ICarrierClient carrier) : BackgroundService
{
    private const int MaxAttempts = 3;

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        await Task.Yield();
        consumer.Subscribe("payments");

        while (!stoppingToken.IsCancellationRequested)
        {
            var result = consumer.Consume(stoppingToken);
            using var document = JsonDocument.Parse(result.Message.Value);

            if (document.RootElement.GetProperty("Type").GetString() == nameof(PaymentCaptured))
            {
                var paymentCaptured = document.Deserialize<PaymentCaptured>()!;
                await BookPickupOrDeadLetterAsync(paymentCaptured, result.Message, stoppingToken);
            }

            consumer.Commit(result);
        }
    }

    private async Task BookPickupOrDeadLetterAsync(PaymentCaptured paymentCaptured, Message<string, string> original, CancellationToken stoppingToken)
    {
        for (var attempt = 1; ; attempt++)
        {
            try
            {
                await carrier.BookPickupAsync(paymentCaptured.OrderId);
                return;
            }
            catch (HttpRequestException) when (attempt < MaxAttempts)
            {
                await Task.Delay(TimeSpan.FromSeconds(attempt), stoppingToken);
            }
            catch (HttpRequestException error)
            {
                await producer.ProduceAsync("shipping.dead-letter", new Message<string, string>
                {
                    Key = original.Key,
                    Value = original.Value,
                    Headers = new Headers
                    {
                        { "error", Encoding.UTF8.GetBytes(error.Message) },
                        { "failed-at", Encoding.UTF8.GetBytes(DateTimeOffset.UtcNow.ToString("O")) },
                        { "attempts", Encoding.UTF8.GetBytes(attempt.ToString()) },
                    },
                });
                return;
            }
        }
    }
}
Consumersrc/NotificationService/NotificationConsumer.csReads two topics. It saves the email from OrderPlaced in its own table and uses it when PaymentCaptured arrives, instead of calling the order service. A duplicate email is acceptable here, so this consumer does not check for duplicates.
using System.Net.Mail;
using System.Text.Json;
using Confluent.Kafka;
using Dapper;
using Npgsql;
using Shop.Contracts;

namespace NotificationService;

public class NotificationConsumer(
    IConsumer<string, string> consumer,
    NpgsqlDataSource db,
    SmtpClient smtp) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        await Task.Yield();
        consumer.Subscribe(["orders", "payments"]);

        while (!stoppingToken.IsCancellationRequested)
        {
            var result = consumer.Consume(stoppingToken);
            using var document = JsonDocument.Parse(result.Message.Value);
            await using var connection = await db.OpenConnectionAsync(stoppingToken);

            switch (document.RootElement.GetProperty("Type").GetString())
            {
                case nameof(OrderPlaced):
                    var orderPlaced = document.Deserialize<OrderPlaced>()!;
                    await connection.ExecuteAsync(
                        "INSERT INTO order_contacts (order_id, email) VALUES (@OrderId, @CustomerEmail) ON CONFLICT DO NOTHING",
                        new { orderPlaced.OrderId, orderPlaced.CustomerEmail });
                    await smtp.SendMailAsync("shop@example.com", orderPlaced.CustomerEmail,
                        "Order received", $"Order {orderPlaced.OrderId} is received.", stoppingToken);
                    break;

                case nameof(PaymentCaptured):
                    var paymentCaptured = document.Deserialize<PaymentCaptured>()!;
                    var email = await connection.QuerySingleAsync<string>(
                        "SELECT email FROM order_contacts WHERE order_id = @OrderId", new { paymentCaptured.OrderId });
                    await smtp.SendMailAsync("shop@example.com", email,
                        "Payment received", $"We received {paymentCaptured.Amount} EUR.", stoppingToken);
                    break;
            }

            consumer.Commit(result);
        }
    }
}
