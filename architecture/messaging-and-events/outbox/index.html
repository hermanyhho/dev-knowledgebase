Architecture / Messaging and events

Transactional Outbox

Usually called the outbox pattern. Makes sure an event is sent if, and only if, the data change it describes was saved.

What it is

A service often has to do two things for one action: save data in its database and publish an event to a broker such as Kafka. These are two separate systems, and no transaction covers both. This is called a dual write. If the service stops between the two steps, the data is saved but the event is never sent.

The outbox pattern removes the second write from the request. The service saves the event as a row in an outbox table, in the same database transaction as the data. A separate process, the relay, reads new outbox rows and publishes them to the broker.

The relay can publish a row and stop before marking it as sent, so the same event can be published twice. Consumers must therefore skip duplicates, as shown on the event-driven architecture page.

Logging and monitoring

With an outbox, a request can succeed while its event waits. If the relay stops, nothing fails visibly, but events pile up. Watch the outbox itself, not only the logs.

The correlation ID is saved in the outbox row, so the relay can put it back in the Kafka headers. Without that column, the link between the HTTP request and the event would be lost at the relay.

Things to know before you build an outbox

PointDetail
Same database as the dataThe outbox table must be in the same database as the data it describes. One transaction cannot cover two databases, so an outbox in a separate "events" database brings the dual write back.
Libraries already do thisIn .NET, MassTransit, NServiceBus and Wolverine include a transactional outbox, so you rarely write the relay yourself. Node has no common library, so teams write a relay like the one below or use Debezium.
A row that always failsA message that Kafka always rejects, for example one over the 1 MB default size limit, must not block the rows behind it. The relay counts attempts per row and marks a row as failed after 5. Skipping a row means later events for the same key are published before it.
It only covers messagesOther side effects, such as charging a card or sending an email from the request, are not covered. Use idempotency keys for those, as the payment service does on the event-driven architecture page.
Waking the relay soonerPostgres LISTEN and NOTIFY can wake the relay as soon as a row is inserted. The timer then only acts as a backup.
Event versionsOld rows and old messages stay around for days, so put a version number in each payload. Consumers then know which shape they are reading.

  4. The outbox relay checks the table every second and finds the unsent row.
  5. It publishes the event to the orders topic, with the order ID as key and the saved correlation ID in the headers.
  6. It marks the row as sent by setting sent_at.
  7. Inventory reads OrderPlaced as usual.
  1. The order service saves the order and commits.
  2. Then it calls Kafka directly. If the service stops, the network fails or Kafka is down at that moment, the event is never sent.
  3. The order exists, but Inventory never reserves stock and the customer gets no email. Nothing tries again, because nothing recorded that an event was due.
  4. Publishing to Kafka first does not help. If the insert then fails, other services act on an order that does not exist.
  1. The relay publishes OrderPlaced to Kafka. Then it stops before it marks the row as sent.
  2. When it starts again, the row is still unsent, so it publishes the same event again.
  3. Inventory gets OrderPlaced twice. Its processed_events table already holds the event ID, so it skips the second copy. The outbox gives at-least-once delivery, and the consumer handles duplicates.
  1. The relay picks a row whose message is larger than Kafka's 1 MB limit. Kafka rejects it.
  2. The relay adds 1 to the row's attempts, saves the error in last_error and logs a warning. It goes on to the next row, so the rest of the batch is still published.
  3. After 5 failed attempts, the relay sets failed_at and logs an error. The row is no longer picked, and the failed-rows alert fires.
  4. A developer fixes the cause and resets failed_at and attempts. The relay picks the row up on its next poll.

Problems it solves

  • Lost eventsThe event is saved with the data. If publishing fails, the row stays unsent and the relay tries again.
  • Events for changes that never happenedThe event exists only if the transaction committed, so consumers never see an order that was rolled back.
  • Requests that fail when the broker is downThe request only needs the database. Events wait in the table until Kafka is back.
  • No record of what was sentThe outbox table shows every event, when it was created and when it was sent.
  • Lost replies in consumersA consumer that also publishes, such as Inventory, writes its reply to its own outbox in the same transaction as its work.

Problems it introduces

  • Duplicate eventsThe relay can publish a row twice, so every consumer must skip duplicates.
  • A short delayA polling relay adds up to one interval, for example 1 second, before an event is published.
  • Another process to runThe relay must run, be monitored and recover after a crash, or events silently pile up.
  • The table keeps growingSent rows need a cleanup job, or queries on the table get slower.
  • Extra database loadPolling runs a query every interval. A partial index on unsent rows keeps it fast.
  • Order with several relay copiesTwo relays can pick rows out of order. Run one relay, or make sure each copy handles different message keys.
  • Failed rows need a personA row marked as failed waits until someone fixes the cause and resets it. Until then, that event has not been sent.
Tablesdb/schema.sqlid grows with each insert, so the relay sends rows in the order they were written. attempts, last_error and failed_at let the relay give up on a row that always fails. SELECT
  count(*) FILTER (WHERE sent_at IS NULL AND failed_at IS NULL) AS waiting_events,
  count(*) FILTER (WHERE failed_at IS NOT NULL) AS failed_events,
  COALESCE(EXTRACT(EPOCH FROM now() - min(created_at) FILTER (WHERE sent_at IS NULL AND failed_at IS NULL)), 0)
    AS oldest_waiting_age_seconds
FROM outbox;

UPDATE outbox
SET failed_at = NULL, attempts = 0, last_error = NULL
WHERE id = $1;

DELETE FROM outbox
WHERE sent_at < now() - INTERVAL '7 days';

Writes the outboxorder-service/src/placeOrder.tsThe order row and the outbox row are written in one transaction. There is no Kafka code here at all.
import { randomUUID } from "node:crypto";
import { Pool } from "pg";
import { Logger } from "pino";
import { OrderPlaced } from "../../contracts/orders";

export type PlaceOrderRequest = {
  customerEmail: string;
  items: { productId: string; quantity: number }[];
  total: number;
  paymentMethodId: string;
};

export async function placeOrder(db: Pool, logger: Logger, correlationId: string, request: PlaceOrderRequest): Promise<string> {
  const orderId = randomUUID();
  const event: OrderPlaced = {
    eventId: randomUUID(),
    type: "OrderPlaced",
    occurredAt: new Date().toISOString(),
    orderId,
    ...request,
  };

  const transaction = await db.connect();
  try {
    await transaction.query("BEGIN");
    await transaction.query(
      "INSERT INTO orders (id, customer_email, total, status) VALUES ($1, $2, $3, 'placed')",
      [orderId, request.customerEmail, request.total],
    );
    await transaction.query(
      `INSERT INTO outbox (event_id, topic, message_key, event_type, payload, correlation_id)
       VALUES ($1, 'orders', $2, $3, $4, $5)`,
      [event.eventId, orderId, event.type, JSON.stringify(event), correlationId],
    );
    await transaction.query("COMMIT");
  } catch (error) {
    await transaction.query("ROLLBACK");
    throw error;
  } finally {
    transaction.release();
  }

  logger.info({ correlationId, orderId, eventId: event.eventId, eventType: event.type }, "saved order and outbox event");
  return orderId;
}
Relayorder-service/src/outboxRelay.tsFOR UPDATE SKIP LOCKED locks the rows it picks, so a second relay copy picks other rows instead of waiting. Each row is published on its own: a failure only adds to that row's attempts, and after 5 the row is marked as failed so it stops blocking the rest. If the relay stops mid-batch, the whole batch is waiting again and is published again.
import { setTimeout as sleep } from "node:timers/promises";
import { Producer } from "kafkajs";
import { Pool, PoolClient } from "pg";
import { Logger } from "pino";

const batchSize = 100;
const pollIntervalMs = 1000;
const maxAttempts = 5;

type OutboxRow = {
  id: string;
  event_id: string;
  topic: string;
  message_key: string;
  event_type: string;
  payload: unknown;
  correlation_id: string;
  attempts: number;
};

async function publishRow(transaction: PoolClient, producer: Producer, logger: Logger, row: OutboxRow): Promise<void> {
  const rowLog = logger.child({ correlationId: row.correlation_id, eventId: row.event_id, eventType: row.event_type });
  try {
    const [stored] = await producer.send({
      topic: row.topic,
      messages: [{
        key: row.message_key,
        value: JSON.stringify(row.payload),
        headers: { "correlation-id": row.correlation_id, "causation-id": row.correlation_id },
      }],
    });
    await transaction.query("UPDATE outbox SET sent_at = now() WHERE id = $1", [row.id]);
    rowLog.info({ topic: row.topic, partition: stored.partition, offset: stored.baseOffset }, "published outbox event");
  } catch (error) {
    const attempts = row.attempts + 1;
    const givingUp = attempts >= maxAttempts;
    await transaction.query(
      `UPDATE outbox
       SET attempts = $2, last_error = $3, failed_at = CASE WHEN $4::boolean THEN now() END
       WHERE id = $1`,
      [row.id, attempts, String(error), givingUp],
    );
    if (givingUp) {
      rowLog.error({ attempts, err: error }, "outbox event failed too many times and is marked as failed");
    } else {
      rowLog.warn({ attempts, err: error }, "could not publish outbox event, will try again on the next poll");
    }
  }
}

async function publishBatch(db: Pool, producer: Producer, logger: Logger): Promise<number> {
  const transaction = await db.connect();
  try {
    await transaction.query("BEGIN");
    const { rows } = await transaction.query<OutboxRow>(
      `SELECT id, event_id, topic, message_key, event_type, payload, correlation_id, attempts
       FROM outbox
       WHERE sent_at IS NULL AND failed_at IS NULL
       ORDER BY id
       LIMIT $1
       FOR UPDATE SKIP LOCKED`,
      [batchSize],
    );

    for (const row of rows) {
      await publishRow(transaction, producer, logger, row);
    }

    await transaction.query("COMMIT");
    return rows.length;
  } catch (error) {
    await transaction.query("ROLLBACK");
    throw error;
  } finally {
    transaction.release();
  }
}

export async function runOutboxRelay(db: Pool, producer: Producer, logger: Logger, stopSignal: AbortSignal): Promise<void> {
  while (!stopSignal.aborted) {
    try {
      const pickedCount = await publishBatch(db, producer, logger);
      if (pickedCount === batchSize) continue;
    } catch (error) {
      logger.warn({ err: error }, "outbox relay could not read the outbox, trying again on the next poll");
    }
    await sleep(pollIntervalMs);
  }
}

import { Kafka } from "kafkajs";
import { Pool, PoolClient } from "pg";
import { Logger } from "pino";
import { OrderPlaced } from "../../contracts/orders";

async function handleOnce(db: Pool, eventId: string, handle: (transaction: PoolClient) => Promise<void>): Promise<boolean> {
  const transaction = await db.connect();
  try {
    await transaction.query("BEGIN");
    const firstDelivery = await transaction.query(
      "INSERT INTO processed_events (event_id) VALUES ($1) ON CONFLICT DO NOTHING",
      [eventId],
    );
    if (firstDelivery.rowCount === 0) {
      await transaction.query("ROLLBACK");
      return false;
    }
    await handle(transaction);
    await transaction.query("COMMIT");
    return true;
  } catch (error) {
    await transaction.query("ROLLBACK");
    throw error;
  } finally {
    transaction.release();
  }
}

async function reserveStock(transaction: PoolClient, items: OrderPlaced["items"]): Promise<boolean> {
  await transaction.query("SAVEPOINT reserve");
  for (const item of items) {
    const updated = await transaction.query(
      "UPDATE stock SET reserved = reserved + $2 WHERE product_id = $1 AND on_hand - reserved >= $2",
      [item.productId, item.quantity],
    );
    if (updated.rowCount === 0) {
      await transaction.query("ROLLBACK TO SAVEPOINT reserve");
      return false;
    }
  }
  return true;
}

export async function startOrderPlacedConsumer(kafka: Kafka, db: Pool, logger: Logger): Promise<void> {
  const consumer = kafka.consumer({ groupId: "inventory-service" });
  await consumer.connect();
  await consumer.subscribe({ topic: "orders" });

  await consumer.run({
    eachMessage: async ({ message }) => {
      const event: OrderPlaced = JSON.parse(message.value!.toString());
      const correlationId = message.headers?.["correlation-id"]?.toString() ?? "missing";

      const handled = await handleOnce(db, event.eventId, async (transaction) => {
        const reserved = await reserveStock(transaction, event.items);
        const reply = reserved
          ? { eventId: `stock-reserved-${event.eventId}`, type: "StockReserved", orderId: event.orderId, total: event.total, paymentMethodId: event.paymentMethodId }
          : { eventId: `stock-unavailable-${event.eventId}`, type: "StockUnavailable", orderId: event.orderId };

        await transaction.query(
          `INSERT INTO outbox (event_id, topic, message_key, event_type, payload, correlation_id)
           VALUES ($1, 'inventory', $2, $3, $4, $5)`,
          [reply.eventId, event.orderId, reply.type, JSON.stringify(reply), correlationId],
        );
      });

      logger.info(
        { correlationId, eventId: event.eventId, eventType: event.type },
        handled ? "reserved stock and saved reply to outbox" : "skipped duplicate event",
      );
    },
  });
}

using System.Text.Json;
using Dapper;
using Npgsql;
using Shop.Contracts;

namespace OrderService;

public record PlaceOrderRequest(string CustomerEmail, List<OrderItem> Items, decimal Total, string PaymentMethodId);

public class PlaceOrderHandler(NpgsqlDataSource db, ILogger<PlaceOrderHandler> logger)
{
    public async Task<Guid> HandleAsync(PlaceOrderRequest request, string correlationId)
    {
        var orderId = Guid.NewGuid();
        var orderPlaced = new OrderPlaced(
            Guid.NewGuid().ToString(), DateTimeOffset.UtcNow, orderId,
            request.CustomerEmail, request.Items, request.Total, request.PaymentMethodId);

        await using var connection = await db.OpenConnectionAsync();
        await using var transaction = await connection.BeginTransactionAsync();

        await connection.ExecuteAsync(
            "INSERT INTO orders (id, customer_email, total, status) VALUES (@orderId, @CustomerEmail, @Total, 'placed')",
            new { orderId, request.CustomerEmail, request.Total }, transaction);

        await connection.ExecuteAsync(
            """
            INSERT INTO outbox (event_id, topic, message_key, event_type, payload, correlation_id)
            VALUES (@EventId, 'orders', @MessageKey, @EventType, @Payload::jsonb, @CorrelationId)
            """,
            new

                orderPlaced.EventId,
                MessageKey = orderId.ToString(),
                EventType = nameof(OrderPlaced),
                Payload = JsonSerializer.Serialize(orderPlaced),
                CorrelationId = correlationId,
            },
            transaction);

        await transaction.CommitAsync();

        logger.LogInformation("Saved order {OrderId} and outbox event {EventId}, correlation {CorrelationId}",
            orderId, orderPlaced.EventId, correlationId);

Relaysrc/OrderService/OutboxRelay.csFOR UPDATE SKIP LOCKED locks the rows it picks, so a second relay copy picks other rows instead of waiting. Each row is published on its own: a failure only adds to that row's attempts, and after 5 the row is marked as failed so it stops blocking the rest. If the relay stops mid-batch, the whole batch is waiting again and is published again.
using System.Text;
using Confluent.Kafka;
using Dapper;
using Npgsql;

namespace OrderService;

public class OutboxRelay(NpgsqlDataSource db, IProducer<string, string> producer, ILogger<OutboxRelay> logger) : BackgroundService
{
    private const int BatchSize = 100;
    private const int MaxAttempts = 5;
    private static readonly TimeSpan PollInterval = TimeSpan.FromSeconds(1);

    private record OutboxRow(long Id, string EventId, string Topic, string MessageKey, string EventType, string Payload, string CorrelationId, int Attempts);

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            try
            {
                var pickedCount = await PublishBatchAsync(stoppingToken);
                if (pickedCount == BatchSize) continue;
            }
            catch (Exception error) when (error is not OperationCanceledException)
            {
                logger.LogWarning(error, "Outbox relay could not read the outbox, trying again on the next poll");
            }

            await Task.Delay(PollInterval, stoppingToken);
        }
    }

    private async Task<int> PublishBatchAsync(CancellationToken stoppingToken)
    {
        await using var connection = await db.OpenConnectionAsync(stoppingToken);
        await using var transaction = await connection.BeginTransactionAsync(stoppingToken);

        var rows = (await connection.QueryAsync<OutboxRow>(
            """
            SELECT id, event_id AS EventId, topic, message_key AS MessageKey, event_type AS EventType,
                   payload::text AS Payload, correlation_id AS CorrelationId, attempts
            FROM outbox
            WHERE sent_at IS NULL AND failed_at IS NULL
            ORDER BY id
            LIMIT @BatchSize
            FOR UPDATE SKIP LOCKED
            """,
            new { BatchSize }, transaction)).ToList();

        foreach (var row in rows)
            await PublishRowAsync(connection, transaction, row, stoppingToken);

        await transaction.CommitAsync(stoppingToken);
        return rows.Count;
    }

    private async Task PublishRowAsync(NpgsqlConnection connection, NpgsqlTransaction transaction, OutboxRow row, CancellationToken stoppingToken)
    {
        try
        {
            var stored = await producer.ProduceAsync(row.Topic, new Message<string, string>
            {
                Key = row.MessageKey,
                Value = row.Payload,
                Headers = new Headers
                {
                    { "correlation-id", Encoding.UTF8.GetBytes(row.CorrelationId) },
                    { "causation-id", Encoding.UTF8.GetBytes(row.CorrelationId) },
                },
            }, stoppingToken);

            await connection.ExecuteAsync("UPDATE outbox SET sent_at = now() WHERE id = @Id", new { row.Id }, transaction);
            logger.LogInformation(
                "Published {EventType} {EventId} to {Topic} partition {Partition} offset {Offset}, correlation {CorrelationId}",
                row.EventType, row.EventId, stored.Topic, stored.Partition.Value, stored.Offset.Value, row.CorrelationId);
        }
        catch (ProduceException<string, string> error)
        {
            var attempts = row.Attempts + 1;
            var givingUp = attempts >= MaxAttempts;
            await connection.ExecuteAsync(
                """
                UPDATE outbox
                SET attempts = @attempts, last_error = @LastError, failed_at = CASE WHEN @givingUp THEN now() END
                WHERE id = @Id
                """,
                new { row.Id, attempts, LastError = error.Error.Reason, givingUp }, transaction);

            if (givingUp)
                logger.LogError(error, "Outbox event {EventId} failed {Attempts} times and is marked as failed, correlation {CorrelationId}",
                    row.EventId, attempts, row.CorrelationId);
            else
                logger.LogWarning(error, "Could not publish outbox event {EventId}, attempt {Attempts}, correlation {CorrelationId}",
                    row.EventId, attempts, row.CorrelationId);
        }
    }
}

using System.Text;
using System.Text.Json;
using Confluent.Kafka;
using Dapper;
using Npgsql;
using Shop.Contracts;

namespace InventoryService;

public class OrderPlacedConsumer(
    IConsumer<string, string> consumer,
    NpgsqlDataSource db,
    ILogger<OrderPlacedConsumer> logger) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        await Task.Yield();
        consumer.Subscribe("orders");

        while (!stoppingToken.IsCancellationRequested)
        {
            var result = consumer.Consume(stoppingToken);
            var orderPlaced = JsonSerializer.Deserialize<OrderPlaced>(result.Message.Value)!;
            var correlationId = result.Message.Headers.TryGetLastBytes("correlation-id", out var bytes)
                ? Encoding.UTF8.GetString(bytes)
                : "missing";

            var handled = await HandleOnceAsync(orderPlaced, correlationId);
            logger.LogInformation("{Outcome} for {EventType} {EventId}, correlation {CorrelationId}",
                handled ? "Reserved stock and saved reply to outbox" : "Skipped duplicate event",
                nameof(OrderPlaced), orderPlaced.EventId, correlationId);

            consumer.Commit(result);
        }
    }

    private async Task<bool> HandleOnceAsync(OrderPlaced orderPlaced, string correlationId)
    {
        await using var connection = await db.OpenConnectionAsync();
        await using var transaction = await connection.BeginTransactionAsync();

        var firstDelivery = await connection.ExecuteAsync(
            "INSERT INTO processed_events (event_id) VALUES (@EventId) ON CONFLICT DO NOTHING",
            new { orderPlaced.EventId }, transaction);
        if (firstDelivery == 0) return false;

        await transaction.SaveAsync("reserve");
        var reserved = await ReserveStockAsync(connection, transaction, orderPlaced.Items);
        if (!reserved) await transaction.RollbackAsync("reserve");

        object reply = reserved
            ? new StockReserved($"stock-reserved-{orderPlaced.EventId}", DateTimeOffset.UtcNow, orderPlaced.OrderId, orderPlaced.Total, orderPlaced.PaymentMethodId)
            : new StockUnavailable($"stock-unavailable-{orderPlaced.EventId}", DateTimeOffset.UtcNow, orderPlaced.OrderId);
        var replyEventId = reserved ? $"stock-reserved-{orderPlaced.EventId}" : $"stock-unavailable-{orderPlaced.EventId}";

        await connection.ExecuteAsync(
            """
            INSERT INTO outbox (event_id, topic, message_key, event_type, payload, correlation_id)
            VALUES (@EventId, 'inventory', @MessageKey, @EventType, @Payload::jsonb, @CorrelationId)
            """,
            new
            {
                EventId = replyEventId,
                MessageKey = orderPlaced.OrderId.ToString(),
                EventType = reply.GetType().Name,
                Payload = JsonSerializer.Serialize(reply, reply.GetType()),
                CorrelationId = correlationId,
            },
            transaction);

        await transaction.CommitAsync();
        return true;
    }

    private static async Task<bool> ReserveStockAsync(NpgsqlConnection connection, NpgsqlTransaction transaction, List<OrderItem> items)
    {
        foreach (var item in items)
        {
            var updated = await connection.ExecuteAsync(
                "UPDATE stock SET reserved = reserved + @Quantity WHERE product_id = @ProductId AND on_hand - reserved >= @Quantity",
                item, transaction);
            if (updated == 0) return false;
        }
        return true;
    }
