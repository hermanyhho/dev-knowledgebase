Architecture / Messaging and events

Saga

Also called the saga pattern. Described by Hector Garcia-Molina and Kenneth Salem in 1987, for long-running database transactions.

What it is

A way to run one business action across several services when no single database transaction can cover them all. Placing an order needs stock from Inventory, a charge from Payment and a pickup from Shipping, and each has its own database.

A saga splits the action into steps. Each step is a local transaction in one service. If a later step fails, the saga runs compensating actions for the steps that already succeeded, in reverse order: refund the payment, then release the stock.

There are two ways to run a saga. In choreography, each service reacts to the others' events, as on the event-driven architecture page. In orchestration, one orchestrator sends a command to each service and saves where the saga is after every reply. This page shows orchestration. Every command and reply is sent through an outbox.

TermMeaningIn the example
SagaOne business action made of steps in several services, each with an undo step.Order saga
Local transactionOne step, saved in one service's own database.Inventory reserves stock
Compensating actionA new action that cancels the effect of an earlier step. It does not erase the earlier step.RefundPayment, ReleaseStock
OrchestratorThe component that sends each command, waits for the reply and decides the next step.Order saga in the order service
CommandA message that asks one service to do something. It has one receiver.ChargePayment
ReplyThe message a service sends back with the result of a command.PaymentCharged, PaymentDeclined
Saga stateA saved record of which step each saga is at.order_sagas table
Main rule: every step that can succeed needs a compensating action, and the orchestrator saves its state in the same transaction as the next command.

Rules for compensating actions

RuleWhy
Safe to run twiceA retry or a duplicate message can send RefundPayment twice. The refund uses the saga ID as an idempotency key, so the card is refunded once.
A new action, not an eraseThe customer sees both the charge and the refund on their bank statement. Other services may already have acted on the first step.
Steps that cannot be undone come lastA sent email cannot be taken back, so the confirmation email is sent only when the saga is completed.
Others can see half-done workWhile the saga runs, reserved stock is already gone for other customers. The order shows as "pending" until the saga ends.
Compensations can fail tooThey are retried like any step. If one keeps failing, a person must fix it, so it raises an alert.

Logging and monitoring

The saga ID is also the correlation ID, so every log line from every service for one order shares it. The state table is the first place to look when an order is stuck.

Diagram

Example flow:

Pick a flow and press Play to follow it through the diagram, step by step.

  1. The order service saves the order as "pending" and starts a saga in the same transaction. The saga's first state, AwaitingStock, is saved in order_sagas. The client gets 202 Accepted.
  2. The orchestrator sends ReserveStock to Inventory.
  3. Inventory replies StockReserved. The orchestrator saves the state AwaitingPayment and, in the same transaction, queues ChargePayment.
  4. Payment charges the card and replies PaymentCharged. The state becomes AwaitingPickup.
  5. Shipping books a pickup with the carrier and replies PickupBooked.
  6. The orchestrator saves the state Completed and marks the order as confirmed. Only now is the confirmation email sent, because an email cannot be undone.
  1. Stock is already reserved. Payment tries to charge the card, the bank declines it, and Payment replies PaymentDeclined.
  2. The orchestrator saves the state ReleasingStock. It now runs the compensating actions for the steps that succeeded.
  3. It sends ReleaseStock. Inventory releases the reserved stock and replies StockReleased.
  4. The orchestrator saves the state Cancelled with the reason "card declined", and marks the order as cancelled.
  1. Stock is reserved and the card is charged. Shipping cannot book a pickup, even after its retries, and replies PickupFailed.
  2. The orchestrator undoes the most recent successful step first. It sends RefundPayment, and Payment replies PaymentRefunded.
  3. Then it sends ReleaseStock, and Inventory replies StockReleased.
  4. The saga ends as Cancelled. Each state was saved on the way, so a crash in the middle continues where it stopped.
  1. The orchestrator saves the state AwaitingPayment and queues ChargePayment. Then its process stops.
  2. Payment charges the card and replies PaymentCharged. The reply waits in the broker, because no orchestrator is running.
  3. A new orchestrator copy starts and reads the reply. It loads saga 42 from order_sagas, sees AwaitingPayment, and continues with BookPickup. Nothing was kept only in memory.
  4. If a reply never arrives, a check finds sagas with no change for 2 minutes and sends the command again. That is safe because every service handles each command only once.

Problems it solves

  • No transaction across servicesEach service saves its own step. Compensations bring the whole action back to a consistent end when a step fails.
  • Half-finished orders after a failureEvery saga ends in a known state, Completed or Cancelled, with the reason saved.
  • Lost progress after a crashThe state is saved after every reply, so a new orchestrator copy continues where the old one stopped.
  • A flow spread across many servicesWith orchestration, the whole flow is written in one state machine you can read top to bottom.
  • Finding stuck ordersA query on the saga state table lists every saga that has not moved for a while.

Problems it introduces

  • Every step needs an undoYou write and test a compensating action for each step, and each must be safe to run twice.
  • Others see half-done workUnlike a database transaction, a saga does not hide its steps. Reserved stock is unavailable to others before the saga ends.
  • Some steps cannot be undoneEmails, shipped parcels and bank transfers need careful ordering, or a human to fix them.
  • Many messages for one actionA successful order takes 6 messages. A cancelled one takes up to 10. Each one can be delayed or duplicated.
  • The orchestrator knows every serviceAdding or changing a step means changing the orchestrator, and it must handle every reply in every state.
  • Harder to testEach combination of failure and state needs a test, including duplicate and late replies.

  saga_id            UUID PRIMARY KEY,
  order_id           UUID NOT NULL UNIQUE,
  state              TEXT NOT NULL,
  amount             NUMERIC(10, 2) NOT NULL,
  payment_method_id  TEXT NOT NULL,
  items              JSONB NOT NULL,
  failure_reason     TEXT,
  updated_at         TIMESTAMPTZ NOT NULL DEFAULT now()

CREATE INDEX order_sagas_unfinished ON order_sagas (updated_at)
  WHERE state NOT IN ('Completed', 'Cancelled');

FROM order_sagas

Starts the sagaorder-service/src/placeOrder.tsOne transaction saves three things: the pending order, the saga's first state, and the first command in the outbox. The client gets 202 Accepted, because the order is not confirmed yet.
import { randomUUID } from "node:crypto";
import { Pool } from "pg";
import { Logger } from "pino";
import { saveCommandToOutbox } from "./orderSaga";

export type PlaceOrderRequest = {
  items: { productId: string; quantity: number }[];
  total: number;
  paymentMethodId: string;
};

export async function placeOrder(db: Pool, logger: Logger, request: PlaceOrderRequest): Promise<string> {
  const orderId = randomUUID();
  const sagaId = randomUUID();

  const transaction = await db.connect();
  try {
    await transaction.query("BEGIN");
    await transaction.query(
      "INSERT INTO orders (id, total, status) VALUES ($1, $2, 'pending')",
      [orderId, request.total],
    );
    await transaction.query(
      `INSERT INTO order_sagas (saga_id, order_id, state, amount, payment_method_id, items)
       VALUES ($1, $2, 'AwaitingStock', $3, $4, $5)`,
      [sagaId, orderId, request.total, request.paymentMethodId, JSON.stringify(request.items)],
    );
    await saveCommandToOutbox(transaction, { type: "ReserveStock", sagaId, orderId, items: request.items });
    await transaction.query("COMMIT");
  } catch (error) {
    await transaction.query("ROLLBACK");
    throw error;
  } finally {
    transaction.release();
  }

  logger.info({ correlationId: sagaId, sagaId, orderId, toState: "AwaitingStock" }, "started order saga");
  return orderId;
}
Orchestratororder-service/src/orderSaga.tsThe transitions table is the whole saga: for each state and reply, the next state and the command to send. FOR UPDATE locks the saga row, so two orchestrator copies cannot handle replies for the same saga at once. A reply with no matching transition, such as a duplicate, is logged and ignored.
import { Kafka } from "kafkajs";
import { Pool, PoolClient } from "pg";
import { Logger } from "pino";
import { SagaCommand, SagaReply } from "../../contracts/orderSaga";

type SagaState =
  | "AwaitingStock" | "AwaitingPayment" | "AwaitingPickup"
  | "RefundingPayment" | "ReleasingStock" | "Completed" | "Cancelled";

type Transition = { nextState: SagaState; command?: SagaCommand["type"] };

const transitions: Record<string, Transition> = {
  "AwaitingStock:StockReserved": { nextState: "AwaitingPayment", command: "ChargePayment" },
  "AwaitingStock:StockUnavailable": { nextState: "Cancelled" },
  "AwaitingPayment:PaymentCharged": { nextState: "AwaitingPickup", command: "BookPickup" },
  "AwaitingPayment:PaymentDeclined": { nextState: "ReleasingStock", command: "ReleaseStock" },
  "AwaitingPickup:PickupBooked": { nextState: "Completed" },
  "AwaitingPickup:PickupFailed": { nextState: "RefundingPayment", command: "RefundPayment" },
  "RefundingPayment:PaymentRefunded": { nextState: "ReleasingStock", command: "ReleaseStock" },
  "ReleasingStock:StockReleased": { nextState: "Cancelled" },
};

const commandTopics: Record<SagaCommand["type"], string> = {
  ReserveStock: "inventory-commands",
  ReleaseStock: "inventory-commands",
  ChargePayment: "payment-commands",
  RefundPayment: "payment-commands",
  BookPickup: "shipping-commands",
};

type SagaRow = {
  saga_id: string;
  order_id: string;
  state: SagaState;
  amount: string;
  payment_method_id: string;
  items: { productId: string; quantity: number }[];
};

export async function saveCommandToOutbox(transaction: PoolClient, command: SagaCommand): Promise<void> {
  await transaction.query(
    `INSERT INTO outbox (event_id, topic, message_key, event_type, payload, correlation_id)
     VALUES ($1, $2, $3, $4, $5, $6)`,
    [`${command.sagaId}-${command.type}`, commandTopics[command.type], command.orderId, command.type, JSON.stringify(command), command.sagaId],
  );
}

function buildCommand(type: SagaCommand["type"], saga: SagaRow): SagaCommand {
  const ids = { sagaId: saga.saga_id, orderId: saga.order_id };
  switch (type) {
    case "ReserveStock": return { type, ...ids, items: saga.items };
    case "ChargePayment": return { type, ...ids, amount: Number(saga.amount), paymentMethodId: saga.payment_method_id };
    case "ReleaseStock": return { type, ...ids };
    case "RefundPayment": return { type, ...ids };
    case "BookPickup": return { type, ...ids };
  }
}

async function handleReply(db: Pool, logger: Logger, reply: SagaReply): Promise<void> {
  const transaction = await db.connect();
  try {
    await transaction.query("BEGIN");
    const { rows: [saga] } = await transaction.query<SagaRow>(
      "SELECT * FROM order_sagas WHERE saga_id = $1 FOR UPDATE",
      [reply.sagaId],
    );
    const sagaLog = logger.child({ correlationId: saga.saga_id, sagaId: saga.saga_id, orderId: saga.order_id });
    const transition = transitions[`${saga.state}:${reply.type}`];

    if (!transition) {
      await transaction.query("ROLLBACK");
      sagaLog.info({ state: saga.state, reply: reply.type }, "ignored a reply that does not match the current state");
      return;
    }

    await transaction.query(
      `UPDATE order_sagas
       SET state = $2, failure_reason = COALESCE($3, failure_reason), updated_at = now()
       WHERE saga_id = $1`,
      [saga.saga_id, transition.nextState, "reason" in reply ? reply.reason : null],
    );
    if (transition.command) {
      await saveCommandToOutbox(transaction, buildCommand(transition.command, saga));
    }
    if (transition.nextState === "Completed" || transition.nextState === "Cancelled") {
      const orderStatus = transition.nextState === "Completed" ? "confirmed" : "cancelled";
      await transaction.query("UPDATE orders SET status = $2 WHERE id = $1", [saga.order_id, orderStatus]);
    }
    await transaction.query("COMMIT");

    sagaLog.info(
      { fromState: saga.state, toState: transition.nextState, reply: reply.type, command: transition.command },
      "saga moved to a new state",
    );
  } catch (error) {
    await transaction.query("ROLLBACK");
    throw error;
  } finally {
    transaction.release();
  }
}

export async function startSagaReplyConsumer(kafka: Kafka, db: Pool, logger: Logger): Promise<void> {
  const consumer = kafka.consumer({ groupId: "order-saga" });
  await consumer.connect();
  await consumer.subscribe({ topic: "order-saga-replies" });
  await consumer.run({
    eachMessage: async ({ message }) => handleReply(db, logger, JSON.parse(message.value!.toString())),
  });
}
Serviceinventory-service/src/inventoryCommands.tsEach reservation is saved as a row, so ReleaseStock knows what to give back. Releasing is safe to run twice: it only touches reservations not released yet. The consumer around this function uses the inbox and writes the reply to the outbox for order-saga-replies, as on the outbox page.
import { PoolClient } from "pg";
import { SagaCommand, SagaReply } from "../../contracts/orderSaga";

type ReserveStock = Extract<SagaCommand, { type: "ReserveStock" }>;

async function reserveStock(transaction: PoolClient, command: ReserveStock): Promise<boolean> {
  await transaction.query("SAVEPOINT reserve");
  for (const item of command.items) {
    const updated = await transaction.query(
      "UPDATE stock SET reserved = reserved + $2 WHERE product_id = $1 AND on_hand - reserved >= $2",
      [item.productId, item.quantity],
    );
    if (updated.rowCount === 0) {
      await transaction.query("ROLLBACK TO SAVEPOINT reserve");
      return false;
    }
    await transaction.query(
      "INSERT INTO reservations (order_id, product_id, quantity) VALUES ($1, $2, $3)",
      [command.orderId, item.productId, item.quantity],
    );
  }
  return true;
}

export async function handleInventoryCommand(transaction: PoolClient, command: SagaCommand): Promise<SagaReply> {
  switch (command.type) {
    case "ReserveStock": {
      const reserved = await reserveStock(transaction, command);
      return { type: reserved ? "StockReserved" : "StockUnavailable", sagaId: command.sagaId };
    }
    case "ReleaseStock": {
      await transaction.query(
        `WITH released AS (
           UPDATE reservations SET released_at = now()
           WHERE order_id = $1 AND released_at IS NULL
           RETURNING product_id, quantity
         )
         UPDATE stock SET reserved = stock.reserved - released.quantity
         FROM released
         WHERE stock.product_id = released.product_id`,
        [command.orderId],
      );
      return { type: "StockReleased", sagaId: command.sagaId };
    }
    default:
      throw new Error(`Inventory does not handle ${command.type}.`);
  }
}
Servicepayment-service/src/paymentCommands.tsBoth the charge and the refund pass an idempotency key built from the saga ID, so Stripe acts only once even if the command arrives twice. A declined card is a normal reply, not an error.
import { PoolClient } from "pg";
import Stripe from "stripe";
import { SagaCommand, SagaReply } from "../../contracts/orderSaga";

export async function handlePaymentCommand(transaction: PoolClient, stripe: Stripe, command: SagaCommand): Promise<SagaReply> {
  switch (command.type) {
    case "ChargePayment":
      try {
        const paymentIntent = await stripe.paymentIntents.create(
          { amount: Math.round(command.amount * 100), currency: "eur", payment_method: command.paymentMethodId, confirm: true },
          { idempotencyKey: `${command.sagaId}-charge` },
        );
        await transaction.query(
          "INSERT INTO payments (order_id, provider_id, amount) VALUES ($1, $2, $3) ON CONFLICT (order_id) DO NOTHING",
          [command.orderId, paymentIntent.id, command.amount],
        );
        return { type: "PaymentCharged", sagaId: command.sagaId };
      } catch (error) {
        if (error instanceof Stripe.errors.StripeCardError) {
          return { type: "PaymentDeclined", sagaId: command.sagaId, reason: error.message };
        }
        throw error;
      }

    case "RefundPayment": {
      const { rows: [payment] } = await transaction.query(
        "SELECT provider_id FROM payments WHERE order_id = $1",
        [command.orderId],
      );
      await stripe.refunds.create(
        { payment_intent: payment.provider_id },
        { idempotencyKey: `${command.sagaId}-refund` },
      );
      await transaction.query("UPDATE payments SET refunded_at = now() WHERE order_id = $1", [command.orderId]);
      return { type: "PaymentRefunded", sagaId: command.sagaId };
    }

    default:
      throw new Error(`Payment does not handle ${command.type}.`);
  }
}
Serviceshipping-service/src/shippingCommands.tsThe consumer around this function retries a few times first, as on the event-driven page. When it gives up, it replies PickupFailed instead of throwing, so the saga can run its compensations.
import { SagaCommand, SagaReply } from "../../contracts/orderSaga";

export type CarrierClient = { bookPickup(orderId: string): Promise<void> };

export async function handleShippingCommand(carrier: CarrierClient, command: SagaCommand): Promise<SagaReply> {
  if (command.type !== "BookPickup") {
    throw new Error(`Shipping does not handle ${command.type}.`);
  }

  try {
    await carrier.bookPickup(command.orderId);
    return { type: "PickupBooked", sagaId: command.sagaId };
  } catch (error) {
    return { type: "PickupFailed", sagaId: command.sagaId, reason: String(error) };
  }
}

using MassTransit;
using Shop.Contracts;

namespace OrderService;

public record PlaceOrderRequest(List<OrderItem> Items, decimal Total, string PaymentMethodId);

public class PlaceOrderHandler(ShopDbContext db, IPublishEndpoint publishEndpoint, ILogger<PlaceOrderHandler> logger)
{
    public async Task<Guid> HandleAsync(PlaceOrderRequest request)
    {
        var order = new Order { Id = Guid.NewGuid(), Total = request.Total, Status = "pending" };

        db.Orders.Add(order);

    }

Orchestratorsrc/OrderService/OrderSaga.csA MassTransit state machine. Each During block lists the replies a state accepts, the command to send and the next state. MassTransit saves OrderSagaState after each message, together with the outgoing commands through its outbox. A reply that does not fit the current state is not handled.
using MassTransit;
using Shop.Contracts;

namespace OrderService;

public class OrderSagaState : SagaStateMachineInstance
{
    public Guid CorrelationId { get; set; }
    public string CurrentState { get; set; } = "";
    public Guid OrderId { get; set; }
    public decimal Amount { get; set; }
    public string PaymentMethodId { get; set; } = "";
    public List<OrderItem> Items { get; set; } = [];
    public string? FailureReason { get; set; }
}

public class OrderSaga : MassTransitStateMachine<OrderSagaState>
{
    private static readonly Uri InventoryCommands = new("queue:inventory-commands");
    private static readonly Uri PaymentCommands = new("queue:payment-commands");
    private static readonly Uri ShippingCommands = new("queue:shipping-commands");

    public State AwaitingStock { get; private set; } = null!;
    public State AwaitingPayment { get; private set; } = null!;
    public State AwaitingPickup { get; private set; } = null!;
    public State RefundingPayment { get; private set; } = null!;
    public State ReleasingStock { get; private set; } = null!;
    public State Completed { get; private set; } = null!;
    public State Cancelled { get; private set; } = null!;

    public Event<OrderSubmitted> OrderSubmitted { get; private set; } = null!;
    public Event<StockReserved> StockReserved { get; private set; } = null!;
    public Event<StockUnavailable> StockUnavailable { get; private set; } = null!;
    public Event<StockReleased> StockReleased { get; private set; } = null!;
    public Event<PaymentCharged> PaymentCharged { get; private set; } = null!;
    public Event<PaymentDeclined> PaymentDeclined { get; private set; } = null!;
    public Event<PaymentRefunded> PaymentRefunded { get; private set; } = null!;
    public Event<PickupBooked> PickupBooked { get; private set; } = null!;
    public Event<PickupFailed> PickupFailed { get; private set; } = null!;

    public OrderSaga(ILogger<OrderSaga> logger)
    {
        InstanceState(saga => saga.CurrentState);

        Event(() => OrderSubmitted, configure => configure.CorrelateById(context => context.Message.SagaId));
        Event(() => StockReserved, configure => configure.CorrelateById(context => context.Message.SagaId));
        Event(() => StockUnavailable, configure => configure.CorrelateById(context => context.Message.SagaId));
        Event(() => StockReleased, configure => configure.CorrelateById(context => context.Message.SagaId));
        Event(() => PaymentCharged, configure => configure.CorrelateById(context => context.Message.SagaId));
        Event(() => PaymentDeclined, configure => configure.CorrelateById(context => context.Message.SagaId));
        Event(() => PaymentRefunded, configure => configure.CorrelateById(context => context.Message.SagaId));
        Event(() => PickupBooked, configure => configure.CorrelateById(context => context.Message.SagaId));
        Event(() => PickupFailed, configure => configure.CorrelateById(context => context.Message.SagaId));

        Initially(
            When(OrderSubmitted)
                .Then(context =>
                {
                    context.Saga.OrderId = context.Message.OrderId;
                    context.Saga.Amount = context.Message.Amount;
                    context.Saga.PaymentMethodId = context.Message.PaymentMethodId;
                    context.Saga.Items = context.Message.Items;
                })
                .Send(InventoryCommands, context => new ReserveStock(context.Saga.CorrelationId, context.Saga.OrderId, context.Saga.Items))
                .TransitionTo(AwaitingStock));

        During(AwaitingStock,
            When(StockReserved)
                .Send(PaymentCommands, context => new ChargePayment(context.Saga.CorrelationId, context.Saga.OrderId, context.Saga.Amount, context.Saga.PaymentMethodId))
                .TransitionTo(AwaitingPayment),
            When(StockUnavailable)
                .Then(context => context.Saga.FailureReason = "out of stock")
                .Publish(context => new OrderCancelled(context.Saga.OrderId, "out of stock"))
                .TransitionTo(Cancelled));

        During(AwaitingPayment,
            When(PaymentCharged)
                .Send(ShippingCommands, context => new BookPickup(context.Saga.CorrelationId, context.Saga.OrderId))
                .TransitionTo(AwaitingPickup),
            When(PaymentDeclined)
                .Then(context => context.Saga.FailureReason = context.Message.Reason)
                .Send(InventoryCommands, context => new ReleaseStock(context.Saga.CorrelationId, context.Saga.OrderId))
                .TransitionTo(ReleasingStock));

        During(AwaitingPickup,
            When(PickupBooked)
                .Publish(context => new OrderConfirmed(context.Saga.OrderId))
                .TransitionTo(Completed),
            When(PickupFailed)
                .Then(context => context.Saga.FailureReason = context.Message.Reason)
                .Send(PaymentCommands, context => new RefundPayment(context.Saga.CorrelationId, context.Saga.OrderId))
                .TransitionTo(RefundingPayment));

        During(RefundingPayment,
            When(PaymentRefunded)
                .Send(InventoryCommands, context => new ReleaseStock(context.Saga.CorrelationId, context.Saga.OrderId))
                .TransitionTo(ReleasingStock));

        During(ReleasingStock,
            When(StockReleased)
                .Publish(context => new OrderCancelled(context.Saga.OrderId, context.Saga.FailureReason ?? "unknown"))
                .TransitionTo(Cancelled));

        BeforeEnterAny(binder => binder.Then(context =>
            logger.LogInformation("Saga {SagaId} for order {OrderId} moved to {State}, correlation {CorrelationId}",
                context.Saga.CorrelationId, context.Saga.OrderId, context.Message.Name, context.Saga.CorrelationId)));
    }
}
Servicesrc/InventoryService/InventoryCommandsConsumer.csEach reservation is saved as a row, so ReleaseStock knows what to give back. Releasing is safe to run twice: it only touches reservations not released yet. MassTransit's inbox and outbox, turned on in the service setup, skip duplicate commands and keep the reply from being lost.
using Dapper;
using MassTransit;
using Npgsql;
using Shop.Contracts;

namespace InventoryService;

public class InventoryCommandsConsumer(NpgsqlDataSource db) : IConsumer<ReserveStock>, IConsumer<ReleaseStock>
{
    public async Task Consume(ConsumeContext<ReserveStock> context)
    {
        var command = context.Message;
        await using var connection = await db.OpenConnectionAsync();
        await using var transaction = await connection.BeginTransactionAsync();

        var reserved = await ReserveStockAsync(connection, transaction, command);
        await transaction.CommitAsync();

        if (reserved)
            await context.Publish(new StockReserved(command.SagaId));
        else
            await context.Publish(new StockUnavailable(command.SagaId));
    }

    public async Task Consume(ConsumeContext<ReleaseStock> context)
    {
        await using var connection = await db.OpenConnectionAsync();
        await connection.ExecuteAsync(
            """
            WITH released AS (
              UPDATE reservations SET released_at = now()
              WHERE order_id = @OrderId AND released_at IS NULL
              RETURNING product_id, quantity
            )
            UPDATE stock SET reserved = stock.reserved - released.quantity
            FROM released
            WHERE stock.product_id = released.product_id
            """,
            new { context.Message.OrderId });

        await context.Publish(new StockReleased(context.Message.SagaId));
    }

    private static async Task<bool> ReserveStockAsync(NpgsqlConnection connection, NpgsqlTransaction transaction, ReserveStock command)
    {
        await transaction.SaveAsync("reserve");
        foreach (var item in command.Items)
        {
            var updated = await connection.ExecuteAsync(
                "UPDATE stock SET reserved = reserved + @Quantity WHERE product_id = @ProductId AND on_hand - reserved >= @Quantity",
                item, transaction);
            if (updated == 0)
            {
                await transaction.RollbackAsync("reserve");
                return false;
            }

            await connection.ExecuteAsync(
                "INSERT INTO reservations (order_id, product_id, quantity) VALUES (@OrderId, @ProductId, @Quantity)",
                new { command.OrderId, item.ProductId, item.Quantity }, transaction);
        }
        return true;
    }
}
Servicesrc/PaymentService/PaymentCommandsConsumer.csBoth the charge and the refund pass an idempotency key built from the saga ID, so Stripe acts only once even if the command arrives twice. A declined card is a normal reply, not an error.
using Dapper;
using MassTransit;
using Npgsql;
using Shop.Contracts;
using Stripe;

namespace PaymentService;

public class PaymentCommandsConsumer(
    PaymentIntentService paymentIntents,
    RefundService refunds,
    NpgsqlDataSource db) : IConsumer<ChargePayment>, IConsumer<RefundPayment>
{
    public async Task Consume(ConsumeContext<ChargePayment> context)
    {
        var command = context.Message;
        try
        {
            var paymentIntent = await paymentIntents.CreateAsync(
                new PaymentIntentCreateOptions
                {
                    Amount = (long)Math.Round(command.Amount * 100),
                    Currency = "eur",
                    PaymentMethod = command.PaymentMethodId,
                    Confirm = true,
                },
                new RequestOptions { IdempotencyKey = $"{command.SagaId}-charge" });

            await using var connection = await db.OpenConnectionAsync();
            await connection.ExecuteAsync(
                "INSERT INTO payments (order_id, provider_id, amount) VALUES (@OrderId, @ProviderId, @Amount) ON CONFLICT (order_id) DO NOTHING",
                new { command.OrderId, ProviderId = paymentIntent.Id, command.Amount });

            await context.Publish(new PaymentCharged(command.SagaId));
        }
        catch (StripeException error) when (error.StripeError?.Type == "card_error")
        {
            await context.Publish(new PaymentDeclined(command.SagaId, error.Message));
        }
    }

    public async Task Consume(ConsumeContext<RefundPayment> context)
    {
        var command = context.Message;
        await using var connection = await db.OpenConnectionAsync();
        var providerId = await connection.QuerySingleAsync<string>(
            "SELECT provider_id FROM payments WHERE order_id = @OrderId", new { command.OrderId });

        await refunds.CreateAsync(
            new RefundCreateOptions { PaymentIntent = providerId },
            new RequestOptions { IdempotencyKey = $"{command.SagaId}-refund" });

        await connection.ExecuteAsync("UPDATE payments SET refunded_at = now() WHERE order_id = @OrderId", new { command.OrderId });
        await context.Publish(new PaymentRefunded(command.SagaId));
    }
}
Servicesrc/ShippingService/BookPickupConsumer.csMassTransit's retry setting tries the carrier a few times first. When the carrier still fails, the consumer replies PickupFailed instead of throwing, so the saga can run its compensations.
using MassTransit;
using Shop.Contracts;

namespace ShippingService;

public interface ICarrierClient
{
    Task BookPickupAsync(Guid orderId);
}

public class BookPickupConsumer(ICarrierClient carrier) : IConsumer<BookPickup>
{
    public async Task Consume(ConsumeContext<BookPickup> context)
    {
        try
        {
            await carrier.BookPickupAsync(context.Message.OrderId);
            await context.Publish(new PickupBooked(context.Message.SagaId));
