React / Rendering

How React Renders

What happens between a state change and new pixels on the screen. Examples use React 19.

What it is

A React component is a function that returns a description of the screen, written in JSX. React calls the function, compares the result with the previous result, and changes only the parts of the page that differ.

This happens in two phases. In the render phase, React calls your components. They must only compute and return JSX: no network calls, no changes to outside variables. In the commit phase, React applies the differences to the DOM. After the browser has painted, React runs your effects, which is where side effects belong.

Comparing the old and new result is reconciliation. React walks both trees and compares the element type and the key at each position. If both are the same, the component keeps its state. If either changed, React removes the old component and its state, and creates a new one.

Main rule: keep rendering pure: the same props and state give the same JSX, with no side effects. Give list items a stable key from the data, never the array index when items can move.

What causes a render

CauseWhat rendersNote
The component's state changesThe component and every component it returns, all the way downSetting the same value as before is skipped
The parent rendersThe child, even if its props did not changeUnless the child is wrapped in memo and its props are equal
A context value it reads changesEvery component that calls useContext for that contextA new object as the value counts as a change
Props changeOnly as a result of the parent renderingProps never change by themselves

A render does not mean the screen changes. If the new elements equal the old ones, the commit phase does nothing. Rendering many components is usually fast; it becomes a problem with large lists or slow calculations during render.

Diagram

Example flow:

Pick a flow and press Play to follow it through the diagram, step by step.

  1. The user clicks "+" on a cart row. The handler in Cart calls setQuantities. React schedules a render; the variable does not change yet.
  2. React calls Cart again, and useState returns the new quantities. Every CartRow that Cart returns is called too.
  3. The components return JSX, which is a tree of plain objects. Creating it changes nothing on screen.
  4. React compares the tree with the previous one. Same types and keys everywhere; only the quantity text and the total differ.
  5. React changes those two text nodes in the DOM. The browser paints.
  6. Effects whose dependencies changed run: first the cleanup from the last render, then the new setup.
  1. One click calls setQuantities(...) and setLastChangedItemId(itemId).
  2. React collects both updates and renders once, with both new values. This is automatic batching, in event handlers, timeouts and promises alike.
  3. One reconciliation and one commit. Measured in React 19: two updates in one click gave one render of the component.
  4. Reading quantities right after setQuantities in the handler still gives the old value. The new value arrives with the next render.
  1. A shopping list renders rows with key={index}. Each row has its own input state. The user types "2 kg" in the apples row.
  2. The user deletes apples. The new list is just bread, and it now has index 0.
  3. React sees key 0 in both trees and keeps that component and its state. The bread row now shows "2 kg", the text typed for apples. Measured in React 19.
  4. With key={item.id}, React sees that the apples key is gone, removes that row with its state, and keeps bread's own empty input.
  1. An edit form shows customer A. Its inputs keep their own state. The user picks customer B in a list.
  2. Same component at the same position: React keeps the state, so the form still shows A's values.
  3. Render it as <CustomerForm key={customer.id} />. A different key means a different component, so React creates a new one with fresh state.
  4. The old form's DOM is removed and a new one is created. This also happens, without asking, when the element type at a position changes.
  1. In development, <StrictMode> calls each component twice and keeps one result.
  2. A component that pushes to an outside array or counts renders in a module variable gives different results each time. Strict Mode makes that visible.
  3. On mount it also runs every effect as setup, cleanup, setup. An effect that subscribes without unsubscribing now has two subscriptions, and the bug shows at once.
  4. None of this happens in a production build. Measured in React 19: mount logged render, render, setup, cleanup, setup.

Problems it solves

  • Updating the page by handYou describe the result for the current state. React works out which DOM nodes to change.
  • Screens out of step with dataEvery state change produces the whole description again, so nothing is forgotten.
  • Slow DOM workOnly the differences reach the DOM, in one commit.
  • Hidden side effectsPure render and separate effects make the order of work predictable, and Strict Mode finds violations.

Problems it introduces

  • More renders than neededA state change at the top renders every component below, unless memoized.
  • State tied to positionWrong keys or a changed element type move or reset state without any error.
  • State is not updated at onceThe new value appears only in the next render, which surprises code that reads it right after setting it.
  • Development and production differStrict Mode's double calls confuse logging and counting during development.
Rendersrc/cart/CartRow.tsxA pure component: the same props always give the same JSX, and it changes nothing outside itself. An impure version would, for example, add 1 to a module-level renderCount variable while rendering. In Strict Mode that count doubles, and in production it depends on how often React happens to render.
export type CartItem = { id: string; name: string; unitPrice: number };

type CartRowProps = {
  item: CartItem;
  quantity: number;
  isLastChanged: boolean;
  onIncrease: (itemId: string) => void;
};

export function CartRow({ item, quantity, isLastChanged, onIncrease }: CartRowProps) {
  return (
    <li className={isLastChanged ? "highlight" : undefined}>
      {item.name} x {quantity} = {(item.unitPrice * quantity).toFixed(2)}
      <button onClick={() => onIncrease(item.id)}>+</button>
    </li>
  );
}
Triggersrc/cart/Cart.tsxCalling a state setter does not change quantities in this call; it asks React for a new render. The updater form current => ... uses the latest value, so two quick clicks add 2. Both setters in increase are batched into one render.
import { useState } from "react";
import { CartRow, type CartItem } from "./CartRow";

export function Cart({ items }: { items: CartItem[] }) {
  const [quantities, setQuantities] = useState<Record<string, number>>({});
  const [lastChangedItemId, setLastChangedItemId] = useState<string | null>(null);

  function increase(itemId: string) {
    setQuantities((current) => ({ ...current, [itemId]: (current[itemId] ?? 1) + 1 }));
    setLastChangedItemId(itemId);
  }

  const quantityOf = (item: CartItem) => quantities[item.id] ?? 1;
  const total = items.reduce((sum, item) => sum + item.unitPrice * quantityOf(item), 0);

  return (
    <section>
      <ul>
        {items.map((item) => (
          <CartRow
            key={item.id}
            item={item}
            quantity={quantityOf(item)}
            isLastChanged={item.id === lastChangedItemId}
            onIncrease={increase}
          />
        ))}
      </ul>
      <p>Total: {total.toFixed(2)}</p>
    </section>
  );
}
Keyssrc/shopping/ShoppingList.tsxEach row keeps the amount you type in its own state. With key={index}, deleting the first row gave the second row the first row's typed text, measured in React 19. With key={item.id}, every row keeps its own state.
import { useState } from "react";

type ShoppingItem = { id: string; name: string };

function ShoppingRow({ item, onDelete }: { item: ShoppingItem; onDelete: () => void }) {
  const [amount, setAmount] = useState("");
  return (
    <li>
      {item.name}
      <input value={amount} onChange={(event) => setAmount(event.target.value)} placeholder="amount" />
      <button onClick={onDelete}>Delete</button>
    </li>
  );
}

export function ShoppingList({ initialItems }: { initialItems: ShoppingItem[] }) {
  const [items, setItems] = useState(initialItems);
  const remove = (itemId: string) => setItems((current) => current.filter((item) => item.id !== itemId));

  return (
    <ul>
      {items.map((item) => (
        <ShoppingRow key={item.id} item={item} onDelete={() => remove(item.id)} />
      ))}
    </ul>
  );
}
Commitsrc/cart/StickyTotal.tsxDuring the commit, React sets ref.current to the DOM node. useLayoutEffect runs after the DOM changes but before the browser paints, so measuring and adjusting here does not flicker. Use it only for measuring; it delays the paint.
import { useLayoutEffect, useRef, useState } from "react";

export function StickyTotal({ total }: { total: number }) {
  const totalRef = useRef<HTMLDivElement>(null);
  const [height, setHeight] = useState(0);

  useLayoutEffect(() => {
    setHeight(totalRef.current?.getBoundingClientRect().height ?? 0);
  }, [total]);

  return (
    <>
      <div style={{ height }} />
      <div ref={totalRef} className="sticky-total">Total: {total.toFixed(2)}</div>
    </>
  );
}
Monitoringsrc/main.tsxcreateRoot takes error callbacks in React 19: onCaughtError for errors an error boundary handled, onUncaughtError for the rest. reportError is your error service's client. <Profiler> reports how long the cart took to render; only slow renders are sent.
import { Profiler, StrictMode } from "react";
import { createRoot } from "react-dom/client";
import { App } from "./App";
import { reportError, reportMetric } from "./monitoring";

const errorContext = { release: import.meta.env.VITE_RELEASE, url: location.pathname };

createRoot(document.getElementById("root")!, {
  onCaughtError: (error, info) => reportError(error, { ...errorContext, handled: true, componentStack: info.componentStack }),
  onUncaughtError: (error, info) => reportError(error, { ...errorContext, handled: false, componentStack: info.componentStack }),
}).render(
  <StrictMode>
    <Profiler
      id="cart"
      onRender={(id, phase, actualDuration) => {
        if (actualDuration > 16) reportMetric("slow_render", { id, phase, durationMs: Math.round(actualDuration) });
      }}
    >
      <App />
    </Profiler>
  </StrictMode>,
);
Effectssrc/cart/useCartAnalytics.tsAn effect for work outside React: sending an event when the cart total changes. The cleanup cancels a pending send, so a quick series of changes sends only the last one. In Strict Mode, setup, cleanup and setup run on mount, which this code handles correctly.
import { useEffect } from "react";
import { sendAnalyticsEvent } from "../analytics";

export function useCartAnalytics(cartId: string, total: number) {
  useEffect(() => {
    const timer = setTimeout(() => {
      sendAnalyticsEvent("cart_total_changed", { cartId, total });
    }, 500);

    return () => clearTimeout(timer);
  }, [cartId, total]);
}
