React / Next.js

Next.js Overview

A React framework that renders components on the server, caches their results, and handles form submissions with server functions. Examples use Next.js 16 with the App Router and Cache Components.

What it is

Plain React runs in the browser. Next.js runs React on the server too. Each folder in app/ is a route, and its page.tsx is a component that can be async and read a database directly. The browser receives finished HTML first, then the JavaScript for the parts that need to be interactive.

Four ideas cover most of it: which components run where, which parts of a page are built ahead of time, how results are cached, and how the browser sends changes back.

IdeaKey pointCommon mistake
Server and Client ComponentsComponents are Server Components by default: they run only on the server and their code never reaches the browser. "use client" at the top of a file marks components that need state, effects or click handlers.Putting "use client" high in the tree, so most code ships to the browser
Static shell and streamingAt build time Next.js renders everything it can into a static shell. Parts that need the request, such as cookies, render per request inside <Suspense> and stream in.Reading cookies() outside <Suspense>, which fails the build
CachingNothing is cached unless you say so. "use cache" in a function caches its result; cacheLife sets how long, cacheTag names it for invalidation.Expecting fetch to be cached by default, as in Next.js 14
Server Actions and ProxyA function with "use server" can be a form's action; the browser calls it with a POST. proxy.ts, formerly middleware.ts, runs before routes for redirects and headers.Checking authorization only in Proxy. Every Server Action must check it itself.
Main rule: keep components on the server unless they need interaction, cache data explicitly with "use cache", wrap request-specific parts in <Suspense>, and check authentication inside every Server Action.

Example flow:

Pick a flow and press Play to follow it through the diagram, step by step.

  1. The request passes proxy.ts, which only redirects or sets headers, then reaches the page.
  2. The page reads products through a function marked "use cache". The result was rendered at build time, so it is part of the static shell.
  3. The static shell, including a fallback for the personal part, is sent at once. The browser shows it and loads the JavaScript for Client Components only.
  4. The part inside <Suspense> reads the cookie, renders for this user, and streams into the page.
  1. The user submits a form. Its action is a Server Action, so the browser sends a POST to the server.
  2. The action checks that the user is logged in and allowed, validates the form data, and writes to the database.
  3. updateTag("products") expires every cached result tagged products.
  4. The same response re-renders the page with fresh data, so the user sees their change.

Problems it solves

  • Slow first loadThe browser gets HTML at once, often from a static shell.
  • Large JavaScript bundlesServer Components send no code to the browser.
  • A separate API for every formServer Actions are called directly from forms.
  • Choosing static or dynamic per pageOne page can be mostly static with small per-request parts.

Problems it introduces

  • Two environments in one codebaseEach component runs on the server, in the browser, or both, and the rules differ.
  • Caching rules to learnCache scope, lifetime and invalidation decide when users see changes.
  • Public endpoints you did not writeEvery Server Action can be called with a direct POST, so each needs its own auth check.
  • Fast-moving APIsCaching, Proxy and request APIs changed in each major version.
Server Componentapp/products/page.tsxAn async Server Component. It reads cached data and passes plain values to a Client Component. The personal part is wrapped in <Suspense>, so the rest of the page can be prerendered.
import { Suspense } from "react";
import { AddToCartButton } from "./add-to-cart-button";
import { getProducts } from "./products";
import { RecentlyViewed } from "./recently-viewed";

export default async function ProductsPage() {
  const products = await getProducts();
  return (
    <main>
      <ul>
        {products.map((product) => (
          <li key={product.id}>
            {product.name} <AddToCartButton productId={product.id} />
          </li>
        ))}
      </ul>
      <Suspense fallback={<p>Loading your history...</p>}>
        <RecentlyViewed />
      </Suspense>
    </main>
  );
}
Per requestapp/products/recently-viewed.tsxcookies() returns a Promise and depends on the request, so this part renders per request. Outside <Suspense>, the build stops with an error.
import { cookies } from "next/headers";

export async function RecentlyViewed() {
  const viewed = (await cookies()).get("recently-viewed")?.value.split(",") ?? [];
  return <p>You viewed {viewed.length} products recently.</p>;
}
Client Componentapp/products/add-to-cart-button.tsx"use client" sends this component's code to the browser, so it can use state. Its props, here a string, must be serializable.
"use client";

import { useState } from "react";

export function AddToCartButton({ productId }: { productId: string }) {
  const [added, setAdded] = useState(false);
  return (
    <button onClick={() => setAdded(true)} disabled={added}>
      {added ? "Added" : "Add to cart"}
    </button>
  );
}
Cacheapp/products/products.ts"use cache" caches the function's result. cacheLife("hours") refreshes it in the background after an hour; the build showed this route as static with revalidate 1h, expire 1d. cacheTag lets an action expire it. db is your database client.
import { cacheLife, cacheTag } from "next/cache";
import { db } from "@/lib/db";

export async function getProducts() {
  "use cache";
  cacheLife("hours");
  cacheTag("products");
  return db.product.findMany({ orderBy: { name: "asc" } });
}
Server Actionapp/products/actions.tsAnyone can call a Server Action with a POST, so it checks the session itself. updateTag expires the cached products at once, and the response shows the new data. auth and db are your own modules.
"use server";

import { updateTag } from "next/cache";
import { auth } from "@/lib/auth";
import { db } from "@/lib/db";

export async function renameProduct(formData: FormData) {
  const session = await auth();
  if (!session?.user.isAdmin) throw new Error("Only admins can rename products.");

  const productId = String(formData.get("productId"));
  const name = String(formData.get("name")).trim();
  if (name.length === 0) throw new Error("The name is empty.");

  await db.product.update({ where: { id: productId }, data: { name } });
  updateTag("products");
}
Proxyproxy.tsFormerly middleware.ts. It runs before matching routes, on Node.js. Here it only sends visitors without a session cookie to the login page: a quick check, not real authorization, which pages and actions must still do. The matcher skips static files.
import { NextResponse, type NextRequest } from "next/server";

export function proxy(request: NextRequest) {
  if (!request.cookies.has("session")) {
    return NextResponse.redirect(new URL("/login", request.url));
  }
  return NextResponse.next();
}

export const config = {
  matcher: ["/account/:path*", "/admin/:path*"],
};
