.NET / Runtime

.NET

A free, open-source platform from Microsoft for running C# programs on Windows, Linux and macOS.

What it is

.NET is three things that ship together. The runtime (CoreCLR) loads your program, turns it into machine code and frees unused memory. The libraries (the Base Class Library) give your code files, HTTP, JSON, collections and threads. The SDK holds the tools you use while developing: the C# compiler and the dotnet command.

C# is not run directly. dotnet build compiles it to IL (intermediate language), a CPU-independent instruction set, and saves it in a .dll file. When the program starts, the runtime's JIT compiler turns each method's IL into machine code for the CPU it runs on.

One .NET process uses many threads. Request handlers and the code after await run on a shared thread pool, so one process uses all CPU cores.

Main rule: C# becomes IL at build time and machine code at run time. Many threads run your code, so never block a thread pool thread while it waits for I/O: use await.

JIT, ReadyToRun and Native AOT

Tiered compilation is on by default. Tier 0 compiles a method fast, with few optimizations, so the app starts quickly. After a method has been called 30 times, a background thread compiles it again at tier 1, using data collected while tier 0 ran (Dynamic PGO, profile-guided optimization).

ModeHow to turn it onWhat changes
JIT (default)NothingSlowest start, fastest code after warm-up.
ReadyToRun<PublishReadyToRun>true</PublishReadyToRun>Machine code is stored in the .dll next to the IL. Faster start. The JIT still recompiles methods called often.
Native AOT<PublishAot>true</PublishAot>One native executable, no JIT. Fastest start, least memory. Code that generates types at run time, and some libraries, do not work.

Garbage collector

You never free memory yourself. Objects are created on the managed heap. When an area fills up, the GC pauses your threads for a short time, marks every object that is still reachable from a variable, and frees the rest. Most objects are used only during one request, so the GC splits the heap into generations and checks young objects most often.

AreaWhat lives thereHow often it is collected
Generation 0New objectsVery often. Fast, because the area is small.
Generation 1Objects that survived one collectionLess often. A buffer between young and old.
Generation 2Long-lived objects: caches, singletons, configurationRarely. Slowest, because it checks the whole heap.
Large object heap (LOH)Objects of 85,000 bytes or more, such as big arrays and stringsOnly with generation 2. Not compacted by default, so it can fragment.
Workstation GCOne heap. Default for console and desktop apps.Smaller memory use, lower throughput.
Server GCOne heap per CPU core. Default for ASP.NET Core.Higher throughput, more memory. Since .NET 9 it resizes its heaps to the load (DATAS).

Threads, the thread pool and async/await

.NET has no event loop for your code. The thread pool keeps a set of worker threads and a queue of work. Each incoming request runs on a free pool thread. Two requests can run at the same moment on two cores, so shared data needs locks or thread-safe types.

When a method reaches await on unfinished I/O, it returns, and its thread goes back to the pool. No thread waits for the network. When the operating system reports the result, the runtime queues the rest of the method to the pool, and whichever thread is free runs it. That is often a different thread from the one before await.

Desktop UI apps (WPF, WinForms) are the exception: they send the continuation back to the UI thread. ASP.NET Core and console apps do not.

SituationWhat happens
Code awaits I/OThe thread is returned to the pool while it waits. Thousands of waiting requests need few threads.
Code calls .Result or .Wait() on a taskThe thread is blocked until the task finishes. It cannot run other work.
All pool threads are blockedNew work queues. The pool adds about one or two threads per second. This is thread pool starvation.
CPU-heavy codeRuns on its pool thread and uses one core. Other requests use the other cores.

Logging and monitoring

Log through ILogger<T>, which ASP.NET Core and the generic host give you through dependency injection. Use message templates: logger.LogInformation("Loading order {OrderId}", orderId). The provider stores OrderId as its own field, so you can search by it. Do not build the message with string interpolation: the field is lost.

Signs of thread pool starvation: response times rise to seconds while CPU use stays low, the thread pool queue length grows, the thread count climbs by one or two per second, and health checks time out. Look for .Result, .Wait() and Thread.Sleep in request code.

Diagram

Example flow:

Pick a flow and press Play to follow it through the diagram, step by step.

  1. You run dotnet build. It restores NuGet packages, then the C# compiler reads Program.cs and the other .cs files in the project.
  2. The compiler writes ShopApi.dll: IL plus metadata that describes every type and method. There is no machine code in it yet.
  3. You run dotnet ShopApi.dll. The host starts CoreCLR, and the type loader reads the types that Main needs.
  4. The JIT compiles Main from IL to machine code for this CPU, and the runtime calls it.
  5. Your code calls the Base Class Library, for example to open a socket. The library calls the operating system.
  1. A request calls CalculateTotal for the first time. The method has no machine code yet, so the runtime asks the JIT to compile it.
  2. Tier 0: the JIT compiles quickly with few optimizations, and counts how often the method is called. This first call is slower than later ones.
  3. After 30 calls, a background thread compiles the method again at tier 1, with full optimizations based on what tier 0 measured.
  4. The next request runs the new code. ReadyToRun skips most tier 0 work at startup. Native AOT has no JIT at all.
  1. A request arrives. Pool thread 7 runs the handler, which calls await httpClient.GetStringAsync(url).
  2. The Base Class Library sends the HTTP request through the operating system. The task is not finished, so the handler returns and thread 7 goes back to the pool.
  3. No thread waits for the response. Thread 7 runs other requests in the meantime.
  4. The response arrives. The runtime queues the rest of the handler to the pool, and free thread 12 runs it.
  5. There is no event loop. Code after await must not depend on the thread: values in [ThreadStatic] fields differ. AsyncLocal<T> values are carried over.
  1. A handler calls httpClient.GetStringAsync(url).Result. The request is sent, and the pool thread is blocked until the response arrives.
  2. Traffic rises. Every pool thread is now blocked in the same .Result call.
  3. Responses arrive. Finishing each task needs a free pool thread, so the work sits in the queue. New requests queue too.
  4. The pool adds about one or two threads per second. Response times reach seconds while CPU stays low. Fix: use await in every method from the handler down.
  1. Each request creates objects: the order, a list of lines, strings for the JSON. They go into generation 0.
  2. Generation 0 fills. The GC pauses threads for a short time, keeps objects still in use and frees the rest. Most request objects are already unused.
  3. Objects that survive move to generation 1, and later to generation 2. Generation 2 is collected rarely, because checking it takes longer.
  4. A 100 KB array is 85,000 bytes or more, so it goes to the large object heap. It is freed only in a generation 2 collection.
  5. In a container, the heap may use 75% of the memory limit by default. If live objects need more, the app throws OutOfMemoryException.

Problems it solves

  • Type errors found lateThe C# compiler rejects wrong types before the app runs.
  • Using all CPU coresOne process runs code on every core through the thread pool.
  • CPU-heavy work in a web serverA slow calculation uses one pool thread. Other requests keep running.
  • Manual memory managementThe GC frees unused objects, and generations keep most pauses short.
  • Choosing many small librariesThe BCL covers HTTP, JSON, files, crypto, collections and logging interfaces.

Problems it introduces

  • Shared data across threadsTwo requests can change the same object at once. You need locks or concurrent collections.
  • Thread pool starvationOne .Result in a busy path can stall the whole app.
  • Slower first requestsTier 0 JIT code and loading assemblies make the first seconds slower. ReadyToRun or AOT helps.
  • Higher memory than a small Node.js processServer GC keeps one heap per core. Tune it in small containers.
  • Confusing names.NET Framework, .NET Core and .NET are different products, and search results mix them.

JITexamples/TieredCompilation.csTimes the same method on call 1, call 2 and after tier 1 has had time to run. Call 1 includes JIT compilation. Later calls are faster. Run it again with DOTNET_TieredCompilation=0 to compile fully optimized code on the first call. Exact numbers depend on the machine.
using System.Diagnostics;

for (int callNumber = 1; callNumber <= 60; callNumber++)
{
    var stopwatch = Stopwatch.StartNew();
    SumOfSquares(100_000);
    stopwatch.Stop();

    if (callNumber is 1 or 2 or 31 or 60)
    {
        Console.WriteLine($"call {callNumber}: {stopwatch.Elapsed.TotalMicroseconds:F0} microseconds");
    }

    Thread.Sleep(20);
}

static long SumOfSquares(int count)
{
    long total = 0;
    for (int number = 0; number < count; number++)
    {
        total += (long)number * number;
    }
    return total;
}

Thread poolexamples/ThreadPoolStarvation.csStarts 200 work items that each block a pool thread for 1 second. Finishing the delay needs a pool thread too, so the queue grows and the thread count rises slowly. It takes far longer than 1 second. Replace .Wait() with await and all 200 finish in about 1 second.
using System.Diagnostics;

var stopwatch = Stopwatch.StartNew();

var blockingWorkItems = Enumerable.Range(1, 200)
    .Select(_ => Task.Run(() => Task.Delay(TimeSpan.FromSeconds(1)).Wait()))
    .ToArray();

while (!Task.WaitAll(blockingWorkItems, TimeSpan.FromSeconds(1)))
{
    Console.WriteLine(
        $"{stopwatch.Elapsed.TotalSeconds:F0} s: pool threads = {ThreadPool.ThreadCount}, queued = {ThreadPool.PendingWorkItemCount}");
}

Console.WriteLine($"200 one-second waits took {stopwatch.Elapsed.TotalSeconds:F0} s");
