System design / Reliability

Reliability Patterns

How a service keeps working when the services it calls are slow, failing, or called too often.

What it is

Every call over the network can fail, hang or arrive twice. Without protection, one slow dependency makes your requests wait, threads and connections fill up, and your service fails too. Five patterns limit the damage.

PatternKey pointWithout it
TimeoutGive every outgoing call a maximum time, shorter than your own request's deadline.A hanging dependency holds your request open for minutes
Retry with backoffRetry failures that are likely temporary, such as a 503 or a timeout, a few times, waiting longer each time with a random part.One network blip fails the user's request
Idempotency keyThe caller sends a unique key with each operation; the server remembers it and does the work only once.A retried payment charges the card twice
Circuit breakerAfter many failures, stop calling the dependency for a while and fail at once. Then let one test call through.Retries pile onto a service that is already down
Rate limitAllow each client a number of requests per time window. Answer 429 above it.One client's traffic slows everyone
Main rule: every outgoing call gets a timeout. Retry only temporary errors, only a few times, with random backoff, and only operations that are safe to repeat or carry an idempotency key.

What to retry

ResponseRetry?Why
Timeout, connection resetYes, if idempotentThe request may or may not have been processed
502, 503, 504YesThe service or a proxy in front of it is temporarily unavailable
429 Too Many RequestsYes, after the Retry-After timeThe server told you when
400, 401, 403, 404, 422NoThe same request will fail the same way
500Usually noOften a bug that a retry repeats

Retry at one layer only. If the browser, the gateway and your service each retry 3 times, one failure becomes 27 calls.

Circuit breaker states

StateCallsMoves to
ClosedPass through normallyOpen, when the failure rate passes a limit, such as 50% of the last 20 calls
OpenFail at once, without calling the dependencyHalf-open, after a wait such as 30 seconds
Half-openA few test calls go throughClosed if they succeed, open again if they fail

Logging and monitoring

WhereWhat to log or measure
Each retryDependency, attempt number, status or error, request ID, at warn. The final failure once, at error.
TimeoutsCount per dependency. A rise means the dependency is slowing down.
Circuit breakerEvery state change, at warn when it opens. Alert on open.

Problems these patterns solve

  • Short network failuresRetries hide brief errors from users.
  • One failure spreadingTimeouts and breakers stop a slow dependency from tying up your service.
  • Duplicate side effectsIdempotency keys make retries safe for payments and orders.
  • Noisy clientsRate limits protect capacity for everyone else.

Problems they introduce

  • More load during an outageBadly configured retries multiply traffic to a failing service.
  • Settings to tuneTimeouts, retry counts, breaker thresholds and limits need real numbers.
  • Storage for keysIdempotency keys must be stored and expired.
  • Errors users seeAn open breaker or a 429 is still a failure the client must handle.
Timeout and retrysrc/charge-payment.tsAbortSignal.timeout ends each attempt after 2 seconds. Only timeouts and 502-504 are retried, at most 3 attempts, with a growing random wait. Every attempt sends the same Idempotency-Key. Retries are logged at warn; the caller logs the final failure.
import { setTimeout as wait } from "node:timers/promises";
import type { Logger } from "pino";

const retryableStatuses = new Set([502, 503, 504]);
const maxAttempts = 3;

export async function chargePayment(requestLogger: Logger, orderId: string, amount: number): Promise<{ paymentId: string }> {
  for (let attempt = 1; ; attempt++) {
    try {
      const response = await fetch("https://payments.internal/charges", {
        method: "POST",
        headers: { "Content-Type": "application/json", "Idempotency-Key": `order-${orderId}` },
        body: JSON.stringify({ orderId, amount }),
        signal: AbortSignal.timeout(2_000),
      });
      if (response.ok) return (await response.json()) as { paymentId: string };
      if (!retryableStatuses.has(response.status) || attempt === maxAttempts) {
        throw new Error(`Payment failed with status ${response.status}.`);
      }
      requestLogger.warn({ dependency: "payments", attempt, status: response.status }, "retrying payment");
    } catch (error) {
      const isTimeout = error instanceof DOMException && error.name === "TimeoutError";
      if (!isTimeout || attempt === maxAttempts) throw error;
      requestLogger.warn({ dependency: "payments", attempt, reason: "timeout" }, "retrying payment");
    }
    await wait(Math.random() * 200 * 2 ** attempt);
  }
}
Circuit breakersrc/payment-breaker.tsThe opossum library wraps the call. When half of the calls in its window fail, it opens and rejects at once for 30 seconds, then lets a test call through. State changes are logged.
import CircuitBreaker from "opossum";
import pino from "pino";
import { chargePayment } from "./charge-payment.js";

const logger = pino();

export const paymentBreaker = new CircuitBreaker(chargePayment, {
  errorThresholdPercentage: 50,
  resetTimeout: 30_000,
  volumeThreshold: 20,
});

paymentBreaker.on("open", () => logger.warn({ dependency: "payments" }, "circuit opened"));
paymentBreaker.on("halfOpen", () => logger.info({ dependency: "payments" }, "circuit half-open"));
paymentBreaker.on("close", () => logger.info({ dependency: "payments" }, "circuit closed"));
Rate limitersrc/rate-limit.tsexpress-rate-limit counts requests per client in a one-minute window and answers 429 with a Retry-After header above 100. The key is the client ID from authentication, so clients behind one IP address do not share a limit. With several servers, give it a Redis store so the count is shared.
import { rateLimit } from "express-rate-limit";

export const perClientRateLimit = rateLimit({
  windowMs: 60_000,
  limit: 100,
  standardHeaders: "draft-8",
  keyGenerator: (req) => req.auth?.clientId ?? req.ip ?? "unknown",
});
Timeout and retryProgram.csAddStandardResilienceHandler, from Microsoft.Extensions.Http.Resilience, adds a total timeout, retries with random backoff for temporary errors, a circuit breaker and a timeout per attempt to every call of this client. The handler sets the idempotency key, so retries send the same one.
builder.Services.AddHttpClient<PaymentClient>(client => client.BaseAddress = new Uri("https://payments.internal"))
    .AddStandardResilienceHandler(options =>
    {
        options.AttemptTimeout.Timeout = TimeSpan.FromSeconds(2);
        options.Retry.MaxRetryAttempts = 2;
        options.TotalRequestTimeout.Timeout = TimeSpan.FromSeconds(10);
        ResilienceSettings.ConfigureBreaker(options);
    });

public sealed class PaymentClient(HttpClient httpClient)
{
    public async Task<PaymentResult> ChargeAsync(string orderId, decimal amount, CancellationToken cancellationToken)
    {
        using var request = new HttpRequestMessage(HttpMethod.Post, "/charges")
        {
            Content = JsonContent.Create(new { orderId, amount }),
        };
        request.Headers.Add("Idempotency-Key", $"order-{orderId}");
        using var response = await httpClient.SendAsync(request, cancellationToken);
        response.EnsureSuccessStatusCode();
        return (await response.Content.ReadFromJsonAsync<PaymentResult>(cancellationToken))!;
    }
}
Circuit breakerResilienceSettings.csThe breaker is part of the standard handler. These settings open it when half of at least 20 calls in 30 seconds fail, and keep it open for 30 seconds. Polly logs state changes through the app's logger.
public static class ResilienceSettings
{
    public static void ConfigureBreaker(HttpStandardResilienceOptions options)
    {
        options.CircuitBreaker.FailureRatio = 0.5;
        options.CircuitBreaker.MinimumThroughput = 20;
        options.CircuitBreaker.SamplingDuration = TimeSpan.FromSeconds(30);
        options.CircuitBreaker.BreakDuration = TimeSpan.FromSeconds(30);
    }
}
Rate limiterRateLimiting.csASP.NET Core's built-in rate limiter. Each client ID gets 100 requests per minute; above that the response is 429. The partition key is the client ID claim, falling back to the IP address.
using System.Threading.RateLimiting;

builder.Services.AddRateLimiter(options =>
{
    options.RejectionStatusCode = StatusCodes.Status429TooManyRequests;
    options.GlobalLimiter = PartitionedRateLimiter.Create<HttpContext, string>(context =>
        RateLimitPartition.GetFixedWindowLimiter(
            context.User.FindFirst("client_id")?.Value ?? context.Connection.RemoteIpAddress?.ToString() ?? "unknown",
            _ => new FixedWindowRateLimiterOptions { PermitLimit = 100, Window = TimeSpan.FromMinutes(1) }));
});

app.UseRateLimiter();
Payment serviceidempotency-keys.sqlThe payment service inserts the key in the same transaction as the charge. A second request with the same key hits the primary key, finds the stored result and returns it without charging. Old keys are deleted after 24 hours.
CREATE TABLE idempotency_keys (
  idempotency_key text PRIMARY KEY,
  response_status integer NOT NULL,
  response_body   jsonb NOT NULL,
  created_at      timestamptz NOT NULL DEFAULT now()
);

INSERT INTO idempotency_keys (idempotency_key, response_status, response_body)
VALUES ('order-o-1', 201, '{"paymentId": "pay-9"}')
ON CONFLICT (idempotency_key) DO NOTHING;

SELECT response_status, response_body FROM idempotency_keys WHERE idempotency_key = 'order-o-1';

DELETE FROM idempotency_keys WHERE created_at < now() - interval '24 hours';
