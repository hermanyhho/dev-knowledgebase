System design / Messaging

Message Queues and Logs

Two kinds of message broker, what they guarantee about delivery, and how order is kept.

What it is

A message broker sits between a service that sends messages and services that process them, so the sender does not wait and does not need the receiver to be running. The event-driven page shows why; this page covers how brokers behave.

There are two designs. A queue, such as RabbitMQ, hands each message to one consumer and deletes it once processed. A log, such as Kafka, appends messages to a file that consumers read at their own position; messages stay for a set time, so several consumer groups and replays can read them.

IdeaKey pointCommon mistake
Queue or logQueues spread jobs over workers. Logs keep a history that many readers use independently.Using a queue when a second team later needs the same events
Delivery guaranteesBrokers give at-least-once delivery: a message can arrive twice, for example after a consumer crashes before acknowledging it.Assuming each message arrives once, and charging twice
OrderingA queue with several consumers does not keep order. Kafka keeps order within one partition, and messages with the same key go to the same partition.Expecting global order across partitions
Failed messagesAfter a few failed attempts, move the message to a dead-letter queue instead of retrying forever.One bad message blocking the whole queue
Main rule: expect every message at least once and make consumers idempotent. Choose the message key by what must stay in order, such as the order ID.

Queue and log compared

Queue (RabbitMQ)Log (Kafka)
After processingMessage deletedMessage kept until the retention time ends
Several consumersShare the work: each message to one consumerEach consumer group reads every message; inside a group, each partition goes to one consumer
ProgressAcknowledgement per messageAn offset per partition: the position read so far
Replay old messagesNot possibleMove the offset back
Good forBackground jobs, emails, tasksEvents many services use, high volume, audit history

Delivery guarantees

GuaranteeHow it happensRisk
At most onceAcknowledge before processingA crash loses the message
At least onceAcknowledge after processingA crash after processing but before the acknowledgement delivers it again
Effectively onceAt least once, plus a consumer that records processed message IDs and skips repeatsNeeds a store for IDs, in the same transaction as the work

Sending is the other half: to avoid losing a message when the database commit succeeds but the publish fails, write it in the same transaction with the transactional outbox.

Problems brokers solve

  • Waiting for slow workThe sender answers the user and the work happens later.
  • Receivers that are downMessages wait in the broker until the consumer is back.
  • Peaks of trafficThe broker holds the extra messages; consumers work through them at their pace.
  • Many services needing one eventA log lets each read it without the sender knowing them.

Problems they introduce

  • DuplicatesAt-least-once delivery means every consumer must handle repeats.
  • Ordering limitsOrder holds only per partition or per single consumer.
  • Delay and eventual consistencyOther services see a change seconds later.
  • Harder debuggingA request's work is spread over services, which correlation IDs must connect.
Producersrc/publish-order-event.tsThe order ID is the message key, so all events of one order go to the same partition and stay in order. The correlation ID travels in a header. Uses the kafkajs API.
import type { Producer } from "kafkajs";

export async function publishOrderPlaced(producer: Producer, orderId: string, correlationId: string) {
  await producer.send({
    topic: "orders",
    messages: [
      {
        key: orderId,
        value: JSON.stringify({ type: "OrderPlaced", messageId: crypto.randomUUID(), orderId }),
        headers: { "correlation-id": correlationId },
      },
    ],
  });
}
Logsrc/billing-consumer.tsThe billing group reads the orders topic. With autoCommit: false, the offset is committed only after the work is done, which gives at-least-once delivery. The correlation ID from the header goes into every log line.
import type { Consumer } from "kafkajs";
import type { Logger } from "pino";
import { handleOrderPlaced } from "./handle-order-placed.js";

export async function runBillingConsumer(consumer: Consumer, logger: Logger) {
  await consumer.subscribe({ topic: "orders" });
  await consumer.run({
    autoCommit: false,
    eachMessage: async ({ topic, partition, message }) => {
      const event = JSON.parse(message.value!.toString());
      const messageLogger = logger.child({ correlationId: message.headers?.["correlation-id"]?.toString(), messageId: event.messageId });
      await handleOrderPlaced(event, messageLogger);
      await consumer.commitOffsets([{ topic, partition, offset: (BigInt(message.offset) + 1n).toString() }]);
    },
  });
}
Queuesrc/email-worker.tsAn amqplib worker. prefetch(10) gives each worker at most 10 unacknowledged jobs. The job is acknowledged after the email is sent. On failure it is rejected without requeue, and the queue's dead-letter settings move it on.
import type { Channel } from "amqplib";
import type { Logger } from "pino";
import { sendConfirmationEmail } from "./email.js";

export async function runEmailWorker(channel: Channel, logger: Logger) {
  await channel.prefetch(10);
  await channel.consume("send-email", async (message) => {
    if (!message) return;
    const job = JSON.parse(message.content.toString());
    try {
      await sendConfirmationEmail(job.orderId);
      channel.ack(message);
    } catch (error) {
      logger.error({ err: error, messageId: job.messageId }, "email job failed");
      channel.nack(message, false, false);
    }
  });
}
ProducerOrderEventPublisher.csThe order ID is the message key, so all events of one order go to the same partition and stay in order. The correlation ID travels in a header. Uses Confluent.Kafka.
using System.Text;
using System.Text.Json;
using Confluent.Kafka;

public sealed class OrderEventPublisher(IProducer<string, string> producer)
{
    public Task PublishOrderPlacedAsync(string orderId, string correlationId) =>
        producer.ProduceAsync("orders", new Message<string, string>
        {
            Key = orderId,
            Value = JsonSerializer.Serialize(new { type = "OrderPlaced", messageId = Guid.NewGuid(), orderId }),
            Headers = new Headers { { "correlation-id", Encoding.UTF8.GetBytes(correlationId) } },
        });
}
LogBillingConsumer.csThe billing group reads the orders topic. EnableAutoCommit = false and the explicit Commit after the work give at-least-once delivery. A logging scope adds the correlation ID to every line.
using System.Text;
using Confluent.Kafka;

public sealed class BillingConsumer(IConsumer<string, string> consumer, OrderPlacedHandler handler, ILogger<BillingConsumer> logger) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        consumer.Subscribe("orders");
        while (!stoppingToken.IsCancellationRequested)
        {
            var result = consumer.Consume(stoppingToken);
            var correlationId = Encoding.UTF8.GetString(result.Message.Headers.GetLastBytes("correlation-id"));
            using (logger.BeginScope(new Dictionary<string, object> { ["CorrelationId"] = correlationId }))
            {
                await handler.HandleAsync(result.Message.Value, stoppingToken);
            }
            consumer.Commit(result);
        }
    }
}
QueueEmailWorker.csA RabbitMQ.Client 7 worker. prefetchCount: 10 limits unacknowledged jobs per worker. The job is acknowledged after the email is sent; on failure it is rejected without requeue, and the queue's dead-letter settings move it on.
using System.Text.Json;
using RabbitMQ.Client;
using RabbitMQ.Client.Events;

public sealed class EmailWorker(IChannel channel, EmailSender emailSender, ILogger<EmailWorker> logger) : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        await channel.BasicQosAsync(prefetchSize: 0, prefetchCount: 10, global: false, stoppingToken);
        var consumer = new AsyncEventingBasicConsumer(channel);
        consumer.ReceivedAsync += async (_, delivery) =>
        {
            var job = JsonSerializer.Deserialize<EmailJob>(delivery.Body.Span)!;
            try
            {
                await emailSender.SendConfirmationAsync(job.OrderId, stoppingToken);
                await channel.BasicAckAsync(delivery.DeliveryTag, multiple: false);
            }
            catch (Exception exception)
            {
                logger.LogError(exception, "Email job {MessageId} failed", job.MessageId);
                await channel.BasicNackAsync(delivery.DeliveryTag, multiple: false, requeue: false);
            }
        };
        await channel.BasicConsumeAsync("send-email", autoAck: false, consumer, stoppingToken);
    }
}
Duplicatesprocessed-messages.sqlThe consumer inserts the message ID in the same transaction as its work, and checks how many rows that insert changed. For a repeated message it changes 0 rows, so the consumer rolls back and skips the invoice. This turns at-least-once delivery into effectively once.
CREATE TABLE processed_messages (
  message_id   uuid PRIMARY KEY,
  processed_at timestamptz NOT NULL DEFAULT now()
);

BEGIN;
INSERT INTO processed_messages (message_id) VALUES ('6f1c9e2a-0b7d-4c55-9a3e-1f2d3c4b5a69')
ON CONFLICT (message_id) DO NOTHING;
INSERT INTO invoices (order_id, total) VALUES ('o-1', 49.90);
COMMIT;
