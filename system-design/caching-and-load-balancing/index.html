System design / Speed

Caching, CDNs and Load Balancing

Three ways to answer more requests faster: keep answers close, keep them in memory, and spread requests over several servers.

What it is

Most requests ask for the same data again and again, and each one costs a database query and a trip across the network. Speed comes from not doing that work twice, doing it closer to the user, and sharing it across servers.

IdeaKey pointCost
CachingKeep the result of slow work, usually in memory or in Redis, and reuse it. The common pattern is cache-aside: read the cache, and on a miss read the database and store the result.Cached data can be out of date. Deciding when to remove it is the hard part.
CDNA network of servers in many cities that keep copies of files and responses close to users. Your server answers once; the CDN answers the rest.Only for responses that are the same for many users; changes need a purge or short lifetimes
Load balancingOne address in front of several app servers. The load balancer sends each request to a healthy server.Servers must not keep user data in their own memory, or the next request may land elsewhere
Main rule: cache data that is read far more often than it changes, give every cache entry a lifetime, and keep app servers stateless so any of them can answer any request.

Keeping a cache correct

ProblemWhat happensFix
Stale dataThe database changed, the cache still has the old valueDelete the key when you write, and set a lifetime (TTL) as a safety net
StampedeA popular key expires and hundreds of requests query the database at onceLet one request refresh it while others wait, or refresh before it expires
Cache downEvery request goes to the databaseTreat the cache as optional: on error, read the database and log a warning
Personal data in a shared cacheOne user's response shown to anotherInclude the user in the key, or mark the response Cache-Control: private

Load balancing basics

ChoiceOptions
How to pick a serverRound robin; least connections, which suits requests of different lengths
HealthThe balancer calls a health endpoint, such as /health/ready, and stops sending to servers that fail it
LayerLayer 4 forwards TCP connections; layer 7 reads HTTP and can route by path or header
SessionsStore them in a shared cache or a token, not in one server's memory. Sticky sessions work but make scaling uneven.

Problems these ideas solve

  • Slow responsesMemory and nearby copies answer in milliseconds.
  • Database overloadA cache takes most repeated reads.
  • One server is not enoughA load balancer spreads requests over many.
  • A server failsHealth checks move traffic to the others.

Problems they introduce

  • Out-of-date answersEvery cache layer can show old data until it expires or is cleared.
  • More to runRedis, CDN settings and the load balancer are more parts to configure and watch.
  • Stateless serversSessions and uploads must move out of server memory and disk.
  • Harder debuggingThe same request can be answered by a CDN, a cache or the database.
Appsrc/product-cache.tsCache-aside with ioredis. A miss reads the database and stores the result for 5 minutes. If Redis fails, the request still works from the database, and a warning is logged with the request ID. Editing a product deletes its key.
import type { Redis } from "ioredis";
import type { Logger } from "pino";
import { loadProductFromDatabase, saveProductToDatabase, type Product } from "./products-db.js";

const productTtlSeconds = 300;
const productKey = (productId: string) => `product:${productId}`;

export async function getProduct(redis: Redis, requestLogger: Logger, productId: string): Promise<Product | null> {
  try {
    const cached = await redis.get(productKey(productId));
    if (cached) return JSON.parse(cached) as Product;
  } catch (error) {
    requestLogger.warn({ err: error, operation: "cache read" }, "cache unavailable, reading the database");
  }

  const product = await loadProductFromDatabase(productId);
  if (product) {
    await redis.set(productKey(productId), JSON.stringify(product), "EX", productTtlSeconds).catch(() => undefined);
  }
  return product;
}

export async function updateProduct(redis: Redis, product: Product): Promise<void> {
  await saveProductToDatabase(product);
  await redis.del(productKey(product.id));
}
Healthsrc/health.tsThe load balancer calls /health/ready. It answers 503 when the database cannot be reached, so the balancer stops sending requests here. /health/live only says the process runs.
import type { Express } from "express";
import type { Pool } from "pg";

export function addHealthRoutes(app: Express, database: Pool) {
  app.get("/health/live", (_req, res) => res.send("ok"));

  app.get("/health/ready", async (_req, res) => {
    try {
      await database.query("SELECT 1");
      res.send("ready");
    } catch {
      res.status(503).send("database unreachable");
    }
  });
}
AppProductCache.csHybridCache keeps a copy in memory and in Redis, and lets only one caller load a missing key while others wait, which prevents a stampede. Editing a product removes its key.
using Microsoft.Extensions.Caching.Hybrid;

public sealed class ProductCache(HybridCache cache, ProductsDatabase database)
{
    private static readonly HybridCacheEntryOptions ProductEntry = new() { Expiration = TimeSpan.FromMinutes(5) };

    public ValueTask<Product?> GetProductAsync(string productId, CancellationToken cancellationToken) =>
        cache.GetOrCreateAsync(
            $"product:{productId}",
            async token => await database.LoadProductAsync(productId, token),
            ProductEntry,
            cancellationToken: cancellationToken);

    public async Task UpdateProductAsync(Product product, CancellationToken cancellationToken)
    {
        await database.SaveProductAsync(product, cancellationToken);
        await cache.RemoveAsync($"product:{product.Id}", cancellationToken);
    }
}
HealthProgram.csThe load balancer calls /health/ready, which runs the checks tagged ready, here the database. AddNpgSql comes from the AspNetCore.HealthChecks.NpgSql package. /health/live runs no checks. Redis is the second layer of HybridCache.
var builder = WebApplication.CreateBuilder(args);

builder.Services.AddStackExchangeRedisCache(options =>
    options.Configuration = builder.Configuration.GetConnectionString("Redis"));
builder.Services.AddHybridCache();
builder.Services.AddHealthChecks()
    .AddNpgSql(builder.Configuration.GetConnectionString("Orders")!, tags: ["ready"]);

var app = builder.Build();

app.MapHealthChecks("/health/live", new() { Predicate = _ => false });
app.MapHealthChecks("/health/ready", new() { Predicate = check => check.Tags.Contains("ready") });

app.Run();
