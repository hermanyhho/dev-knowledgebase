System design / Databases

Database Indexes

A sorted copy of chosen columns that lets the database find rows without reading the whole table. Examples use PostgreSQL 18.

What it is

Without an index, the database answers WHERE customer_id = 'c-042' by reading every row of the table and checking each one. With 2 million orders, that is about 40,000 pages of 8 KB.

An index is a separate structure that stores the values of chosen columns in sorted order. Next to each value it stores where the row is in the table. Because the values are sorted, the database finds a value in a few steps, the same way you find a word in a dictionary, and then reads only the matching rows.

The cost: every insert, update and delete must also change every index on the table.

Main rule: create indexes for the queries you run often, matching their WHERE, JOIN and ORDER BY columns. Every index slows down writes and uses disk, so check with EXPLAIN before and after.

How one lookup works

The query: the 20 newest orders of customer c-042, in a table of 2 million orders, with an index on (customer_id, created_at).

StepWhat PostgreSQL doesPages read
1. PlanThe planner estimates that about 100 rows match and picks an index scan.0
2. Root pageCompares c-042 with the separator values and follows the pointer to the right branch page.1
3. Branch pageDoes the same and follows the pointer to the right leaf page.1
4. Leaf pageThe entries for c-042 are next to each other, sorted by created_at. It reads them from the newest end.1-2
5. HeapReads each of the 20 rows from its page, using the row location.up to 20

About 24 pages instead of 40,000. The tree grows slowly: each page holds hundreds of entries, so 3 or 4 levels cover hundreds of millions of rows.

Column order in a multicolumn index

An index on (customer_id, created_at) is sorted by customer_id first. Inside each customer, entries are sorted by created_at.

QueryUses the index?Why
WHERE customer_id = $1YesIt is the first column.
WHERE customer_id = $1 ORDER BY created_at DESC LIMIT 20Yes, with no sort stepOne customer's entries are already sorted by date. PostgreSQL reads the index backwards and stops after 20.
WHERE customer_id = $1 AND created_at >= $2Yes, both columnsAn equal value on the first column, then a range on the second.
WHERE customer_id = $1 AND status = 'pending'PartlyThe index finds the customer. Each of those rows is then checked for status.
WHERE created_at >= $1Usually noOne day's orders are spread across every customer in the index. PostgreSQL 18 can use a skip scan when the first column has few distinct values, which is not the case for customers.
Order the columns: columns compared with = first, then the column used for a range or for sorting.

What each index costs

CostDetail
Slower writesAn insert writes the row and one entry in every index. A table with 6 indexes does 7 writes per insert.
Fewer HOT updatesPostgreSQL can update a row without touching its indexes (a HOT update) only when no indexed column changes. Indexing a column that changes often removes this.
Disk and memoryIndexes take disk space and share the database's memory cache with the table pages.
Random keysRandom UUIDs (version 4) are inserted at random places in the index, so many pages change. uuidv7(), new in PostgreSQL 18, is ordered by time, so new keys go to the end.
Locks while buildingCREATE INDEX blocks writes until it finishes. CREATE INDEX CONCURRENTLY does not, but takes longer and cannot run inside a transaction.
No automatic indexes on foreign keysPostgreSQL indexes primary keys and unique constraints only. Add indexes on foreign key columns you join or delete by.

Diagram

Example flow:

Pick a flow and press Play to follow it through the diagram, step by step.

  1. The app runs SELECT ... WHERE customer_id = 'c-042' ORDER BY created_at DESC LIMIT 20.
  2. The planner's statistics say about 100 of 2 million rows match. It picks an index scan on orders_customer_created_idx.
  3. PostgreSQL reads the root page. c-042 sorts before c-300, so it follows the first pointer.
  4. The branch page for c-001 .. c-299 points to the leaf page that holds c-042.
  5. In the leaf page, the entries for c-042 sit next to each other, sorted by date. PostgreSQL reads them from the newest one backwards.
  6. Each entry holds a row location. PostgreSQL reads page 2 for row (2,4) and page 0 for row (0,7). About 24 pages in total.
  1. The app runs SELECT ... WHERE total > 1000. No index starts with total.
  2. The planner has no index to use, so it plans a sequential scan, split across 2 parallel workers.
  3. PostgreSQL reads every heap page and checks total on every row. With 2 million rows this takes about 100 ms.
  4. If the query runs often, the slow query log and pg_stat_statements show it. An index on total only helps if few orders are over 1000.
  1. The app needs only created_at and total. The index was created with INCLUDE (total), so its leaf entries hold both.
  2. PostgreSQL walks from the root page to the leaf page, as in the first flow.
  3. The leaf entries already hold every column the query needs. If VACUUM has marked those heap pages as all-visible, PostgreSQL does not read the heap at all.
  4. The plan shows Index Only Scan and Heap Fetches: 0. On a table with many recent changes, the heap fetches grow until the next VACUUM.
  1. The app inserts an order for c-042.
  2. PostgreSQL writes the row into a heap page with free space, for example page 3. It gets a new row location.
  3. PostgreSQL walks the index to the leaf page for c-042 and adds an entry with the new date and row location, in sorted position.
  4. If the leaf page is full, PostgreSQL splits it into two pages and adds a pointer to the branch page. This is extra work on the write.
  5. The same happens in every other index on orders, including the primary key. Each index makes every insert slower.
  1. Before the index exists, the query takes about 100 ms. The app logs slow query with the query name, duration and request ID.
  2. You find the query in pg_stat_statements by total time, then run EXPLAIN (ANALYZE). The plan shows Seq Scan and Rows Removed by Filter: 1999904.
  3. You add the index with CREATE INDEX CONCURRENTLY, so writes to orders continue while it builds.
  4. You run EXPLAIN (ANALYZE) again. The plan shows Index Scan Backward and the query takes under 1 ms.

Problems it solves

  • Slow reads on large tablesA lookup reads about 24 pages instead of 40,000, and the gap grows with the table.
  • Sorting large resultsRows come out of the index already in order, so ORDER BY ... LIMIT stops early.
  • Duplicate valuesA unique index rejects a second row with the same email or order number.
  • Slow joinsAn index on the join column finds the matching rows in the other table directly.
  • Database loadLess disk reading and CPU per query, so one server handles more queries.

Problems it introduces

  • Slower writesEvery insert, and every update of an indexed column, changes every index.
  • Disk and memoryIndexes can together be larger than the table, and they compete for the cache.
  • Indexes that are never usedA wrong column order or a function on the column means the planner ignores the index, but writes still pay for it.
  • Locks on live tablesA plain CREATE INDEX blocks writes. The concurrent version needs extra care in migrations.
  • Plans that changeThe planner decides from statistics, so the same query can switch plans when the data grows.

import type { Pool } from "pg";
import type { Logger } from "pino";
import { timedQuery } from "./timed-query.js";

export type OrderSummary = { id: string; createdAt: Date; total: string };

export function findRecentOrders(
  database: Pool,
  requestLogger: Logger,
  customerId: string,
  limit = 20,
): Promise<OrderSummary[]> {
  return timedQuery<OrderSummary>(
    database,
    requestLogger,
    "findRecentOrders",
    `SELECT id, created_at AS "createdAt", total
       FROM orders
      WHERE customer_id = $1
      ORDER BY created_at DESC
      LIMIT $2`,
    [customerId, limit],
  );
}

export async function createOrder(
  database: Pool,
  requestLogger: Logger,
  customerId: string,
  total: string,
): Promise<void> {
  await timedQuery(
    database,
    requestLogger,
    "createOrder",
    "INSERT INTO orders (customer_id, status, total) VALUES ($1, 'pending', $2)",
    [customerId, total],
  );
}
Loggingsrc/timed-query.tsEvery query goes through this function. requestLogger is the per-request child logger, so each line already has the request ID. It logs the query name, not the values, because values can hold personal data.
import type { Pool, QueryResultRow } from "pg";
import type { Logger } from "pino";

const slowQueryThresholdMs = 200;

export async function timedQuery<Row extends QueryResultRow>(
  database: Pool,
  requestLogger: Logger,
  queryName: string,
  sql: string,
  values: unknown[],
): Promise<Row[]> {
  const startedAt = performance.now();
  const result = await database.query<Row>(sql, values);
  const durationMs = Math.round(performance.now() - startedAt);

  if (durationMs >= slowQueryThresholdMs) {
    requestLogger.warn({ queryName, durationMs, rowCount: result.rowCount }, "slow query");
  }
  return result.rows;
}
QueryOrdersRepository.csThe WHERE and ORDER BY columns match the index (customer_id, created_at) in the same order, so PostgreSQL reads 20 index entries and stops. Npgsql sends the values as parameters ($1), never pasted into the SQL text.
using Npgsql;

public sealed record OrderSummary(Guid Id, DateTime CreatedAt, decimal Total);

public sealed class OrdersRepository(NpgsqlDataSource dataSource, ILogger<OrdersRepository> logger)
{
    public Task<List<OrderSummary>> FindRecentOrdersAsync(string customerId, int limit = 20) =>
        SlowQueryLog.TimeAsync(logger, "FindRecentOrders", async () =>
        {
            await using var command = dataSource.CreateCommand("""
                SELECT id, created_at, total
                  FROM orders
                 WHERE customer_id = $1
                 ORDER BY created_at DESC
                 LIMIT $2
                """);
            command.Parameters.Add(new NpgsqlParameter { Value = customerId });
            command.Parameters.Add(new NpgsqlParameter { Value = limit });

            var orders = new List<OrderSummary>();
            await using var reader = await command.ExecuteReaderAsync();
            while (await reader.ReadAsync())
            {
                orders.Add(new OrderSummary(reader.GetGuid(0), reader.GetDateTime(1), reader.GetDecimal(2)));
            }
            return orders;
        });

    public Task<int> CreateOrderAsync(string customerId, decimal total) =>
        SlowQueryLog.TimeAsync(logger, "CreateOrder", async () =>
        {
            await using var command = dataSource.CreateCommand(
                "INSERT INTO orders (customer_id, status, total) VALUES ($1, 'pending', $2)");
            command.Parameters.Add(new NpgsqlParameter { Value = customerId });
            command.Parameters.Add(new NpgsqlParameter { Value = total });
            return await command.ExecuteNonQueryAsync();
        });
}
LoggingSlowQueryLog.csEvery query goes through this method. ASP.NET Core adds the trace ID to each log line through the request's logging scope, so the line can be matched to the request. It logs the query name, not the values, because values can hold personal data.
using System.Diagnostics;

public static class SlowQueryLog
{
    private static readonly TimeSpan SlowQueryThreshold = TimeSpan.FromMilliseconds(200);

    public static async Task<T> TimeAsync<T>(ILogger logger, string queryName, Func<Task<T>> runQuery)
    {
        var startedAt = Stopwatch.GetTimestamp();
        var result = await runQuery();
        var elapsed = Stopwatch.GetElapsedTime(startedAt);

        if (elapsed >= SlowQueryThreshold)
        {
            logger.LogWarning("Slow query {QueryName} took {DurationMs} ms", queryName, (long)elapsed.TotalMilliseconds);
        }
        return result;
    }
}

Loggingdb/find-slow-and-unused.sqlThe first query lists the queries with the most total time, which is where an index helps most. The second lists indexes that were never used since statistics were last reset. Unique indexes are left out, because they also prevent duplicates.
SELECT calls,
       round(total_exec_time) AS total_ms,
       round(mean_exec_time::numeric, 1) AS mean_ms,
       rows,
       query
  FROM pg_stat_statements
 ORDER BY total_exec_time DESC
 LIMIT 10;

SELECT stats.relname AS table_name,
       stats.indexrelname AS index_name,
       stats.idx_scan AS times_used,
       pg_size_pretty(pg_relation_size(stats.indexrelid)) AS index_size
  FROM pg_stat_user_indexes AS stats
  JOIN pg_index AS definition ON definition.indexrelid = stats.indexrelid
 WHERE stats.idx_scan = 0
   AND NOT definition.indisunique
 ORDER BY pg_relation_size(stats.indexrelid) DESC;
