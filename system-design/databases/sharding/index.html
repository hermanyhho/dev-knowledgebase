System design / Databases

Sharding and Consistent Hashing

Splitting one table's rows over several database servers, and choosing which server holds which row. Examples use PostgreSQL 18.

What it is

Replication adds servers for reads, but every write still goes to one primary. When writes or data size outgrow one server, the rows are split: each shard is a separate database server that holds part of the rows.

A column, the shard key, decides where a row goes. In a system that serves many companies, the key is usually the tenant ID: all rows of one company are on the same shard, so most queries need only one server.

Consistent hashing is a way to map keys to shards so that adding a shard moves only a small share of the keys. With hash % 4, changing to hash % 5 moves 80% of all keys. With a hash ring it moves 20%.

Main rule: shard last, after indexes, replicas, caching and a larger server. Choose a shard key that almost every query filters on and that spreads load evenly.

Options to try before sharding

ProblemTry first
Slow queriesIndexes that match the queries
Too many readsRead replicas and a cache
Too many writes or too little memoryA larger server. Cloud servers with hundreds of GB of memory are common.

One part of the system writes far more than the restGive that part its own database, as in microservices

Many systems combine two: consistent hashing for most tenants, and a directory that pins very large tenants to their own shard.

How consistent hashing finds a shard

StepWhat happens
1. Place the shardsHash shard-1#0 to shard-1#99, and the same for each shard. Each hash is a position on the ring.
2. Hash the keyhash("t-17") gives a position on the same ring.
3. Walk clockwiseThe first shard position at or after the key's position owns the key. Past the top, wrap around to the start.
4. Add a shardIts 100 new positions each take over the keys just before them. Keys elsewhere keep their shard.

Measured with 100,000 tenant IDs: with 100 virtual nodes each of 5 shards held 19-22% of keys. With 1 position per shard, 4 shards held 22-28% each.

Choosing a shard key

KeyResult
tenant_id in a business appGood. Almost every query is for one tenant, and its rows are together. Very large tenants need their own shard.
user_id in a consumer appGood for a user's own data. Feeds and searches that cross users need another design.
created_atBad. All new writes go to the newest shard while the others are idle.
countryBad. A few countries hold most users, so shards are very uneven.
A key that changesBad. A change moves the row to another shard.

What becomes harder

TaskOn one serverWith shards
A query across all tenantsOne queryOne query per shard, then merge the results in the app. Better: copy the data to an analytics database.
A join between rows on two shardsA JOINTwo queries joined in code. Keep rows that are joined on the same shard.
A transaction across shardsOne transactionNot possible as one transaction. Use a saga.
Unique valuesA unique indexUnique only per shard. Use UUIDs for IDs, and include the shard key in unique constraints.
Schema migrationsRun onceRun on every shard, and handle a shard where it failed.

  2. The router checks the directory of large tenants first. t-17 is not in it.
  3. The router hashes "t-17". The result is a position on the ring, between S1 and S2.
  4. From that position it walks clockwise. The first shard position it meets is S2.
  5. The query goes to shard 2, which holds every row of t-17. Every log line for the query includes shard-2.
  1. The four shards are full. Tenant t-17 is on shard 2, tenant t-9 on shard 4.
  2. A new server, shard 5, gets 100 positions on the ring. One of them, S5, lands between t-17 and S2.
  3. Only keys between S1 and S5 now meet a different shard first. t-17 moves to shard 5. t-9 stays on shard 4.
  4. A rebalancing job copies the rows of moved tenants to shard 5, then switches each tenant's reads and writes. Across all 100 positions, about 20% of tenants move.
  5. With hash % 4 changed to hash % 5, about 80% of tenants would have moved. Click Hash ring to see the program that measures both.
  1. An admin page asks for the total revenue of all tenants last month.
  2. No single shard has the answer, because every shard holds some tenants.
  3. The app sends the same query to all four shards at once and adds up the results.
  4. The page is as slow as the slowest shard, and fails if one shard is down. For reports, copy the data to one analytics database instead.
  1. Tenant t-1 has 40% of all orders. On a shared shard it would make that shard hot.
  2. The router finds t-1 in the directory.
  3. The directory sends t-1 to shard 1, which holds no other tenant. The hash ring is not used for it.
  4. Every other tenant still uses the ring. The directory stays small, so it is cached in memory and reloaded every minute.
  1. Imagine the shard key were the month of created_at, one month per shard.
  2. Every new order belongs to the current month, so every insert goes to shard 4.
  3. Shards 1 to 3 hold old months. They get almost no writes.

Problems it solves

  • Writes that one server cannot handleEach shard takes the writes of its own tenants.
  • Data larger than one serverEach shard holds a part, so disk and memory needs are split.
  • One tenant's load slowing everyoneLarge tenants can get their own shard.
  • Large outagesA failed shard affects only its own tenants.
  • Data residencyShards in different regions can keep each tenant's data in its own country.

Problems it introduces

  • Queries across shardsReports, searches and joins across tenants need one query per shard or a separate analytics copy.
  • No transactions across shardsChanges to two shards need a saga or careful ordering.
  • Moving dataAdding a shard means copying rows while the app runs, then switching without losing writes.
  • A key that is hard to changeChanging the shard key later means moving every row.
  • More to runEvery migration, backup and alert happens once per shard.
Routingsrc/hash-ring.tsEach shard gets 100 positions from hashing shard-name#0 to shard-name#99. MD5 is used because it is fast and spreads values evenly; it is not used for security here. The C# version uses the same hash, so both apps send a tenant to the same shard. A linear search over 500 positions takes microseconds; use a binary search for thousands.
import { createHash } from "node:crypto";

export function hashToRingPosition(value: string): number {
  return createHash("md5").update(value).digest().readUInt32BE(0);
}

type RingPosition = { position: number; shardName: string };

export class HashRing {
  private readonly positions: RingPosition[] = [];

  constructor(shardNames: string[], private readonly virtualNodesPerShard = 100) {
    for (const shardName of shardNames) this.addShard(shardName);
  }

  addShard(shardName: string): void {
    for (let index = 0; index < this.virtualNodesPerShard; index++) {
      this.positions.push({ position: hashToRingPosition(`${shardName}#${index}`), shardName });
    }
    this.positions.sort((first, second) => first.position - second.position);
  }

  shardFor(shardKey: string): string {
    const keyPosition = hashToRingPosition(shardKey);
    const firstClockwise = this.positions.find((entry) => entry.position >= keyPosition);
    return (firstClockwise ?? this.positions[0]).shardName;
  }
}

import { HashRing, hashToRingPosition } from "../src/hash-ring.js";

const tenantIds = Array.from({ length: 100_000 }, (_, index) => `t-${index}`);
const fourShards = new HashRing(["shard-1", "shard-2", "shard-3", "shard-4"]);

const movedWithModulo = tenantIds.filter(
  (tenantId) => hashToRingPosition(tenantId) % 4 !== hashToRingPosition(tenantId) % 5,
);

console.log({
  movedWithRing: movedWithRing.length / tenantIds.length,
  movedWithModulo: movedWithModulo.length / tenantIds.length,
});
Directorysrc/shard-placement.tsThe directory is checked first, then the ring. The directory is a small table, so it is loaded into memory and reloaded every minute instead of being queried on every request.
import type { Pool } from "pg";
import { HashRing } from "./hash-ring.js";

export class ShardPlacement {
  private pinnedTenants = new Map<string, string>();

  constructor(private readonly ring: HashRing, private readonly directoryDatabase: Pool) {}

  async reloadDirectory(): Promise<void> {
    const { rows } = await this.directoryDatabase.query<{ tenant_id: string; shard_name: string }>(
      "SELECT tenant_id, shard_name FROM tenant_shard_directory",
    );
    this.pinnedTenants = new Map(rows.map((row) => [row.tenant_id, row.shard_name]));
  }

  shardFor(tenantId: string): string {
    return this.pinnedTenants.get(tenantId) ?? this.ring.shardFor(tenantId);
  }
}
Appsrc/orders-repository.tsOne connection pool per shard. Every query includes tenant_id, so it touches one shard. The report sends the same query to every shard in parallel and adds the results. Log lines carry the shard name, so a slow shard can be found.
import type { Pool } from "pg";
import type { Logger } from "pino";
import type { ShardPlacement } from "./shard-placement.js";

export class OrdersRepository {
  constructor(private readonly placement: ShardPlacement, private readonly shardPools: Map<string, Pool>) {}

  async findOrders(requestLogger: Logger, tenantId: string) {
    const shardName = this.placement.shardFor(tenantId);
    const startedAt = performance.now();
    const { rows } = await this.shardPools.get(shardName)!.query(
      "SELECT id, total, created_at FROM orders WHERE tenant_id = $1 ORDER BY created_at DESC LIMIT 50",
      [tenantId],
    );
    requestLogger.debug({ shardName, tenantId, durationMs: Math.round(performance.now() - startedAt) }, "orders read");
    return rows;
  }

  async revenueOfAllTenants(requestLogger: Logger, from: Date, to: Date): Promise<number> {
    const startedAt = performance.now();
    const perShard = await Promise.all(
      [...this.shardPools.values()].map((pool) =>
        pool.query<{ revenue: string }>(
          "SELECT coalesce(sum(total), 0) AS revenue FROM orders WHERE created_at >= $1 AND created_at < $2",
          [from, to],
        ),
      ),
    );
    requestLogger.info({ shardCount: perShard.length, durationMs: Math.round(performance.now() - startedAt) }, "query sent to every shard");
    return perShard.reduce((total, result) => total + Number(result.rows[0].revenue), 0);
  }
}
RoutingHashRing.csEach shard gets 100 positions from hashing shard-name#0 to shard-name#99. It uses the same MD5 hash and byte order as the TypeScript version, so both apps send a tenant to the same shard. MD5 is used because it spreads values evenly; it is not used for security here.
using System.Buffers.Binary;
using System.Security.Cryptography;
using System.Text;

public sealed class HashRing
{
    private readonly SortedList<uint, string> positions = new();
    private readonly int virtualNodesPerShard;

    public HashRing(IEnumerable<string> shardNames, int virtualNodesPerShard = 100)
    {
        this.virtualNodesPerShard = virtualNodesPerShard;
        foreach (var shardName in shardNames) AddShard(shardName);
    }

    public void AddShard(string shardName)
    {
        for (var index = 0; index < virtualNodesPerShard; index++)
        {
            positions[HashToRingPosition($"{shardName}#{index}")] = shardName;
        }
    }

    public string ShardFor(string shardKey)
    {
        var keyPosition = HashToRingPosition(shardKey);
        foreach (var (position, shardName) in positions)
        {
            if (position >= keyPosition) return shardName;
        }
        return positions.Values[0];
    }

    public static uint HashToRingPosition(string value) =>
        BinaryPrimitives.ReadUInt32BigEndian(MD5.HashData(Encoding.UTF8.GetBytes(value)));
}

DirectoryShardPlacement.csThe directory is checked first, then the ring. The directory is a small table, so it is loaded into memory and reloaded every minute by a background service instead of being queried on every request.
using System.Collections.Frozen;
using Npgsql;

public sealed class ShardPlacement(HashRing ring, NpgsqlDataSource directoryDatabase)
{
    private FrozenDictionary<string, string> pinnedTenants = FrozenDictionary<string, string>.Empty;

    public async Task ReloadDirectoryAsync()
    {
        var loaded = new Dictionary<string, string>();
        await using var command = directoryDatabase.CreateCommand("SELECT tenant_id, shard_name FROM tenant_shard_directory");
        await using var reader = await command.ExecuteReaderAsync();
        while (await reader.ReadAsync())
        {
            loaded[reader.GetString(0)] = reader.GetString(1);
        }
        pinnedTenants = loaded.ToFrozenDictionary();
    }

    public string ShardFor(string tenantId) =>
        pinnedTenants.TryGetValue(tenantId, out var shardName) ? shardName : ring.ShardFor(tenantId);
}
AppOrdersRepository.csOne data source per shard. Every query includes tenant_id, so it touches one shard. The report sends the same query to every shard in parallel and adds the results. Log lines carry the shard name, so a slow shard can be found.
using System.Diagnostics;
using Npgsql;

public sealed class OrdersRepository(
    ShardPlacement placement,
    IReadOnlyDictionary<string, NpgsqlDataSource> shardDataSources,
    ILogger<OrdersRepository> logger)
{
    public async Task<int> CountOrdersAsync(string tenantId)
    {
        var shardName = placement.ShardFor(tenantId);
        await using var command = shardDataSources[shardName].CreateCommand("SELECT count(*) FROM orders WHERE tenant_id = $1");
        command.Parameters.Add(new NpgsqlParameter { Value = tenantId });
        var orderCount = Convert.ToInt32(await command.ExecuteScalarAsync());
        logger.LogDebug("Orders counted on {ShardName} for {TenantId}", shardName, tenantId);
        return orderCount;
    }

    public async Task<decimal> RevenueOfAllTenantsAsync(DateTimeOffset from, DateTimeOffset to)
    {
        var startedAt = Stopwatch.GetTimestamp();
        var perShard = await Task.WhenAll(shardDataSources.Values.Select(async dataSource =>
        {
            await using var command = dataSource.CreateCommand(
                "SELECT coalesce(sum(total), 0) FROM orders WHERE created_at >= $1 AND created_at < $2");
            command.Parameters.Add(new NpgsqlParameter { Value = from });
            command.Parameters.Add(new NpgsqlParameter { Value = to });
            return (decimal)(await command.ExecuteScalarAsync())!;
        }));
        logger.LogInformation("Query sent to {ShardCount} shards in {DurationMs} ms",
            perShard.Length, (long)Stopwatch.GetElapsedTime(startedAt).TotalMilliseconds);
        return perShard.Sum();
    }
}

Sharddb/shard-schema.sqlEvery shard has the same tables. tenant_id is in the primary key and leads every index, because every query filters on it. IDs are UUIDs, so two shards never create the same ID.
CREATE TABLE orders (
  tenant_id  text NOT NULL,
  id         uuid NOT NULL DEFAULT uuidv7(),
  total      numeric(10, 2) NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (tenant_id, id)
);

CREATE INDEX orders_tenant_created_idx ON orders (tenant_id, created_at);
