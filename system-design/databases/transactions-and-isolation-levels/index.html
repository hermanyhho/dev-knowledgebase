System design / Databases

Transactions and Isolation Levels

How a database keeps a group of changes together, and what two transactions running at the same time can see of each other. Examples use PostgreSQL 18.

What it is

A transaction is a group of statements that the database applies completely or not at all. An order that lowers the stock and inserts the order row must not stop halfway.

Many transactions run at the same moment. The isolation level decides what one transaction sees of the others' changes, and which conflicts the database stops. A higher level stops more conflicts, but returns more errors that your code must retry.

PostgreSQL keeps old versions of each row next to the new ones. A reader sees the versions that were committed when its snapshot was taken, so readers never wait for writers.

Main rule: keep transactions short and never wait for a network call inside one. Read-then-write code needs a lock, a single conditional statement, or a higher isolation level with a retry.

ACID

ACID names the four guarantees a transaction gives.

LetterGuaranteeHow PostgreSQL keeps it

ConsistentEach commit leaves the data valid under the rules in the schema.Constraints such as CHECK (stock >= 0), foreign keys and unique indexes are checked.
IsolatedTransactions running at the same time do not see each other's unfinished work.Snapshots and row locks, at the chosen isolation level.

Problems that concurrent transactions cause

ProblemWhat happensExample
Dirty readA transaction reads a change that another one has not committed yet.A report counts stock 0, then the other transaction rolls back. PostgreSQL never allows this.
Non-repeatable readThe same row, read twice in one transaction, has different values.An invoice reads the price, another transaction changes it, the invoice reads it again.
Phantom readThe same WHERE, run twice, returns new rows.A count of today's orders changes during the report.
Lost updateTwo transactions read a value, both compute a new one, and the second write replaces the first.Two buyers both read stock 1 and both write stock 0. Two orders, one item.
Write skewTwo transactions check a rule across several rows, then each changes a different row. Together they break the rule.Two doctors each go off call, because each saw the other still on call.

Ways to prevent a lost update

MethodHowUse it when
One conditional statementUPDATE products SET stock = stock - 1 WHERE id = $1 AND stock >= 1. Zero rows changed means out of stock.The rule fits in one statement. The simplest and fastest option.

Common mistakes

MistakeWhat goes wrongFix
An HTTP call or a message send inside a transactionLocks are held while the other service is slow. If the transaction rolls back, the call already happened.Call before or after. To send messages, use the outbox.
A transaction left openIt holds locks and stops VACUUM from removing old row versions, so tables grow.Always commit or roll back in a finally block. Set idle_in_transaction_session_timeout.
Locking rows in a different order in different code pathsDeadlocks under load.Lock rows in a fixed order, for example ORDER BY id ... FOR UPDATE.
Using a higher level without a retryUsers see random errors under load.Retry the whole transaction on 40001 and 40P01, 3 attempts with a short random wait.
Retrying only the failed statementThe transaction is already aborted. Every later statement fails.Roll back and run the whole transaction again, including its reads.

Example flow:

Pick a flow and press Play to follow it through the diagram, step by step.

  1. Buyer 1's checkout starts a transaction at the default level, read committed, and reads the stock of product 7: 1.
  2. Buyer 2's checkout does the same at the same moment. It also reads 1.
  3. A's code computes 1 - 1 = 0 and runs UPDATE products SET stock = 0. PostgreSQL writes a new row version and locks the row.
  4. A commits. Stock 0 is now the committed version.
  5. B's code also computes 0 from its earlier read and writes stock 0. Nothing fails. Both orders are saved, but only one item existed.
  6. Fixes: one conditional UPDATE ... WHERE stock >= 1 (click Transaction B), a row lock (next flow), or repeatable read with a retry.
  1. A reads the stock with SELECT stock ... FOR UPDATE. It gets 1 and a lock on the row until it ends.
  2. B runs the same query. The row is locked, so B's query waits.
  3. A writes stock 0, inserts the order and commits. The lock is released.
  4. B's query continues. At read committed it returns the newest committed version: stock 0.
  5. B's code sees 0, rolls back and answers "out of stock". One order, one item.
  1. Both checkouts start repeatable read transactions and read stock 1. Each keeps the snapshot from its first statement.
  2. A writes stock 0 and commits.
  3. B tries to update a row that changed after its snapshot. PostgreSQL stops it: could not serialize access due to concurrent update, SQLSTATE 40001.
  4. B rolls back. The retry code runs the whole transaction again, with a new snapshot.
  5. The second attempt reads stock 0 and answers "out of stock". The retry was logged at warn with the attempt number and SQLSTATE.
  1. A updates product 7 but does not commit yet. The old version stays in the table next to the new one.
  2. B reads the row and gets the last committed version: stock 1. B does not wait for A's lock. Readers do not block writers, and writers do not block readers.
  3. A commits.
  4. B reads again. At read committed each statement takes a new snapshot, so it now sees 0. At repeatable read it would still see 1.
  5. No transaction can see the stock 1 version any more. VACUUM removes it later. A transaction left open keeps old versions from being removed.
  1. A's order has products 7 and 9. B's order has 9 and 7. A locks 7 first, and B locks 9 first.
  2. A asks for product 9 and waits for B.
  3. B asks for product 7 and waits for A. Neither can continue.
  4. After deadlock_timeout (1 s) PostgreSQL looks for a cycle of waits, finds one and cancels one transaction with SQLSTATE 40P01. Here it cancels B.
  5. A gets product 9 and commits. B retries. To prevent it, lock products in a fixed order, for example by id.

Problems it solves

  • Changes that stop halfwayStock is never lowered without the order row, even if the app crashes between the two statements.
  • Concurrent requests overwriting each otherLocks and higher isolation levels stop lost updates and overselling.
  • Reports that see half-finished workA snapshot gives every query a consistent view of committed data.
  • Data lost in a crashA committed change is on disk in the write-ahead log.
  • Readers slowing down writersWith row versions, reads and writes do not wait for each other.

Problems it introduces

  • Waiting for locksA busy row, such as a popular product, makes transactions queue behind each other.
  • Errors you must retryRepeatable read, serializable and deadlocks all return errors that the code must handle.
  • DeadlocksLocks taken in different orders cancel transactions under load.
  • Table growthOld row versions stay until VACUUM removes them, and a long transaction delays that.
  • Only inside one databaseA transaction cannot include a call to another service or a message broker. That needs the outbox or a saga.
Row locksrc/place-order-with-lock.tsAll statements of one transaction must run on the same connection, so the code takes one from the pool. FOR UPDATE locks the product row until COMMIT or ROLLBACK. The finally block returns the connection to the pool, so it is never left inside an open transaction.
import type { Pool } from "pg";

export type OrderResult = "placed" | "out-of-stock";

export async function placeOrderWithLock(database: Pool, customerId: string, productId: number): Promise<OrderResult> {
  const connection = await database.connect();
  try {
    await connection.query("BEGIN");
    const { rows } = await connection.query<{ stock: number }>(
      "SELECT stock FROM products WHERE id = $1 FOR UPDATE",
      [productId],
    );
    if (rows.length === 0 || rows[0].stock < 1) {
      await connection.query("ROLLBACK");
      return "out-of-stock";
    }
    await connection.query("UPDATE products SET stock = stock - 1 WHERE id = $1", [productId]);
    await connection.query("INSERT INTO orders (customer_id, product_id) VALUES ($1, $2)", [customerId, productId]);
    await connection.query("COMMIT");
    return "placed";
  } catch (error) {
    await connection.query("ROLLBACK");
    throw error;
  } finally {
    connection.release();
  }
}

If two of these run at once, the second waits for the first, then checks stock >= 1 again on the new version and changes 0 rows. No explicit lock and no retry are needed. import type { Pool } from "pg";
import type { OrderResult } from "./place-order-with-lock.js";

export async function placeOrderConditional(database: Pool, customerId: string, productId: number): Promise<OrderResult> {
  const connection = await database.connect();
  try {
    await connection.query("BEGIN");
    const stockUpdate = await connection.query(
      "UPDATE products SET stock = stock - 1 WHERE id = $1 AND stock >= 1",
      [productId],
    );
    if (stockUpdate.rowCount === 0) {
      await connection.query("ROLLBACK");
      return "out-of-stock";
    }
    await connection.query("INSERT INTO orders (customer_id, product_id) VALUES ($1, $2)", [customerId, productId]);
    await connection.query("COMMIT");
    return "placed";
  } catch (error) {
    await connection.query("ROLLBACK");
    throw error;
  } finally {
    connection.release();
  }
}
Retrysrc/with-transaction-retry.tsRuns the whole transaction function again on a serialization failure or a deadlock. The random wait spreads out transactions that collided. Each retry is logged at warn with the request ID from the request logger. After the last attempt the error goes to the caller, which logs it once.
import { setTimeout as wait } from "node:timers/promises";
import type { Pool } from "pg";
import type { Logger } from "pino";
import { placeOrderWithLock } from "./place-order-with-lock.js";

const retryableErrorCodes = new Set(["40001", "40P01"]);

export async function withTransactionRetry<Result>(
  requestLogger: Logger,
  operationName: string,
  runTransaction: () => Promise<Result>,
  maxAttempts = 3,
): Promise<Result> {
  for (let attempt = 1; ; attempt++) {
    try {
      return await runTransaction();
    } catch (error) {
      const errorCode = (error as { code?: string }).code;
      const canRetry = errorCode !== undefined && retryableErrorCodes.has(errorCode) && attempt < maxAttempts;
      if (!canRetry) throw error;

      requestLogger.warn({ operationName, attempt, errorCode }, "transaction conflict, retrying");
      await wait(Math.random() * 50 * attempt);
    }
  }
}

export function placeOrderSafely(database: Pool, requestLogger: Logger, customerId: string, productId: number) {
  return withTransactionRetry(requestLogger, "placeOrder", () => placeOrderWithLock(database, customerId, productId));
}
Row lockPlaceOrderWithLock.csThe command uses the transaction's connection. FOR UPDATE locks the product row until commit or rollback. If the method returns or throws before CommitAsync, disposing the transaction rolls it back.
using Npgsql;

public enum OrderResult { Placed, OutOfStock }

public sealed class PlaceOrderWithLock(NpgsqlDataSource dataSource)
{
    public async Task<OrderResult> RunAsync(string customerId, int productId)
    {
        await using var connection = await dataSource.OpenConnectionAsync();
        await using var transaction = await connection.BeginTransactionAsync();

        await using var readStock = new NpgsqlCommand(
            "SELECT stock FROM products WHERE id = $1 FOR UPDATE", connection, transaction);
        readStock.Parameters.Add(new NpgsqlParameter { Value = productId });
        var stock = (int?)await readStock.ExecuteScalarAsync();
        if (stock is null or < 1)
        {
            return OrderResult.OutOfStock;
        }

        await using var lowerStock = new NpgsqlCommand(
            "UPDATE products SET stock = stock - 1 WHERE id = $1", connection, transaction);
        lowerStock.Parameters.Add(new NpgsqlParameter { Value = productId });
        await lowerStock.ExecuteNonQueryAsync();

        await using var insertOrder = new NpgsqlCommand(
            "INSERT INTO orders (customer_id, product_id) VALUES ($1, $2)", connection, transaction);
        insertOrder.Parameters.Add(new NpgsqlParameter { Value = customerId });
        insertOrder.Parameters.Add(new NpgsqlParameter { Value = productId });
        await insertOrder.ExecuteNonQueryAsync();

        await transaction.CommitAsync();
        return OrderResult.Placed;
    }
}

using Npgsql;

public sealed class PlaceOrderConditional(NpgsqlDataSource dataSource)
{
    public async Task<OrderResult> RunAsync(string customerId, int productId)
    {
        await using var connection = await dataSource.OpenConnectionAsync();
        await using var transaction = await connection.BeginTransactionAsync();

        await using var lowerStock = new NpgsqlCommand(
            "UPDATE products SET stock = stock - 1 WHERE id = $1 AND stock >= 1", connection, transaction);
        lowerStock.Parameters.Add(new NpgsqlParameter { Value = productId });
        if (await lowerStock.ExecuteNonQueryAsync() == 0)
        {
            return OrderResult.OutOfStock;
        }

        await using var insertOrder = new NpgsqlCommand(
            "INSERT INTO orders (customer_id, product_id) VALUES ($1, $2)", connection, transaction);
        insertOrder.Parameters.Add(new NpgsqlParameter { Value = customerId });
        insertOrder.Parameters.Add(new NpgsqlParameter { Value = productId });
        await insertOrder.ExecuteNonQueryAsync();

        await transaction.CommitAsync();
        return OrderResult.Placed;
    }
}
RetryTransactionRetry.csRuns the whole transaction function again on a serialization failure or a deadlock. The when filter lets every other error, and the last failed attempt, go to the caller. The random wait spreads out transactions that collided. ASP.NET Core adds the trace ID to each warning through the request's logging scope.
using Npgsql;

public static class TransactionRetry
{
    public static async Task<T> RunAsync<T>(ILogger logger, string operationName, Func<Task<T>> runTransaction, int maxAttempts = 3)
    {
        for (var attempt = 1; ; attempt++)
        {
            try
            {
                return await runTransaction();
            }
            catch (PostgresException exception) when (attempt < maxAttempts && IsRetryable(exception))
            {
                logger.LogWarning("Transaction conflict in {OperationName}, attempt {Attempt}, SQLSTATE {SqlState}, retrying",
                    operationName, attempt, exception.SqlState);
                await Task.Delay(Random.Shared.Next(0, 50 * attempt));
            }
        }
    }

    private static bool IsRetryable(PostgresException exception) =>
        exception.SqlState is PostgresErrorCodes.SerializationFailure or PostgresErrorCodes.DeadlockDetected;
}
Databasedb/row-versions.sqlRun the two sessions in two terminals with psql. xmin is the id of the transaction that created the row version. Session 2 keeps seeing stock 1 until session 1 commits, and it never waits. After the commit, the row has a new ctid: it is a new version in a new place.
CREATE TABLE products (
  id    integer PRIMARY KEY,
  name  text NOT NULL,
  stock integer NOT NULL CHECK (stock >= 0)
);
INSERT INTO products VALUES (7, 'Desk lamp', 1), (9, 'Bulb', 4);

-- session 1
BEGIN;
UPDATE products SET stock = 0 WHERE id = 7;
SELECT xmin, ctid, stock FROM products WHERE id = 7;

-- session 2
SELECT xmin, ctid, stock FROM products WHERE id = 7;

-- session 1
COMMIT;

-- session 2
SELECT xmin, ctid, stock FROM products WHERE id = 7;

  FROM jobs
 WHERE status = 'waiting'
 ORDER BY id
 LIMIT 10
   FOR UPDATE SKIP LOCKED;

SELECT id, stock
  FROM products
 WHERE id = ANY($1)
 ORDER BY id
   FOR UPDATE;

  FROM pg_stat_activity

Loggingdb/long-transactions.sqlLists transactions open for more than a minute, oldest first. idle in transaction means the app started a transaction and is not sending anything: often a missing commit, or a slow call made inside the transaction. application_name shows which service holds it, if each service sets it in its connection string.
SELECT pid,
       application_name,
       state,
       now() - xact_start AS open_for,
       left(query, 80) AS last_query
  FROM pg_stat_activity
 WHERE xact_start < now() - interval '1 minute'
 ORDER BY xact_start;
