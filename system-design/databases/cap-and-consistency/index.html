System design / Databases

CAP and Consistency

What a database with copies on several servers can guarantee when the network between them fails. Examples use Apache Cassandra 5, which lets each query choose.

What it is

When data is copied to several servers, the network between them can fail. Some servers can no longer reach the others, but clients can still reach them. This is a network partition.

A server that cannot reach the others has two options for a request. It can answer with what it has, and its data may be old. Or it can refuse, and the data stays correct. It cannot do both. The CAP theorem states this: during a partition, a system chooses between consistency and availability.

Partitions cannot be prevented, so the real question is what each operation does when one happens. A bank balance should refuse. A product description can show the old version.

Main rule: choose per operation, not per system. Money, stock and unique names need consistency. Feeds, counters, profiles and catalogs can usually accept old data for a few seconds.

Quorums: how many copies must answer

With N copies, a write waits for W copies and a read asks R copies. If W + R > N, every read asks at least one copy that has the newest write.

N = 3Read sees the newest write?Works with one node down?Speed
W = 1, R = 1 (ONE)NoYesFastest
W = 2, R = 2 (QUORUM)YesYesWaits for the second-fastest node
W = 3, R = 1YesReads yes, writes noWrites wait for the slowest node

Consistency models

Between "always the newest" and "eventually equal" there are useful steps. Each one is a guarantee to the user.

ModelGuaranteeExample
LinearizableEvery read sees the latest completed write, from any client.Stock, balances, locks
Read your writesA user always sees their own changes. Others may see them later.Editing your profile
Monotonic readsA user never sees data go back to an older state.A comment that appears does not disappear
CausalIf one change led to another, everyone sees them in that order.A reply never appears before its question
EventualAll copies match once writes stop.Like counts, view counts

Latency without a partition: PACELC

CAP describes partitions only. PACELC adds the normal case: if there is a Partition, choose Availability or Consistency; Else, choose Latency or Consistency. Waiting for other copies makes every request slower, even when the network is fine.

Resolving conflicting writes

If both sides of a partition accepted writes to the same row, the copies disagree when the network returns.

MethodHowRisk
Last write winsKeep the value with the newest timestamp. Cassandra does this per column.The other write is lost. Clocks that differ between servers pick the wrong one.
Keep both, merge in the appStore both versions and let code or the user merge them.More code. Used for shopping carts: merge both carts.
CRDTsData types whose copies always merge to the same result, such as counters and sets.Only for data that fits those types
Avoid the conflictMake operations that must not conflict consistent, for example with a lightweight transaction.Unavailable on the cut-off side

Diagram

Example flow:

Pick a flow and press Play to follow it through the diagram, step by step.

  1. Client A changes the user's name from Ann to Anna, at consistency level QUORUM. Node 1 receives the write and coordinates it.
  2. Node 1 writes its own copy and sends the write to node 2 and node 3.
  3. Node 2 confirms. That is 2 of 3 copies, a quorum, so Client A gets success. Node 3 confirms a moment later.
  4. Client B reads at QUORUM. Node 3 asks itself and node 2. Two copies out of three always include one with the newest write.
  5. Client B gets "Anna". If the two copies had disagreed, the one with the newer timestamp would win.
  1. The link between the zones fails. Node 3 and client B can still talk to each other, but not to zone 1.
  2. Client B changes a name at QUORUM. Node 3 needs 2 of 3 copies, but it can reach only itself.
  3. Node 3 refuses at once with UnavailableException: 2 replicas required, 1 alive. The data stays correct, and the user in zone 2 gets an error.
  4. In zone 1, nodes 1 and 2 are a majority. Client A's writes at QUORUM still succeed.
  5. Client B logs a warning with the consistency level, required and alive replicas, and the request ID. Monitoring shows the zone is cut off.
  1. The link fails right after Client A changed the name to Anna. Node 3 did not get that write.
  2. Client B reads the profile. QUORUM fails, so its code falls back to ONE, which only needs node 3.
  3. Node 3 answers with its copy: "Ann". The page works, but shows old data.
  4. If client B also writes at ONE, for example "Annie", node 3 accepts it. Now the zones hold different values.
  5. Each fallback is logged and counted, so you know how many users saw old data during the split.
  1. During the split, node 1 could not deliver Anna to node 3. It stored the write as a hint, for up to 3 hours.
  2. The link comes back. Node 1 sends its hints to node 3.
  3. Node 3 compares timestamps. Annie was written during the split, after Anna, so node 3 keeps Annie.
  4. Node 3 sends its own hint for Annie to zone 1, and a scheduled nodetool repair fixes any copies still different. All copies now hold Annie.
  5. Client A was told that Anna was saved, and it is gone without an error. With last write wins this is the expected result. If that is not acceptable, the operation must choose consistency.
  1. Two users try to take the username "anna" at the same moment. Last write wins would let both succeed.
  2. Client A sends INSERT ... IF NOT EXISTS, a lightweight transaction. The nodes agree on it with Paxos rounds that need a majority.
  3. The first insert gets [applied] = true. The second sees the existing row and gets false.
  4. During a split, the same insert from zone 2 fails, because node 3 has no majority. The username stays unique. This operation chose consistency.

What choosing availability gives

  • Pages that keep workingUsers in a cut-off zone still read and write.
  • Lower latencyA request waits for the nearest copy only.
  • Writes in every regionEach region accepts writes without a round trip to another one.

What choosing consistency gives

  • No old dataEvery read sees the newest write.
  • No conflicts to mergeUnique names, stock and balances stay correct.
  • Simpler codeThe app can treat the data as one copy.

What choosing availability costs

  • Old readsUsers can see data that already changed, or that goes back in time.
  • Lost or conflicting writesLast write wins silently drops one of two writes.
  • Repair workHints, read repair and scheduled repairs must run, or copies drift apart.

What choosing consistency costs

  • Errors during a partitionThe cut-off side refuses requests.
  • Higher latencyEvery request waits for a majority, which may be in another zone.
  • Fewer copies allowed to failWith 3 copies, losing 2 stops writes.
Clientsrc/profile-writes.tsThe name change uses QUORUM: it succeeds only when 2 of 3 copies have it. The username uses IF NOT EXISTS, a lightweight transaction, so two users cannot take the same name even if both requests arrive at once. The [applied] column says whether the insert happened.
import cassandra from "cassandra-driver";

const { types } = cassandra;

export async function updateDisplayName(client: cassandra.Client, userId: string, displayName: string): Promise<void> {
  await client.execute(
    "UPDATE users SET display_name = ? WHERE user_id = ?",
    [displayName, userId],
    { prepare: true, consistency: types.consistencies.quorum },
  );
}

export async function reserveUsername(client: cassandra.Client, username: string, userId: string): Promise<boolean> {
  const result = await client.execute(
    "INSERT INTO usernames (username, user_id) VALUES (?, ?) IF NOT EXISTS",
    [username, userId],
    { prepare: true, consistency: types.consistencies.quorum, serialConsistency: types.consistencies.serial },
  );
  return result.first().get("[applied]") === true;
}
Clientsrc/profile-reads.tsThis operation chooses availability. It reads at QUORUM, and only if not enough replicas are alive does it read at ONE, which may return old data. Every fallback is logged at warn with the request ID from the request logger, and counted. Other errors are not caught here.
import cassandra from "cassandra-driver";
import type { Logger } from "pino";

const { types, errors } = cassandra;

function readDisplayName(client: cassandra.Client, userId: string, consistency: number) {
  return client.execute("SELECT display_name FROM users WHERE user_id = ?", [userId], { prepare: true, consistency });
}

function isNotEnoughReplicas(error: unknown): error is cassandra.errors.ResponseError {
  return error instanceof errors.ResponseError && error.code === types.responseErrorCodes.unavailableException;
}

export async function getDisplayName(client: cassandra.Client, requestLogger: Logger, userId: string): Promise<string | undefined> {
  try {
    const result = await readDisplayName(client, userId, types.consistencies.quorum);
    return result.first()?.get("display_name");
  } catch (error) {
    if (!isNotEnoughReplicas(error)) throw error;

    const { required, alive } = error as unknown as { required: number; alive: number };
    requestLogger.warn({ operation: "getDisplayName", consistency: "QUORUM", required, alive }, "not enough replicas, reading at ONE");
    const result = await readDisplayName(client, userId, types.consistencies.one);
    return result.first()?.get("display_name");
  }
}
ClientProfileWrites.csThe name change uses Quorum: it succeeds only when 2 of 3 copies have it. The username uses IF NOT EXISTS, a lightweight transaction, so two users cannot take the same name even if both requests arrive at once. The [applied] column says whether the insert happened.
using Cassandra;

public sealed class ProfileWrites(ISession session)
{
    public async Task UpdateDisplayNameAsync(string userId, string displayName)
    {
        var statement = new SimpleStatement("UPDATE users SET display_name = ? WHERE user_id = ?", displayName, userId)
            .SetConsistencyLevel(ConsistencyLevel.Quorum);
        await session.ExecuteAsync(statement);
    }

    public async Task<bool> ReserveUsernameAsync(string username, string userId)
    {
        var statement = new SimpleStatement("INSERT INTO usernames (username, user_id) VALUES (?, ?) IF NOT EXISTS", username, userId)
            .SetConsistencyLevel(ConsistencyLevel.Quorum)
            .SetSerialConsistencyLevel(ConsistencyLevel.Serial);
        var result = await session.ExecuteAsync(statement);
        return result.First().GetValue<bool>("[applied]");
    }
}
ClientProfileReads.csThis operation chooses availability. It reads at Quorum, and only if not enough replicas are alive does it read at One, which may return old data. The when filter lets every other error through. ASP.NET Core adds the trace ID to the warning through the request's logging scope.
using Cassandra;

public sealed class ProfileReads(ISession session, ILogger<ProfileReads> logger)
{
    public async Task<string?> GetDisplayNameAsync(string userId)
    {
        try
        {
            return await ReadDisplayNameAsync(userId, ConsistencyLevel.Quorum);
        }
        catch (UnavailableException exception)
        {
            logger.LogWarning("Not enough replicas for {Operation} at {Consistency}: {Required} required, {Alive} alive. Reading at One",
                "GetDisplayName", exception.Consistency, exception.RequiredReplicas, exception.AliveReplicas);
            return await ReadDisplayNameAsync(userId, ConsistencyLevel.One);
        }
    }

    private async Task<string?> ReadDisplayNameAsync(string userId, ConsistencyLevel consistency)
    {
        var statement = new SimpleStatement("SELECT display_name FROM users WHERE user_id = ?", userId)
            .SetConsistencyLevel(consistency);
        var rows = await session.ExecuteAsync(statement);
        return rows.FirstOrDefault()?.GetValue<string>("display_name");
    }
}

CONSISTENCY QUORUM;

During a split, each side sees the other side as down. nodetool repair compares the copies of each table and fixes differences. Run it on each node, with -pr, at least once within gc_grace_seconds, or deleted rows can come back.
