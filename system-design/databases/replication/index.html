System design / Databases

Database Replication

Keeping copies of a database on other servers, to spread reads and to survive the loss of a server. Examples use PostgreSQL 18.

What it is

One server, the primary, accepts all writes. Every change it makes is written to its write-ahead log (WAL). The primary sends that log to one or more replicas, which apply the same changes in the same order. Each replica becomes a copy of the primary, a moment later.

Replicas answer read queries, so reads are spread over several servers. If the primary fails, a replica is promoted and becomes the new primary.

The cost is time: a replica is behind the primary by some milliseconds, or by seconds under load. A read from a replica can return data that was already changed on the primary.

Main rule: send writes, and reads that must see those writes, to the primary. Send reads that can be a few seconds old to replicas. Measure the lag and alert on it.

What happens during a failover

StepWhat happensTypical time
1. DetectA failover manager, such as Patroni or the cloud service, sees that the primary stopped answering health checks.10-30 s
2. ChooseIt picks the replica with the most WAL applied. A synchronous replica has every commit.Under 1 s
3. FenceIt makes sure the old primary cannot accept writes, for example by stopping it. Two primaries at once would split the data.Under 1 s
4. PromoteThe replica stops applying WAL and starts accepting writes.A few seconds
5. RedirectThe database's DNS name or proxy now points to the new primary. Apps reconnect.Seconds, depending on DNS caching

During these steps writes fail. The app must retry them, or return an error the client can retry. Managed services such as Amazon RDS, Azure Database for PostgreSQL and Cloud SQL run all five steps for you.

Problems it solves

  • One server cannot handle all readsEach replica adds read capacity. Most apps read far more than they write.
  • Losing the only database serverA replica is promoted in seconds or minutes, instead of restoring a backup for hours.
  • Losing committed dataA synchronous replica holds every commit on a second server.
  • Reports slowing down the appHeavy analytics queries run on their own replica.
  • Users far from the databaseA replica in another region answers reads close to those users.

Problems it introduces

  • Old data on replicasEvery read from a replica can be behind. The code must decide which reads can accept that.
  • Writes do not scaleAll writes still go to one primary. Spreading writes needs sharding.
  • Slower commitsA synchronous replica adds a network round trip to every commit.
  • Failover is hard to get rightDetection, fencing and redirecting must all work, or two primaries can accept writes at once.
  • More servers to runEach replica costs the same as the primary and needs monitoring.
Routingsrc/database-pools.tsTwo connection pools. DATABASE_PRIMARY_URL points to the primary's DNS name, which follows a failover. DATABASE_REPLICA_URL points to a reader endpoint that spreads connections over the replicas; managed services provide one. The pg package has no built-in read/write routing, so the code picks the pool.
import { Pool } from "pg";

export type DatabasePools = { primary: Pool; replica: Pool };

export function createDatabasePools(): DatabasePools {
  return {
    primary: new Pool({ connectionString: process.env.DATABASE_PRIMARY_URL, max: 20 }),
    replica: new Pool({ connectionString: process.env.DATABASE_REPLICA_URL, max: 40 }),
  };
}
Appsrc/profile-service.tsAfter a user writes, their reads go to the primary for 5 seconds, which is longer than the normal lag. lastWriteAt is stored in the user's session, so it works on every API instance. Reads by other users still go to replicas.
import type { Pool } from "pg";
import type { DatabasePools } from "./database-pools.js";

const readFromPrimaryAfterWriteMs = 5_000;

export type UserSession = { userId: string; lastWriteAt?: number };

function poolForReading(databases: DatabasePools, session: UserSession): Pool {
  const wroteRecently = Date.now() - (session.lastWriteAt ?? 0) < readFromPrimaryAfterWriteMs;
  return wroteRecently ? databases.primary : databases.replica;
}

export async function updateDisplayName(databases: DatabasePools, session: UserSession, displayName: string): Promise<void> {
  await databases.primary.query("UPDATE profiles SET display_name = $1 WHERE user_id = $2", [displayName, session.userId]);
  session.lastWriteAt = Date.now();
}

export async function getProfile(databases: DatabasePools, session: UserSession, userId: string) {
  const { rows } = await poolForReading(databases, session).query(
    "SELECT user_id, display_name FROM profiles WHERE user_id = $1",
    [userId],
  );
  return rows[0];
}
RoutingDatabaseSetup.csNpgsql connects to several hosts and asks each whether it is a primary or a standby. Primary always finds the current primary, also after a failover. PreferStandby uses a replica and falls back to the primary if none is up. Load Balance Hosts spreads connections over the replicas. Example connection string: Host=db-1,db-2,db-3;Database=profiles;Username=profile_api;Load Balance Hosts=true.
using Npgsql;

public static class DatabaseSetup
{
    public static void AddDatabases(this IServiceCollection services, string connectionString)
    {
        var allHosts = new NpgsqlDataSourceBuilder(connectionString).BuildMultiHost();

        services.AddKeyedSingleton<NpgsqlDataSource>("primary",
            allHosts.WithTargetSession(TargetSessionAttributes.Primary));
        services.AddKeyedSingleton<NpgsqlDataSource>("replica",
            allHosts.WithTargetSession(TargetSessionAttributes.PreferStandby));
    }
}
AppProfileService.csAfter a user writes, their reads go to the primary for 5 seconds, which is longer than the normal lag. LastWriteAt is stored in the user's session, so it works on every API instance. Reads by other users still go to replicas.
using Npgsql;

public sealed class UserSession
{
    public required string UserId { get; init; }
    public DateTimeOffset? LastWriteAt { get; set; }
}

public sealed class ProfileService(
    [FromKeyedServices("primary")] NpgsqlDataSource primary,
    [FromKeyedServices("replica")] NpgsqlDataSource replica)
{
    private static readonly TimeSpan ReadFromPrimaryAfterWrite = TimeSpan.FromSeconds(5);

    public async Task UpdateDisplayNameAsync(UserSession session, string displayName)
    {
        await using var command = primary.CreateCommand("UPDATE profiles SET display_name = $1 WHERE user_id = $2");
        command.Parameters.Add(new NpgsqlParameter { Value = displayName });
        command.Parameters.Add(new NpgsqlParameter { Value = session.UserId });
        await command.ExecuteNonQueryAsync();
        session.LastWriteAt = DateTimeOffset.UtcNow;
    }

    public async Task<string?> GetDisplayNameAsync(UserSession session, string userId)
    {
        await using var command = DataSourceForReading(session)
            .CreateCommand("SELECT display_name FROM profiles WHERE user_id = $1");
        command.Parameters.Add(new NpgsqlParameter { Value = userId });
        return (string?)await command.ExecuteScalarAsync();
    }

    private NpgsqlDataSource DataSourceForReading(UserSession session) =>
        DateTimeOffset.UtcNow - session.LastWriteAt < ReadFromPrimaryAfterWrite ? primary : replica;
}
Primarydb/primary.confANY 1 (replica_a, replica_c) makes a commit wait for whichever of the two confirms first, so one replica can be down. max_slot_wal_keep_size limits how much WAL a lost replica can hold on the primary's disk. A single unimportant write can skip the wait with SET LOCAL synchronous_commit = local.
wal_level = replica
max_wal_senders = 10
max_replication_slots = 10
max_slot_wal_keep_size = 50GB

synchronous_standby_names = 'ANY 1 (replica_a, replica_c)'
synchronous_commit = on
Replicascripts/create-replica.shpg_basebackup copies the primary's data folder over the network. -R writes the connection settings and the file that makes the server start as a replica. -C -S replica_a creates a replication slot, so the primary keeps the WAL this replica still needs. The application_name must match the name in synchronous_standby_names.
pg_basebackup \
  --host=db-1 \
  --username=replicator \
  --pgdata=/var/lib/postgresql/data \
  --wal-method=stream \
  -R -C -S replica_a \
  --progress

Replicadb/replica-checks.sqlThe first query runs on a replica and shows how old its newest applied change is. If the primary has no writes for a while, this number grows even though the replica is up to date. The last two queries are the exact way to read your own write: after the write, read the primary's LSN, then wait until the replica has replayed that far.
SELECT pg_is_in_recovery() AS is_replica,
       now() - pg_last_xact_replay_timestamp() AS behind_by;

SELECT pg_current_wal_lsn() AS write_position;

SELECT pg_last_wal_replay_lsn() >= $1::pg_lsn AS has_the_write;
Failoverdb/failover.sqlWhat a failover manager runs. On the chosen replica, pg_promote ends replication and waits up to 60 seconds for the server to accept writes. Never promote while the old primary can still accept writes: stop it first. Patroni and managed services do these steps and the DNS change for you.
SELECT pg_is_in_recovery();

SELECT pg_last_wal_replay_lsn();

SELECT pg_promote(wait => true, wait_seconds => 60);

SELECT pg_is_in_recovery();
Monitoringdb/replication-monitoring.sqlRun on the primary. The first query shows each connected replica, whether it is synchronous, and its lag. The second shows how much WAL each replication slot holds. An inactive slot with growing WAL means a replica is gone: drop the slot or the disk fills up.
SELECT application_name,
       client_addr,
       state,
       sync_state,
       write_lag,
       flush_lag,
       replay_lag
  FROM pg_stat_replication;

SELECT slot_name,
       active,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS wal_held
  FROM pg_replication_slots;
