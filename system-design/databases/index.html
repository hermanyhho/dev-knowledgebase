System design / Databases

Databases Overview

The five ideas that decide how a database stays fast and correct as data and traffic grow. Each has its own detail page.

What it is

A single database server is enough for most apps for a long time. Problems appear in a fixed order as the app grows: queries get slow, users change the same rows at once, one server gets too many reads, then too many writes, and finally copies on several servers can disagree.

Each problem has a standard answer with its own cost. This page gives the key idea of each. The detail pages show how it works step by step, with code.

TopicProblem it answersKey ideaCost
IndexesA query reads the whole tableA sorted copy of chosen columns finds rows in a few page readsEvery write also updates every index
Transactions and isolation levelsTwo requests change the same data at onceA transaction applies all its changes or none. The isolation level decides what it sees of others.Locks, waits and errors to retry
ReplicationToo many reads, or one server failingCopies of the database receive every change and answer readsReplicas can be a few seconds behind
ShardingToo many writes or too much data for one serverRows are split over several servers by a key, such as the tenant IDQueries across shards and transactions across shards become hard
CAP and consistencyCopies cannot reach each otherDuring a network split, a request must choose: answer with possibly old data, or refuseOld data, or errors
Main rule: solve the problem you have, in this order: indexes, a larger server and a cache, read replicas, then sharding. Each step adds cost that the earlier steps do not have.

Key terms

TermMeaning
IndexA separate sorted structure, usually a B-tree, that points to rows.
TransactionStatements between BEGIN and COMMIT that succeed or fail together.
Isolation levelHow much one transaction sees of others running at the same time: read committed, repeatable read, serializable.
Primary and replicaThe primary takes all writes; replicas receive its changes and answer reads.
Replication lagHow far a replica is behind the primary.
Shard and shard keyA server holding part of the rows, and the column that decides which part.
Network partitionRunning servers that cannot reach each other.

Problems these ideas solve

  • Slow queriesIndexes turn full table scans into a few page reads.
  • Wrong data from concurrent requestsTransactions and isolation levels keep changes complete and separate.
  • One server is not enoughReplicas spread reads; shards spread writes and data.
  • A server failsA replica is promoted instead of restoring a backup.

Problems they introduce

  • Slower writesIndexes and synchronous replicas add work to every write.
  • Old dataReplicas and available-first systems can return data that already changed.
  • Errors to handleIsolation conflicts, deadlocks and consistency failures need retries.
  • More to runEvery replica and shard is another server to monitor, back up and migrate.
Indexesindexes.sqlThe index matches the query: equality on customer_id, then sorting by created_at. CONCURRENTLY lets writes continue while it builds. EXPLAIN shows whether the planner uses it.
CREATE INDEX CONCURRENTLY orders_customer_created_idx
    ON orders (customer_id, created_at);

EXPLAIN (ANALYZE)
SELECT id, total FROM orders
 WHERE customer_id = 'c-042'
 ORDER BY created_at DESC
 LIMIT 20;
Transactionsplace-order.sqlBoth statements commit together or not at all. The WHERE stock >= 1 check and the change happen in one statement, so two buyers cannot both take the last item.
BEGIN;

UPDATE products SET stock = stock - 1
 WHERE id = 7 AND stock >= 1;

INSERT INTO orders (customer_id, product_id) VALUES ('c-042', 7);

COMMIT;
Replicationreplication-lag.sqlRun on the primary. Each row is a connected replica, with how far behind it is. Reads that must see a user's own latest write go to the primary instead.
SELECT application_name, sync_state, replay_lag
  FROM pg_stat_replication;
Shardingshard-schema.sqlThe same table exists on every shard. tenant_id is the shard key: it leads the primary key and every query filters on it, so most queries touch one shard.
CREATE TABLE orders (
  tenant_id  text NOT NULL,
  id         uuid NOT NULL DEFAULT uuidv7(),
  total      numeric(10, 2) NOT NULL,
  PRIMARY KEY (tenant_id, id)
);
CAPconsistency-levels.cqlCassandra lets each query choose. QUORUM needs 2 of 3 copies and fails when it cannot reach them: consistent. ONE answers from any copy, which may be old: available.
CONSISTENCY QUORUM;
SELECT display_name FROM profiles.users WHERE user_id = 'u-42';

CONSISTENCY ONE;
SELECT display_name FROM profiles.users WHERE user_id = 'u-42';
