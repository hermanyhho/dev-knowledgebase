Generics and Utility Types

Writing a function or type once for many types, and building new types from existing ones.

What it is

A generic function has a type parameter, written in angle brackets: findById<T>(items: T[], id: string): T | undefined. When you call it with a list of orders, the compiler sets T to Order, and the result is Order | undefined. The same function works for customers, products or anything else, and the link between what goes in and what comes out is kept.

A constraint limits what T can be. T extends { id: string } means: any type, as long as it has a string id. Inside the function you can then read item.id.

Utility types are generic types that ship with TypeScript and build a new type from another. Omit<Order, "id"> is an order without its ID, which is what a create request contains. Deriving types this way keeps them in step when Order changes.

Main rule: use a type parameter only when the output type depends on the input type. Derive related types from one source type instead of writing them again.

How the built-in types are written

Utility types are ordinary TypeScript, defined in lib.es5.d.ts. Reading them explains mapped and conditional types.

Diagram

Example flow:

Pick a flow and press Play to follow it through the diagram, step by step.

  1. You call findById(orders, "o-1"), where orders is an Order[]. You do not write a type argument.
  2. The parameter is items: T[] and the argument is Order[], so the compiler infers T = Order.
  3. It checks the constraint: Order has id: string, so it fits { id: string }.
  4. The return type T | undefined becomes Order | undefined. The caller must check for undefined, then has a full Order.
  1. Someone calls findById([10, 20], "o-1").
  2. The compiler tries T from the list of numbers.
  3. A number has no id. The call fails: TS2322: Type 'number' is not assignable to type '{ id: string; }'.
  4. Without the constraint, item.id inside the function would not compile, because T could be anything.
  1. You add currency: string to Order.
  2. NewOrder is Order minus two fields, so it now requires currency too. Every place that creates an order without one fails to compile.
  3. OrderPatch picks only status and total, so it does not change. Patching the currency is not allowed until you add it there.
  4. If the request types had been written out by hand, they would have missed the new field without any error.
  1. The status union gets a third member: "shipped".
  2. statusLabels has the type Record<OrderStatus, string>: it must have a property for every status.
  3. It has labels for pending and paid only. The compiler reports TS2741: Property 'shipped' is missing.
  4. You add the label. A plain object type such as { [status: string]: string } would not have noticed.
  1. loadOrders is an async function. Its return type is inferred, and nobody wrote it down.
  2. ReturnType<typeof loadOrders> gives Promise<Order[]>. Awaited removes the promise: Order[].
  3. A cache or a test can now use LoadedOrders, and it follows any change to loadOrders.
  4. The same file shows withTiming<T>: a generic wrapper that logs the duration of any async operation and returns its result with the original type.

orders-api/

Problems it solves

  • The same code for each typeOne generic function or class replaces copies for orders, customers and products.
  • Losing the type through a helperA generic helper returns the same type it received, instead of any.
  • Types that drift apartRequest, patch and summary types derived from one source change with it.
  • Incomplete mapsRecord over a union fails the build when a key is missing.

Problems it introduces

  • Harder to readSignatures with several type parameters and constraints take time to understand.
  • Long error messagesErrors inside derived and conditional types can span many lines.
  • False safetyA generic return type the caller picks, such as parse<T>(), checks nothing.
  • Nothing at runtimeCode cannot read T, so it cannot create or check a T by itself.

Generic functionsrc/find-by-id.tsT appears in the parameter and in the return type, which is why it is generic: the result has the same type as the list items. The constraint makes item.id allowed.
import type { Order } from "./order.js";

export function findById<T extends { id: string }>(items: T[], id: string): T | undefined {
  return items.find((item) => item.id === id);
}

declare const orders: Order[];

const order = findById(orders, "o-1");
if (order) {
  console.log(order.status, order.total);
}

K extends keyof T allows only real property names, so a typo such as "totl" fails with TS2345: Argument of type '"totl"' is not assignable to parameter of type '"id" | "total"'. The return type T[K] is the type of that property.

findById([10, 20], "o-1");

function getProperty<T, K extends keyof T>(object: T, key: K): T[K] {
  return object[key];
}

const order = { id: "o-1", total: 10 };
const total = getProperty(order, "total");
const typo = getProperty(order, "totl");

Derivedsrc/how-utility-types-are-written.tsCopies of the built-in definitions, with a My prefix so they do not clash. A mapped type goes over property names with in keyof. A conditional type tests with extends, and infer captures a part of the type being tested.
type MyPartial<T> = { [P in keyof T]?: T[P] };

type MyReadonly<T> = { readonly [P in keyof T]: T[P] };

type MyPick<T, K extends keyof T> = { [P in K]: T[P] };

type MyRecord<K extends keyof any, V> = { [P in K]: V };

type MyExclude<T, U> = T extends U ? never : T;

type MyOmit<T, K extends keyof any> = MyPick<T, MyExclude<keyof T, K>>;

type MyReturnType<T extends (...args: any) => any> = T extends (...args: any) => infer R ? R : any;
Derivedsrc/status-labels.tsRecord<OrderStatus, string> requires one property per status. With "shipped" in the union and no label for it, the build fails with TS2741: Property 'shipped' is missing in type '{ pending: string; paid: string; }' but required in type 'Record<OrderStatus, string>'.

Derivedsrc/with-timing.tsLoadedOrders follows the return type of loadOrders. withTiming works for any async operation and returns the same T it received. It logs the name, duration and outcome with the request logger, which carries the request ID. It does not log the result, because it cannot know what T contains. It rethrows errors without logging them, so the caller that handles the error logs it once.
import type { Logger } from "pino";
import type { Order } from "./order.js";

export async function loadOrders(customerId: string): Promise<Order[]> {
  return [];
}

export type LoadedOrders = Awaited<ReturnType<typeof loadOrders>>;

export async function withTiming<T>(requestLogger: Logger, operationName: string, operation: () => Promise<T>): Promise<T> {
  const startedAt = performance.now();
  try {
    const result = await operation();
    requestLogger.debug({ operationName, durationMs: Math.round(performance.now() - startedAt) }, "operation finished");
    return result;
  } catch (error) {
    requestLogger.debug({ operationName, durationMs: Math.round(performance.now() - startedAt), outcome: "failed" }, "operation finished");
    throw error;
  }
}

declare const requestLogger: Logger;
const orders = await withTiming(requestLogger, "loadOrders", () => loadOrders("c-42"));
