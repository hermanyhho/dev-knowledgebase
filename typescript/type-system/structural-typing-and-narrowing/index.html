Structural Typing and Narrowing

TypeScript compares types by their shape, and makes a type more specific after each check in your code.

What it is

Structural typing: a value fits a type if it has the properties the type needs, with the right types. The name of the type does not matter. Any object with id and total fits Order, even one created for something else. C# works the other way: a class fits only if it is declared as that class or inherits from it.

Narrowing: a variable can have a type with several options, such as string | undefined. After a check such as if (name !== undefined), the compiler knows which option is left, and allows only the properties of that option inside the if.

Together they give the most useful pattern in TypeScript: describe each state as its own object type with a status property, combine them in a union, and let a switch on status narrow to the right one.

Main rule: model each state as one member of a discriminated union, narrow it with a switch on the shared property, and end the switch with a never check so a new state fails the build.

Diagram

Example flow:

Pick a flow and press Play to follow it through the diagram, step by step.

  1. The payment provider answers with JSON. Its type is unknown until it is checked.
  2. The schema checks it and returns a PaymentResult: one of three object types, each with a different status.
  3. Before the switch, only status can be read. result.reason does not compile, because two of the three members have no reason.
  4. Inside case "declined", the compiler has narrowed result to the declined member. result.reason is a plain string.
  5. Writing result.receiptUrl there fails with TS2339: Property 'receiptUrl' does not exist on type '{ status: "declined"; reason: string; }'.
  1. The provider adds a fourth status, refunded. You add it to the schema, so PaymentResult now has four members.
  2. The switch still handles three. The fourth falls through to default.
  3. In default, result should be never, but it is the refunded member. assertNever(result) fails: TS2345: Argument of type '{ status: "refunded"; ... }' is not assignable to parameter of type 'never'.
  4. The build lists every switch that must handle refunds. After you add the case, default is never again.
  1. A form gives { id, total, couponCode }. saveOrder expects Order = { id, total }.
  2. Passing the form object in a variable compiles: it has every property Order needs. The extra couponCode goes along at runtime.
  3. Writing the same object as a literal inside the call fails with TS2353: Object literal may only specify known properties. A new literal with extra properties is most likely a typo.
  4. If saveOrder writes the whole object to a database or response, the extra field goes too. Copy the fields you need.
  1. cancelOrder(orderId: string, customerId: string) is called as cancelOrder(customerId, orderId). Both are strings, so it compiles.
  2. With branded types, OrderId is string & { __brand: "OrderId" }. The brand exists only in the type: at runtime the value is a plain string.
  3. The swapped call now fails with TS2345: Argument of type 'CustomerId' is not assignable to parameter of type 'OrderId'.
  4. A branded value is created in one place, for example a function that checks the format and returns OrderId.
  1. A hand-written guard isPaymentResult(value): value is PaymentResult only checks that value has a status property.
  2. When it returns true, the compiler treats the value as a PaymentResult. It does not read the guard's body.
  3. { status: "weird" } passes the guard, and a later switch reaches the never branch at runtime.
  4. Let the schema decide instead: PaymentResultSchema.safeParse(value).success checks every field, and the type comes from the same schema.

Problems it solves

  • Impossible statesA discriminated union cannot hold a succeeded payment with a decline reason.
  • Forgotten casesA never check turns a new state into a build error at every place that must handle it.
  • Checks repeated everywhereAfter one check, the compiler knows the narrower type for the rest of the block.
  • Plain JavaScript objectsStructural typing fits JSON and object literals, which have no class.

Problems it introduces

  • Accidental matchesAny value with the right shape fits, including the wrong kind of ID.
  • Extra properties travel alongObjects can carry fields the type does not mention into databases and responses.
  • Trusted claimsType guards, as and assertion functions are not checked by the compiler.
  • Narrowing is lost in callbacksA let variable narrowed outside a callback is wide again inside it, because it could change.
Schemasrc/payment-result-schema.tsz.discriminatedUnion reads status first and checks only the matching member, so error messages name the right fields. The type comes from the schema. A status the schema does not know fails here, and is logged at error with the provider's value.
import { z } from "zod";
import type { Logger } from "pino";

export const PaymentResultSchema = z.discriminatedUnion("status", [
  z.object({ status: z.literal("succeeded"), paymentId: z.string(), receiptUrl: z.url() }),
  z.object({ status: z.literal("declined"), paymentId: z.string(), reason: z.string() }),
  z.object({ status: z.literal("requires_action"), paymentId: z.string(), redirectUrl: z.url() }),
]);

export type PaymentResult = z.infer<typeof PaymentResultSchema>;

export function parsePaymentResult(responseBody: unknown, requestLogger: Logger): PaymentResult {
  const result = PaymentResultSchema.safeParse(responseBody);
  if (!result.success) {
    const status = (responseBody as { status?: unknown } | null)?.status;
    requestLogger.error({ provider: "card-provider", status, issues: result.error.issues.length }, "unexpected payment result");
    throw new Error("The payment provider returned an unexpected result.");
  }
  return result.data;
}

Narrowingsrc/handle-payment-result.tsIn each case, result has the type of one member, so only that member's fields compile. assertNever accepts only never: if a member is not handled, the call does not compile. If unchecked data reaches it at runtime, it throws. Logs include the status and payment ID, not the whole object.
import type { Logger } from "pino";
import type { PaymentResult } from "./payment-result-schema.js";

export function assertNever(value: never): never {
  throw new Error(`Unexpected value: ${JSON.stringify(value)}`);
}

export type NextStep =
  | { kind: "show-receipt"; url: string }
  | { kind: "show-error"; message: string }
  | { kind: "redirect"; url: string };

export function nextStepFor(result: PaymentResult, requestLogger: Logger): NextStep {
  requestLogger.info({ paymentId: result.paymentId, status: result.status }, "payment result received");

  switch (result.status) {
    case "succeeded":
      return { kind: "show-receipt", url: result.receiptUrl };
    case "declined":
      return { kind: "show-error", message: result.reason };
    case "requires_action":
      return { kind: "redirect", url: result.redirectUrl };
    default:
      return assertNever(result);
  }
}
Shapessrc/structural-typing.tsThe first call compiles: fromForm has every property of Order. The second fails with TS2353, because a new literal with an unknown property is most likely a typo. toOrder copies only the known fields. The class and the plain object are interchangeable, because only their shapes are compared.
type Order = { id: string; total: number };

function saveOrder(order: Order): void {}

const fromForm = { id: "o-1", total: 10, couponCode: "WELCOME" };
saveOrder(fromForm);
saveOrder({ id: "o-1", total: 10, couponCode: "WELCOME" });

function toOrder(source: Order): Order {
  return { id: source.id, total: source.total };
}
saveOrder(toOrder(fromForm));

class Invoice {
  constructor(
    public id: string,
    public total: number,
  ) {}
}
saveOrder(new Invoice("i-9", 25));
Brandssrc/ids.tsThe __brand property exists only in the type; no value ever has it. Branded IDs are created only by functions that check the format, and the cast is allowed only there. After that, swapping the two kinds of ID fails to compile.
export type OrderId = string & { readonly __brand: "OrderId" };
export type CustomerId = string & { readonly __brand: "CustomerId" };

export function toOrderId(value: string): OrderId {
  if (!/^o-\d+$/.test(value)) throw new Error("The order ID has the wrong format.");
  return value as OrderId;
}

export function toCustomerId(value: string): CustomerId {
  if (!/^c-\d+$/.test(value)) throw new Error("The customer ID has the wrong format.");
  return value as CustomerId;
}

export function cancelOrder(orderId: OrderId, customerId: CustomerId): void {}

const orderId = toOrderId("o-1");
const customerId = toCustomerId("c-42");
cancelOrder(orderId, customerId);
cancelOrder(customerId, orderId);
Guardssrc/type-guards.tsThe compiler trusts a guard's value is Type claim. The first guard checks one property and claims the whole type, so { status: "weird" } passes. The second uses the schema, so the claim and the check cannot differ. The assertion function narrows for the rest of the scope, or throws.
import { PaymentResultSchema, type PaymentResult } from "./payment-result-schema.js";

export function isPaymentResultWrong(value: unknown): value is PaymentResult {
  return typeof value === "object" && value !== null && "status" in value;
}

export function isPaymentResult(value: unknown): value is PaymentResult {
  return PaymentResultSchema.safeParse(value).success;
}

export function assertIsDefined<T>(value: T, name: string): asserts value is NonNullable<T> {
  if (value === undefined || value === null) throw new Error(`${name} is missing.`);
}

function readCustomerEmail(customer: { email?: string }): string {
  assertIsDefined(customer.email, "email");
  return customer.email.toLowerCase();
}
