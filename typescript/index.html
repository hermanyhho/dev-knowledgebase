TypeScript Overview

JavaScript with types that are checked before the program runs. The key ideas, each with its own detail page.

What it is

TypeScript adds type annotations to JavaScript. The compiler, tsc, checks that values match their types, then removes the types and outputs plain JavaScript. Node.js and browsers run only that JavaScript.

Four ideas explain almost every surprise: types do not exist at runtime, types are compared by shape, types can be generic and derived from each other, and tsconfig.json decides how files and imports are found.

Main rule: trust types only for values your own code created; validate outside data once where it enters. Turn on strict, and run tsc --noEmit in CI.

Example flow:

Pick a flow and press Play to follow it through the diagram, step by step.

  1. tsc reads tsconfig.json, then checks each file. Objects are compared by shape, and each case of a switch narrows a union.
  2. Generic functions get their type parameters from the arguments. Derived types such as Omit<Order, "id"> follow the source type.
  3. With no errors, tsc writes JavaScript. Every type is gone.
  4. At runtime a request body arrives. Nothing checks its type unless a schema does, at the point where it enters.

Problems it solves

  • Mistakes found in productionWrong property names and types fail the build instead.
  • Unclear contractsFunction signatures show what goes in and comes out.
  • Forgotten casesA new member of a union fails every switch that does not handle it.
  • No runtime costTypes are removed, so the program runs as plain JavaScript.

Problems it introduces

  • False confidenceTypes say nothing about data from outside.
  • Escape hatchesany, as and ! silence the compiler.
  • A build step and settingstsconfig.json options interact, and import rules surprise newcomers.
  • Complex typesDeep generic and conditional types give long error messages.

Narrowingpayment-result.tsEach state is its own object type with a fixed status. Inside each case, only that state's fields exist. If a fourth status is added, assertNever fails to compile.
type PaymentResult =
  | { status: "succeeded"; receiptUrl: string }
  | { status: "declined"; reason: string };

function assertNever(value: never): never {
  throw new Error(`Unexpected value: ${JSON.stringify(value)}`);
}

function messageFor(result: PaymentResult): string {
  switch (result.status) {
    case "succeeded":
      return `Paid. Receipt: ${result.receiptUrl}`;
    case "declined":
      return `Declined: ${result.reason}`;
    default:
      return assertNever(result);
  }
}
Genericsgenerics.tsfindById returns the same type as its list items. NewOrder is derived from Order, so a new field in Order appears in it too.
type Order = { id: string; customerId: string; total: number; createdAt: Date };

function findById<T extends { id: string }>(items: T[], id: string): T | undefined {
  return items.find((item) => item.id === id);
}

type NewOrder = Omit<Order, "id" | "createdAt">;
Runtimeorder-schema.tsThe schema checks the data while the program runs, and z.infer gives the matching type, so the check and the type cannot differ.
import { z } from "zod";

export const NewOrderSchema = z.object({
  customerId: z.string().min(1),
  total: z.number().nonnegative(),
});

export type NewOrder = z.infer<typeof NewOrderSchema>;

const result = NewOrderSchema.safeParse(JSON.parse('{"customerId":"c-42","total":"12.50"}'));
console.log(result.success);
