tsconfig and Module Resolution

The settings file that tells the compiler what to check and what to output, and how it finds the file behind each import.

What it is

tsconfig.json sits in the project root. It tells tsc which files belong to the project, how strict the checks are, which JavaScript version to write, and how to find the file behind each import.

Finding that file is module resolution. It happens twice: tsc does it at compile time to find types, and Node.js or a bundler does it again at runtime to find code. tsc does not change the import strings it writes to the output. So the setting "module": "nodenext" makes tsc follow the same rules as Node.js, and an import that compiles also works when the program runs.

That is why a Node.js project writes import { orders } from "./orders.js" in a .ts file: .js is the name the file has when Node.js loads it. See CommonJS and ES modules for the two module systems.

Main rule: for code that Node.js runs, use "module": "nodenext" and write imports as Node.js will load them. For code that a bundler builds, use "module": "preserve" with "moduleResolution": "bundler".

Diagram

Example flow:

Pick a flow and press Play to follow it through the diagram, step by step.

  1. You write import { orders } from "./orders", without an extension, in a project with "type": "module".
  2. With "module": "nodenext", tsc applies Node.js rules and stops: TS2835: Relative import paths need explicit file extensions ... Did you mean './orders.js'?
  3. You write "./orders.js". tsc knows this is the output name and reads the types from src/orders.ts.
  4. tsc writes dist/server.js with the import string unchanged: "./orders.js".
  5. Node.js loads dist/orders.js, which exists. The import works at compile time and at runtime.
  1. You write import { z } from "zod". A bare name means a package.
  2. tsc opens node_modules/zod/package.json and reads its exports field. It picks the "types" entry and reads that .d.ts file.
  3. If a package has no types, tsc looks in node_modules/@types/. Without either, the import has the type any, or an error under strict.
  4. At runtime Node.js reads the same exports field, but picks the "import" or "default" entry: the JavaScript.
  1. To avoid "../../../config.js", someone adds "paths": { "@app/*": ["src/*"] } to tsconfig.json.
  2. import { config } from "@app/config.js" compiles: tsc uses paths to find the file.
  3. The output still says "@app/config.js". Node.js does not read tsconfig.json, looks for a package named @app/config.js, and fails at startup with ERR_MODULE_NOT_FOUND.
  4. Use the imports field in package.json instead: "#app/*": "./dist/*". Node.js reads it at runtime, and tsc maps it back to src.
  1. You add noUncheckedIndexedAccess and verbatimModuleSyntax to tsconfig.json.
  2. orders[0].total now fails with TS2532: Object is possibly 'undefined'. An empty list has no first item, and before this setting the compiler ignored that.
  3. import { Order, orders } fails with TS1484: 'Order' is a type and must be imported using a type-only import.
  4. You write import { type Order, orders }. The output keeps orders and drops Order, and every tool that compiles one file at a time gets the same result.
  1. A React app is built by Vite. Its tsconfig.json uses "module": "preserve", "moduleResolution": "bundler" and "noEmit": true.
  2. import { Button } from "./button" compiles without an extension, because a bundler finds button.tsx by itself.
  3. Vite reads the imports and builds the JavaScript. tsc only checks types, in the editor and in CI.
  4. The browser never sees the original import strings: the bundler replaced them. That is why the bundler rules can be looser than the Node.js rules.

Problems it solves

  • Imports that compile but fail at runtimenodenext applies the Node.js rules at compile time, so most of these fail the build instead.
  • One project, many toolsThe editor, tsc, test runners and linters all read the same settings.
  • Choosing how strict to beA project can turn on checks one by one while fixing old code.
  • Types for packagesThe exports field lets a package ship types and code side by side.

Problems it introduces

  • Many settings that interactmodule, moduleResolution, target and lib depend on each other.
  • The .js extension in .ts filesCorrect, but surprising until you know why.
  • Settings that only tsc knowspaths compiles but breaks at runtime unless another tool repeats it.
  • Different setups for server and frontendCode shared between them must follow the stricter Node.js rules.

Aliasespackage.jsonThe imports field is part of Node.js, so the alias works at runtime too. Its names must start with #. It points at dist, where the running code is, and tsc maps that back to src for types. A paths entry in tsconfig.json would compile, then fail when Node.js starts.
{
  "name": "orders-api",
  "type": "module",
  "imports": {
    "#app/*": "./dist/*"
  },
  "scripts": {
    "build": "tsc",
    "start": "node --enable-source-maps dist/server.js",
    "typecheck": "tsc --noEmit"
  }
}
Packagenode_modules/zod/package.jsonA shortened exports field of the kind packages publish. Each entry lists files per condition. tsc picks "types", Node.js picks "import" for ES modules or "require" for CommonJS. Files that are not listed cannot be imported.
{
  "name": "zod",
  "type": "module",
  "exports": {
    ".": {
      "types": "./index.d.ts",
      "import": "./index.js",
      "require": "./index.cjs"
    },
    "./package.json": "./package.json"
  }
}
Sourcesrc/server.tsThree kinds of imports. The relative one ends in .js, the file name at runtime. import type is removed from the output. The alias starts with # and comes from package.json.
import { z } from "zod";
import { type Order, orders } from "./orders.js";
import { config } from "#app/config.js";

const OrderIdSchema = z.string().startsWith("o-");

export function findOrder(orderId: string): Order | undefined {
  const validOrderId = OrderIdSchema.parse(orderId);
  return orders.find((order) => order.id === validOrderId);
}

console.log({ port: config.port });
