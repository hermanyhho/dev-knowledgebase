TypeScript / Compiling

Compile Time and Runtime

TypeScript checks types before the program runs, then removes them. While the program runs, only JavaScript is left.

What it is

TypeScript is JavaScript with type annotations. The TypeScript compiler, tsc, reads your code and reports places where a value does not match its type. Then the types are removed and plain JavaScript is left. Node.js and browsers only ever run that JavaScript.

This means types only protect values that your own code created and the compiler could see. Data from outside, such as a request body, a JSON file or an environment variable, arrives while the program runs. No type check happens then. If the data has the wrong shape, the code runs with it anyway.

The fix is to check outside data once, where it enters, with code that runs: a schema library such as Zod. After that check, the type is true.

Main rule: trust a type only for values your own code created. Every value from outside starts as unknown and is validated once, where it enters.

With Node.js running .ts files, set "erasableSyntaxOnly": true in tsconfig.json (TypeScript 5.8 and later). The compiler then reports syntax that Node.js cannot strip.

How C# differs

C# still needs validation for rules such as "quantity must be positive", but it catches wrong types by itself. In TypeScript, a schema library does both.

  1. The source has a type Order, a function with annotated parameters, and a union type for the status.
  2. After checking, tsc writes dist/orders.js. The type line is gone, and so are all the annotations.
  3. Node.js runs the JavaScript. Nothing in it says that total must be a number.
  4. That is why code such as if (value instanceof Order) cannot work for a type: there is no Order at runtime.
  1. A client sends an order with "shippingFee": "4.99". The fee is a string, not a number.
  2. The handler writes const order = req.body as NewOrder. The compiler accepts it, and at runtime the line does nothing.
  3. The items cost 25, and the code adds the fee with +. With a string, + joins text: 25 + "4.99" is "254.99". No error is thrown.
  4. The wrong total is saved, or a later line throws with a message far from the cause. The type said number the whole time.
  1. The same request arrives, with the fee as a string.
  2. The handler calls NewOrderSchema.safeParse(req.body). This code runs and checks each field.
  3. The check fails on shippingFee: expected a number, got a string. The API answers 400 with those paths, and logs them at warn with the request ID.
  4. For a correct body, safeParse returns the data with the type NewOrder, which Zod derives from the schema. From here the type is true.
  1. You run node src/server.ts on Node.js 24. Node.js replaces each type annotation with spaces and runs the rest.
  2. No type checking happens. A type error in the file does not stop it from running.
  3. The file has an enum, which needs generated JavaScript. Node.js stops: TypeScript enum is not supported in strip-only mode.

Problems it solves

  • Mistakes found only in productionWrong property names, missing arguments and wrong types fail the build instead.
  • Unclear function contractsParameter and return types show what a function expects and gives back.
  • Risky renamesThe editor renames a property everywhere it is used, and the compiler reports what it missed.
  • No cost at runtimeTypes are removed, so the program is exactly as fast as plain JavaScript.

Problems it introduces

  • False confidence about outside dataA type on a request body looks safe but checks nothing at runtime.
  • Escape hatchesany, as and ! silence the compiler, and errors return at runtime.
  • Two definitions of one shapeWithout a schema library you write the type and the validation separately, and they drift apart.
  • A build stepCode needs tsc or a tool that strips types, and type checking needs its own step in CI.
Sourcesrc/orders.tsThe status is a union of strings, not an enum, so the file contains only erasable syntax. The last line has the mistake from the first flow: the compiler sees the literal value and reports it.
export type OrderStatus = "pending" | "paid";

export type Order = {
  id: string;
  total: number;
  status: OrderStatus;
};

export function addShipping(order: Order): number {
  return order.total + 4.99;
}

const order: Order = { id: "o-1", total: "12.50", status: "paid" };
Schemasrc/order-schema.tsOne definition gives both the runtime check and the type. z.infer turns the schema into a TypeScript type, so the two cannot drift apart. Examples use Zod 4.
import { z } from "zod";

export const NewOrderSchema = z.object({
  customerId: z.string().min(1),
  items: z
    .array(
      z.object({
        productId: z.string().min(1),
        quantity: z.number().int().positive(),
        unitPrice: z.number().nonnegative(),
      }),
    )
    .min(1),
  shippingFee: z.number().nonnegative(),
});

export type NewOrder = z.infer<typeof NewOrderSchema>;
Schemasrc/create-order.tssafeParse returns a result instead of throwing. Failed fields are logged by path and error code, with the request ID that req.log, from pino-http, carries. The values are not logged, because they can hold personal data. After the check, result.data has the type NewOrder.
import type { Request, Response } from "express";
import { NewOrderSchema } from "./order-schema.js";
import { orderTotal } from "./order-total.js";

export function createOrder(req: Request, res: Response) {
  const result = NewOrderSchema.safeParse(req.body);
  if (!result.success) {
    const failedFields = result.error.issues.map((issue) => ({
      path: issue.path.map(String).join("."),
      code: issue.code,
    }));
    req.log.warn({ route: "POST /orders", failedFields }, "request body failed validation");
    return res.status(400).json({ errors: failedFields });
  }

  const total = orderTotal(result.data);
  res.status(201).json({ total });
}
Castsrc/create-order-unsafe.tsThe version to avoid. req.body is any, and as NewOrder only tells the compiler to believe it. With the first request from requests.http, orderTotal returns the string "254.99" instead of the number 29.99, and no error is thrown.
import type { Request, Response } from "express";
import type { NewOrder } from "./order-schema.js";
import { orderTotal } from "./order-total.js";

export function createOrderUnsafe(req: Request, res: Response) {
  const order = req.body as NewOrder;
  const total = orderTotal(order);
  res.status(201).json({ total });
}
Your codesrc/order-total.tsThis function is correct for every value that matches NewOrder. It has no reason to check types again. It is only safe because every caller passes data that went through the schema.
import type { NewOrder } from "./order-schema.js";

export function orderTotal(order: NewOrder): number {
  const itemsTotal = order.items.reduce((total, item) => total + item.quantity * item.unitPrice, 0);
  return itemsTotal + order.shippingFee;
}
Outside datasrc/config.tsEnvironment variables are outside data too. z.coerce.number() turns "3000" into 3000. If a variable is missing or wrong, the app logs which ones and exits at startup, instead of failing later on the first request. The values are never logged, since some are secrets.
import { z } from "zod";
import pino from "pino";

const ConfigSchema = z.object({
  PORT: z.coerce.number().int().default(3000),
  DATABASE_URL: z.string().url(),
  NODE_ENV: z.enum(["development", "test", "production"]),
});

const result = ConfigSchema.safeParse(process.env);
if (!result.success) {
  const invalidVariables = result.error.issues.map((issue) => issue.path.map(String).join("."));
  pino().fatal({ invalidVariables }, "configuration is invalid, exiting");
  process.exit(1);
}

export const config = result.data;
