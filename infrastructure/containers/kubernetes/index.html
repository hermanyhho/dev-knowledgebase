Infrastructure / Containers

Kubernetes

Also called K8s. Runs containers on a group of machines and keeps them in the state you describe.

What it is

Kubernetes runs containers on a group of machines called a cluster. You do not start or stop containers yourself. You write down the state you want, for example "3 copies of the orders image, version 1.4.0, each with 256 MiB of memory", and send it to the cluster.

Kubernetes stores that desired state. Programs called controllers compare it with what is running and fix every difference: they start missing containers, replace lost ones and remove extra ones. They repeat this check all the time, so the cluster returns to the desired state after a failure.

It runs container images, for example images built with Docker. Google started the project in 2014. The Cloud Native Computing Foundation runs it now.

TermMeaningIn the example
ClusterThe control plane plus the machines that run your containers.One cluster for production
Control planeThe programs that store the desired state and decide what runs where.API server, etcd, scheduler, controllers
NodeOne machine, virtual or physical, that runs pods.Node A, node B
PodThe smallest unit Kubernetes runs: one or more containers that share an IP address.One copy of the orders app
ManifestA YAML file that describes an object you want.deployment.yaml
ControllerA loop that compares desired and actual state and acts on the difference.The ReplicaSet controller keeps 3 pods running
Main rule: you describe the desired state, and Kubernetes keeps the actual state equal to it. To change something, change the YAML and apply it again. Changes made by hand to a running pod are lost when the pod is replaced.

Control plane and worker nodes

ComponentRuns onWhat it does
API serverControl planeThe only way in. kubectl, controllers and kubelets all read and write objects through it. It checks permissions and validates each object.
etcdControl planeA key-value database that stores every object. If it is lost, the cluster's state is lost, so it must be backed up.
SchedulerControl planePicks a node for each new pod, based on free CPU and memory and your placement rules.
Controller managerControl planeRuns the built-in controllers: Deployment, ReplicaSet, Node, Job, EndpointSlice and more.
kubeletEvery nodeStarts the pods assigned to its node, runs their probes and reports their status to the API server.
Container runtimeEvery nodePulls images and runs containers. Usually containerd.
kube-proxyEvery nodeSets network rules so traffic to a Service IP reaches one of its pods. Some network plugins, such as Cilium, replace it.

Only the API server talks to etcd. Every other component watches the API server for changes and writes its results back to it. In a managed cluster such as EKS, AKS or GKE, the cloud provider runs the control plane, and you see only the nodes.

Declarative YAML and the reconciliation loop

You keep manifests in Git and run kubectl apply -f k8s/. kubectl sends each file to the API server, which stores it. Applying the same files again changes nothing. Applying a changed file updates only the changed fields. kubectl diff -f k8s/ shows the change before you apply it.

Commands such as kubectl scale or kubectl edit change the cluster directly. The next apply from Git overwrites those changes, so use them only in an emergency, then update Git.

Step of the loopWhat the controller doesExample
1. WatchGets a notice from the API server when an object it handles changes.A pod of the ReplicaSet was deleted
2. CompareReads the desired state and the actual state.Desired 3 pods, existing 2
3. ActWrites the change to the API server.Creates 1 pod
4. RepeatAlso runs again on a timer, so a missed notice is corrected later.Every few minutes

Controllers do not call each other. The Deployment controller creates a ReplicaSet object, and the ReplicaSet controller notices it and creates pods. Each one only reads and writes objects through the API server.

Rolling updates and rollbacks

When you change the pod template of a Deployment, for example the image tag, Kubernetes replaces pods a few at a time. It creates a new ReplicaSet for the new version, scales it up and scales the old one down. A new pod counts only after its readiness probe passes.

SettingMeaningDefaultIn the example
maxSurgeHow many pods above replicas may exist during the update25%1: up to 4 pods
maxUnavailableHow many pods below replicas may be not ready during the update25%0: never fewer than 3 ready
progressDeadlineSecondsTime without progress before the rollout is marked failed600Default
revisionHistoryLimitOld ReplicaSets kept for rollback10Default

kubectl rollout status deployment/orders -n shop waits until the update finishes or fails. A failed rollout does not roll back by itself. It stops, and the old pods keep serving. kubectl rollout undo deployment/orders -n shop switches back to the previous ReplicaSet with the same rolling steps.

A rollback restores the pod template only. It does not undo database migrations or changes inside a ConfigMap. After a rollback, also change the image tag in Git, or the next apply rolls forward again.

Health probes

The kubelet calls each probe on a timer, by default every 10 seconds, and acts after 3 failures in a row. The app code for these endpoints is in the diagram: click a pod.

ProbeQuestion it answersWhen it failsWhat to check
StartupHas the app finished starting?Liveness and readiness wait. After failureThreshold times periodSeconds, the container is restarted.The liveness endpoint. It gives slow starters time without a long liveness delay.
LivenessIs the process stuck?The kubelet restarts the container.Only the process itself: can it answer HTTP?
ReadinessCan this pod take requests now?The pod is removed from the Service endpoints. It is not restarted.Startup work is finished. The pod is not overloaded.

Common mistake: checking the database in the liveness probe. When the database is down, every pod fails liveness and is restarted, again and again. Restarts do not fix the database, and the restart loop slows recovery. Keep liveness to the process. A shared database in readiness causes a similar problem: all pods leave the Service at once, and callers get connection errors instead of a clear error from your app.

When a container exits, the kubelet restarts it in the same pod, with a growing delay of up to 5 minutes. kubectl get pods shows this as CrashLoopBackOff.

Resource requests and limits

SettingUsed byWhen the container goes over it
requests.cpuThe scheduler: the node must have this much CPU free. Also sets the pod's share when CPU is short.Nothing. The pod can use spare CPU on the node.
limits.cpuThe Linux CPU quota, counted per 100 ms periodThe container is throttled: it waits for the next period. Requests get slower. Nothing restarts.
requests.memoryThe schedulerNothing at once. When the node runs low on memory, pods above their request are evicted first.
limits.memoryThe Linux kernelThe kernel kills the container. Status OOMKilled, exit code 137. The kubelet restarts it.

A common setup: memory limit equal to the memory request, a CPU request, and no CPU limit or a high one. CPU throttling is hard to see: the pod stays healthy, but its p99 latency rises. .NET reads the memory limit and keeps its heap below 75% of it. For Node.js, set --max-old-space-size below the limit, as the Node.js page explains.

Pod shutdown sequence

StepWhat happens
1. TerminatingThe pod is marked for deletion, because of a rollout, a scale-down, a node drain or kubectl delete. The grace period starts: terminationGracePeriodSeconds, 30 by default.
2. Removed from the ServiceThe pod is removed from the Service endpoints. Every kube-proxy and the Gateway need a moment to stop sending it traffic. Steps 2 and 3 start at the same time.
3. preStop hookThe kubelet runs the preStop hook, for example a 5 second sleep. The app keeps serving the late requests during that time.
4. SIGTERMThe kubelet sends SIGTERM to the main process (PID 1) of each container.
5. App exitsThe app stops accepting connections, finishes requests in progress, closes database connections and exits.
6. SIGKILLIf the container still runs when the grace period ends, the kubelet sends SIGKILL. Requests in progress fail.

The grace period covers the preStop hook and the SIGTERM handling together. With 30 seconds and a 5 second preStop, the app has 25 seconds. The example app gives itself 20. The sleep action in preStop needs Kubernetes 1.30 or newer.

Start the app process directly, for example CMD ["node", "dist/server.js"]. With npm start or a shell script, that program is PID 1 and may not pass SIGTERM on to Node.js.

Configuration and secrets

The Deployment passes ConfigMap and Secret values to the container as environment variables with envFrom. The app reads them once at startup and stops with a clear error if one is missing. Changing a ConfigMap does not change running pods. Run kubectl rollout restart deployment/orders -n shop to start new pods that read the new values.

A base64 value can be decoded by anyone who can read it. To protect Secrets: turn on encryption at rest for etcd, let few people read Secrets, and keep the real values in a secret store such as AWS Secrets Manager or Azure Key Vault. A tool such as the External Secrets Operator copies them into Kubernetes Secrets. Never commit real secret values to Git.

Service discovery with DNS

Every Service gets a DNS name inside the cluster. A pod looks it up like any host name and connects to the Service IP. Pod IPs change each time a pod is replaced, so config holds names, never pod IPs.

When Kubernetes is too much

A cluster needs people who understand its networking, upgrades and security settings. It also needs add-ons: a Gateway controller, a log agent, metrics and certificate management. For a small team with a few services, that work can cost more than it saves.

A managed container service runs your image with scaling, rolling deploys and health checks, with no cluster to maintain: Azure Container Apps, Google Cloud Run or AWS ECS with Fargate. Move to Kubernetes when you need what it adds, such as many microservices, custom controllers or the same setup on several clouds.

Managed KubernetesCloudNodes
EKSAWSYou manage node groups, or EKS Auto Mode manages them for you.
AKSAzureYou manage node pools, or AKS Automatic manages them for you.
GKEGoogle CloudYou manage node pools, or Autopilot manages them and bills per pod request.

In all three, the provider runs the API server and etcd, backs them up and offers version upgrades. You still choose when to upgrade, install add-ons and secure your workloads.

Diagram

Example flow:

Pick a flow and press Play to follow it through the diagram, step by step.

  1. You run kubectl apply -f k8s/. kubectl sends deployment.yaml to the API server. The API server checks that you may create Deployments and that the YAML is valid.
  2. The API server saves the Deployment in etcd and answers "created". No container runs yet: only the desired state is stored.
  3. The Deployment controller sees a Deployment without a ReplicaSet and creates one. The ReplicaSet controller sees 0 of 3 pods and creates 3 Pod objects. They have no node yet, so their status is Pending.
  4. The scheduler sees 3 pods without a node. It compares their CPU and memory requests with each node's free capacity, spreads them out and writes a node name into each pod: 2 on node A, 1 on node B.
  5. Each kubelet sees the pods assigned to its node. It tells the container runtime to pull the image and start the container, and starts the probes.
  6. Each pod answers 200 on /health/ready, so it is marked ready and added to the Service endpoints. The Deployment reports 3 of 3 ready.
  1. A browser sends GET https://shop.example.com/orders/42. The cloud load balancer passes it to the Gateway controller running in the cluster.
  2. The HTTPRoute matches the host shop.example.com and the path prefix /orders, so the Gateway sends the request to the orders Service.
  3. The Service sends the request to one ready pod from its endpoints, here the pod on node B. The rules that do this are kept up to date by kube-proxy on each node.
  4. The app handles the request. It writes one JSON log line to standard output with the trace ID from the traceparent header. The node's log agent sends that line to the log store with the pod name added.
  5. The response goes back the same way. When the app calls another service, it uses a DNS name such as payments.shop.svc.cluster.local and sends the same trace ID along.
  1. You change the image tag to 1.5.0 and run kubectl apply. The API server stores the new pod template.
  2. The Deployment controller creates a new ReplicaSet for 1.5.0 with 1 pod. maxSurge: 1 allows 4 pods for now. The scheduler places it on node B, and the kubelet starts it.
  3. The new pod passes its readiness probe and joins the Service. 4 pods now take requests.
  4. maxUnavailable: 0 means an old pod is removed only after a new one is ready. The controller scales the old ReplicaSet to 2, and one old pod shuts down. The "Pod shutdown" flow shows those steps.
  5. The same steps repeat twice more. Then 3 new pods serve, and the old ReplicaSet has 0 pods. It is kept so you can roll back.
  6. If a new pod never becomes ready, the rollout stops and the old pods keep serving. kubectl rollout undo scales the old ReplicaSet up again with the same steps.
  1. Node B loses power. Its kubelet stops sending heartbeats, the regular status updates it sends to the API server.
  2. After a grace period of less than a minute, the node controller marks node B NotReady. Its pod is marked not ready and removed from the Service, so new requests go only to node A.
  3. After 5 more minutes by default, the pod on node B is evicted. The ReplicaSet controller now counts 2 of 3 pods and creates a new Pod object.
  4. The scheduler places the new pod on node A, the only ready node with room. Node A's kubelet starts it.
  5. The new pod passes readiness and joins the Service. The Deployment has 3 of 3 ready again, and no person had to act.
  1. A rollout, a scale-down or kubectl delete pod asks the API server to delete the pod on node B. It is marked Terminating, and its 30 second grace period starts.
  2. The EndpointSlice controller removes the pod from the Service. Every kube-proxy and the Gateway must update their rules, which takes a moment. A few requests can still arrive.
  3. At the same time, the kubelet runs the preStop hook: sleep 5 seconds. The app keeps serving, so those late requests still succeed.
  4. The kubelet sends SIGTERM to the app. The app stops accepting connections, finishes the requests in progress and closes its database pool.
  5. The app exits with code 0, usually within a few seconds. If it still ran 30 seconds after step 1, the kubelet would send SIGKILL and stop it at once.

Problems it solves

  • Manual restartsCrashed containers and lost nodes are replaced without a person acting.
  • Downtime during deploysRolling updates with readiness probes keep enough pods serving. A rollback is one command.
  • Badly used serversThe scheduler fills nodes based on requests, and the autoscaler adds pods under load.
  • Different setup per environmentThe same YAML runs in every cluster, on any cloud or in your own data center.
  • Hard-coded addressesServices and DNS give each app a stable name while pods come and go.

Problems it introduces

  • Much to learnObjects, networking, probes, permissions and add-ons. A small team can spend more time on the cluster than on the product.
  • Regular upgradesKubernetes has 3 minor releases a year, each supported for about 14 months, so every cluster needs an upgrade at least once a year.
  • Harder debuggingA failed request can come from the Gateway, the Service, a probe, a network policy or the app. You check each layer in turn.
  • Rules for the appThe app must answer probes, handle SIGTERM, log to standard output and keep no data on local disk.
  • A lot of YAMLOne small service needs 5 or more manifests. Teams add Helm or Kustomize to manage them, which is one more tool.
  • Idle capacity costs moneySystem pods, spare room on nodes for rescheduling and the control plane fee are paid even with no traffic.
Your appsrc/server.tsLiveness only checks that the process answers. Readiness waits for startup work. On SIGTERM the server stops taking connections, finishes open requests, then exits. Node.js 24, Express 5.
import express from "express";
import pino from "pino";
import pg from "pg";
import { config } from "./config.js";
import { ordersRouter } from "./orders/ordersRouter.js";

const shutdownTimeoutMs = 20_000;
const logger = pino();
const database = new pg.Pool(config.database);
const app = express();
let hasFinishedStartup = false;

app.get("/health/live", (req, res) => {
  res.sendStatus(200);
});

app.get("/health/ready", (req, res) => {
  res.sendStatus(hasFinishedStartup ? 200 : 503);
});

app.use("/orders", ordersRouter(database, config.paymentsBaseUrl));

const server = app.listen(config.port, () => {
  logger.info({ port: config.port }, "listening");
});

process.on("SIGTERM", () => {
  logger.info("SIGTERM received, finishing requests in progress");
  setTimeout(() => process.exit(1), shutdownTimeoutMs).unref();

  server.close(async () => {
    await database.end();
    logger.info("shutdown finished");
    process.exit(0);
  });
});

await database.query("SELECT 1");
hasFinishedStartup = true;
logger.info("startup finished, ready for traffic");

function requireEnv(name: string): string {
  const value = process.env[name];
  if (!value) {
    throw new Error(`Environment variable ${name} is not set.`);
  }
  return value;
}

Your appsrc/Orders/Program.csThe liveness endpoint runs no checks, so it fails only when the process cannot answer. The host handles SIGTERM: Kestrel stops taking connections and waits for open requests up to ShutdownTimeout. .NET 10.
using Microsoft.AspNetCore.Diagnostics.HealthChecks;
using Npgsql;
using Orders;

var builder = WebApplication.CreateBuilder(args);

builder.Logging.ClearProviders();
builder.Logging.AddJsonConsole();

var settings = OrdersSettings.FromConfiguration(builder.Configuration);
builder.Services.AddSingleton(settings);
builder.Services.AddSingleton(NpgsqlDataSource.Create(settings.DatabaseConnectionString));
builder.Services.AddSingleton<StartupWork>();
builder.Services.AddHostedService(services => services.GetRequiredService<StartupWork>());
builder.Services.AddHealthChecks().AddCheck<StartupWork>("startup", tags: ["ready"]);
builder.Services.Configure<HostOptions>(options => options.ShutdownTimeout = TimeSpan.FromSeconds(20));

var app = builder.Build();

app.MapHealthChecks("/health/live", new HealthCheckOptions { Predicate = _ => false });
app.MapHealthChecks("/health/ready", new HealthCheckOptions { Predicate = check => check.Tags.Contains("ready") });
app.MapOrderEndpoints();

app.Lifetime.ApplicationStopping.Register(() =>
    app.Logger.LogInformation("SIGTERM received, finishing requests in progress"));

app.Run();
Your appsrc/Orders/StartupWork.csRuns once at startup and reports not ready until it has finished. If the database cannot be reached, the exception stops the host and Kubernetes restarts the container.
using Microsoft.Extensions.Diagnostics.HealthChecks;
using Npgsql;

namespace Orders;

public class StartupWork(NpgsqlDataSource database) : BackgroundService, IHealthCheck
{
    private volatile bool _hasFinished;

    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        await using var command = database.CreateCommand("SELECT 1");
        await command.ExecuteScalarAsync(stoppingToken);
        _hasFinished = true;
    }

    public Task<HealthCheckResult> CheckHealthAsync(HealthCheckContext context, CancellationToken cancellationToken = default) =>
        Task.FromResult(_hasFinished
            ? HealthCheckResult.Healthy()
            : HealthCheckResult.Unhealthy("Startup work has not finished."));
}
Your appsrc/Orders/OrdersSettings.csEnvironment variables are part of IConfiguration, so the same names as in the ConfigMap work. A missing value stops the app at startup.
using Npgsql;

namespace Orders;

public record OrdersSettings(string PaymentsBaseUrl, string DatabaseConnectionString)
{
    public static OrdersSettings FromConfiguration(IConfiguration configuration)
    {
        var connectionString = new NpgsqlConnectionStringBuilder
        {
            Host = Require(configuration, "DB_HOST"),
            Database = Require(configuration, "DB_NAME"),
            Username = Require(configuration, "DB_USER"),
            Password = Require(configuration, "DB_PASSWORD"),
        };

        return new OrdersSettings(Require(configuration, "PAYMENTS_BASE_URL"), connectionString.ConnectionString);
    }

    private static string Require(IConfiguration configuration, string key) =>
        configuration[key] ?? throw new InvalidOperationException($"Environment variable {key} is not set.");
}
