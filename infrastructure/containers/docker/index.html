Infrastructure / Containers

Docker

A tool that builds container images and runs them as containers. First released in 2013.

What it is

Docker packages an application with everything it needs to run: the runtime, system libraries and your code. That package is an image. A running copy of an image is a container.

A container is a normal Linux process. The Linux kernel gives it its own view of processes, network and files (namespaces), and caps the CPU and memory it can use (control groups, or cgroups). All containers on a machine share that machine's kernel. There is no second operating system inside.

You write the build steps in a Dockerfile, build the image once, store it in a registry, and run the same image on your laptop, in CI and in production.

TermMeaningIn the example

Main rule: build one image and run that same image in every environment. Settings and secrets come from environment variables when the container starts. Data that must be kept goes in a volume or an external database, never in the container.

Containers compared with virtual machines

ContainerVirtual machine
What runs insideYour app's processes onlyA full guest operating system
KernelThe host's Linux kernel, shared by all containersIts own kernel
IsolationNamespaces and cgroups inside one kernel. A kernel bug can affect every container.A hypervisor. Stronger separation.
Start timeUnder a second: the time to start one processTens of seconds: the guest system boots
SizeTens to hundreds of MBSeveral GB
Operating systemLinux containers need a Linux kernelAny system the hypervisor supports

macOS and Windows have no Linux kernel. Docker Desktop starts a small Linux virtual machine and runs every container inside it. On Windows it uses WSL 2. Published ports still appear on localhost. Bind mounts are slower, because files are shared from your machine into the virtual machine. An image built on an Apple silicon Mac is for arm64. Build with --platform linux/amd64 for most cloud servers.

Image layers and the build cache

Each Dockerfile step that changes files (RUN, COPY, ADD) creates a layer. Docker caches every layer. On the next build it reuses a layer if the step and its input files have not changed. Once one layer changes, Docker builds that layer and every layer after it again.

So put the steps that change least at the top. Copy the dependency list and install packages first. Copy your source code after that.

Dockerfile orderAfter you change one source file
1. COPY package.json package-lock.json
2. RUN npm ci
3. COPY src		Steps 1 and 2 come from the cache. Only step 3 runs. The build takes seconds.
1. COPY . .
2. RUN npm ci		Step 1 changed, so step 2 runs again. Every code change downloads all packages.
1. COPY ShopApi.csproj
2. RUN dotnet restore
3. COPY . .		The same pattern for .NET. Restore runs only when the project file changes.

Use CMD for a normal app. Use ENTRYPOINT when the image is one program, and CMD for its default arguments. Write both in the JSON array form, called the exec form. The section on signals explains why.

Multi-stage builds

Building an app needs tools that running it does not: the .NET SDK, or TypeScript and the dev dependencies. A multi-stage Dockerfile has several FROM lines. The first stage uses a large image with the build tools and compiles the app. The last stage starts from a small runtime image and copies only the build output with COPY --from=build. Only the last stage becomes the image you ship.

ImageContainsSize, about
node:24Debian, Node.js, compilers and many tools1.1 GB

Tags and digests

A tag is a name that the image owner can point at a different image at any time. node:24 points to a new image after every Node.js 24 patch release. latest is only the default tag name. It does not mean newest, and it changes without notice.

ReferenceCan it change later?Use it for
node:24-slimYes, with every patch releaseBase images, with regular rebuilds to get security fixes

Some images, such as postgres, declare a VOLUME. If you do not name one, Docker creates an anonymous volume with a random name. A new container does not reuse it, so the data seems gone, and the old volume keeps using disk space. Always name the volume.

Networking and published ports

TopicWhat happens
Publishing a port-p 8080:3000 forwards port 8080 on the host to port 3000 in the container. Without -p, nothing outside Docker can reach the app.

Signals, PID 1 and shutdown

docker stop sends SIGTERM to the process with PID 1 in the container. If that process has not exited after 10 seconds, Docker sends SIGKILL, which ends it at once. Kubernetes does the same with a 30-second default. What PID 1 is depends on how you write the start command.

Start commandPID 1On docker stop
CMD ["node", "dist/server.js"]nodeYour SIGTERM handler runs. Clean shutdown, exit code 0.
CMD node dist/server.jsCan be /bin/shThe shell does not pass SIGTERM to your app. After 10 seconds SIGKILL ends both. Exit code 137.
CMD ["npm", "start"]npmAn extra npm process runs between Docker and your app. Start node directly.
Node.js with no handlernodeThe kernel does not apply the default "terminate" action to PID 1, so the signal is ignored until SIGKILL. .NET registers a handler for you.
docker run --init, or init: true in Composetini, a small init programIt passes signals to your app and cleans up exited child processes.

On SIGTERM the app stops accepting connections, finishes open requests, closes database and cache connections, then exits. Keep this shorter than the stop timeout. The example allows 8 seconds.

Docker Compose for local development

compose.yaml describes the app, PostgreSQL and Redis in one file. Compose creates a network for them and a named volume for the database. depends_on with condition: service_healthy waits until the database and cache healthchecks pass before it starts the app. Without the condition, Compose waits only for the containers to start, and the app can try to connect before PostgreSQL accepts connections.

CommandWhat it does
docker compose up -d --buildBuilds the app image and starts all services in the background
docker compose psLists the services with their health status
docker compose logs -f appShows the app's output and keeps printing new lines
docker compose exec db psql -U shopRuns a command inside a running container
docker compose downStops and removes the containers and the network. Volumes stay.
docker compose down -vAlso deletes the volumes. The database is empty on the next start.

Diagram

Example flow:

Pick a flow and press Play to follow it through the diagram, step by step.

  1. You write a Dockerfile: a base image, the dependency install, your code and the start command.
  2. docker build -t shop-api:1.4.0 . runs each step. Every step that changes files is saved as a read-only layer. The layers together are the image.
  3. docker run or docker compose up creates a container: the image layers plus a new writable layer. Then it starts the CMD process.
  4. The app process runs on the host's Linux kernel like any other process. Namespaces give it its own process list, network and files. cgroups cap its memory and CPU.
  5. The browser calls localhost:8080. -p 8080:3000 forwards the request to port 3000 in the app container.
  6. The app connects to db:5432. Docker's DNS server on the shop_default network returns the db container's address.
  1. You change one line in a source file and run docker build again.
  2. FROM: the base image is the same, so Docker reuses its layers.
  3. The dependency files (package.json, or the .csproj) did not change. Docker reuses the copy and the install layers. npm ci or dotnet restore does not run.
  4. The source copy has a changed file, so Docker builds this layer and every layer after it again. The build takes seconds.
  5. If the Dockerfile copied all source before the install step, every code change would run the install again. That is why the dependency files are copied first.
  1. The image is on the build machine, tagged ghcr.io/example-org/shop-api:1.4.0.
  2. docker push uploads each layer the registry does not have yet, then the image manifest. It prints the digest, sha256:....
  3. The tag 1.4.0 now points to that digest. Someone can push a different image with the same tag later. The digest always means these exact layers.
  4. A server runs docker pull with the digest. It downloads only the layers it does not have. The base image layers are often there already.
  5. docker run starts a container from the pulled image. The server runs the same files that CI tested.
  1. A process in the app container writes /tmp/report.csv. No volume is mounted at /tmp, so the file goes into the container's writable layer.
  2. docker compose down removes the container and its writable layer. The next up starts a new container from the image. The file is gone.
  3. The db container mounts the named volume pgdata at /var/lib/postgresql/data. PostgreSQL writes its files to the host disk, outside the container.
  4. docker compose down, then up: a new db container mounts the same volume. The orders are still there.
  5. docker compose down -v also deletes the volume. Use it only when you want an empty database.
  1. docker stop: the kernel delivers SIGTERM to PID 1 in the app container. With the exec form of CMD, PID 1 is node or dotnet itself.
  2. The app's shutdown code runs. The server stops accepting new connections and lets open requests finish.
  3. The app closes its database pool and Redis connection, logs that shutdown is complete, and exits with code 0. All of this takes less than 8 seconds.
  4. Now the same with the shell form, CMD node dist/server.js. PID 1 can be /bin/sh. The shell does not pass SIGTERM on, so the app never receives it.
  5. After 10 seconds Docker sends SIGKILL. The process ends at once, open requests fail, and the exit code is 137. The fix: exec form, or --init.

Problems it solves

  • Different setups on each machineThe image contains the runtime version and system libraries, so laptops, CI and servers run the same files.
  • Slow setup for new developersdocker compose up starts the app, database and cache with one command.
  • Version conflicts on one serverTwo apps can use different Node.js or .NET versions on the same machine.
  • Manual, uneven deploysA deploy pulls an image and starts a container. A rollback starts the previous tag.
  • Idle server capacityContainers start in under a second and share one kernel, so one server runs many of them.

Problems it introduces

  • More to learnDockerfiles, layers, networks and volumes, and later an orchestrator such as Kubernetes.
  • Weaker isolation than virtual machinesAll containers share one kernel. A kernel vulnerability affects every container on the host.
  • Images need regular rebuildsBase images get security fixes often. Your app gets them only when you rebuild and redeploy.
  • Data loss by mistakeFiles in the writable layer are deleted with the container. Databases need named volumes and backups.
  • Slower files on macOS and WindowsBind mounts share files into a Linux virtual machine, which slows file-heavy work such as npm install.
  • Harder debugging in small imagesChiseled .NET images have no shell, so docker exec ... sh does not work.

COPY package.json package-lock.json ./

COPY tsconfig.json ./

FROM node:24-slim

WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci --omit=dev
COPY --from=build /app/dist ./dist

Appsrc/server.tsJSON logs to standard output with pino, a request ID on every log line, a /health endpoint, and a clean shutdown on SIGTERM that finishes within 8 seconds, before Docker's 10-second SIGKILL. It listens on 0.0.0.0 so the published port reaches it.
import { randomUUID } from "node:crypto";
import express, { type NextFunction, type Request, type Response } from "express";
import pino from "pino";
import { Pool } from "pg";
import { createCacheClient } from "./cache.js";

const logger = pino();
const port = Number(process.env.PORT ?? 3000);
const shutdownTimeoutMs = 8_000;
const database = new Pool({ connectionString: process.env.DATABASE_URL });
const cache = await createCacheClient(logger);

const app = express();

app.use((req, res, next) => {
  const requestId = req.get("x-request-id") ?? randomUUID();
  const startedAt = performance.now();
  res.setHeader("x-request-id", requestId);
  res.locals.logger = logger.child({ requestId });

  res.on("finish", () => {
    res.locals.logger.info(
      { method: req.method, path: req.path, status: res.statusCode, durationMs: Math.round(performance.now() - startedAt) },
      "request finished",
    );
  });
  next();
});

app.get("/health", (req, res) => {
  res.json({ status: "ok" });
});

app.get("/orders/:orderId", async (req, res) => {
  const cacheKey = `order:${req.params.orderId}`;
  const cachedOrder = await cache.get(cacheKey);
  if (cachedOrder) return res.type("application/json").send(cachedOrder);

  const result = await database.query(
    'SELECT id, customer_id AS "customerId", total FROM orders WHERE id = $1',
    [req.params.orderId],
  );
  if (result.rowCount === 0) return res.status(404).json({ message: "The order does not exist." });

  await cache.setEx(cacheKey, 60, JSON.stringify(result.rows[0]));
  res.json(result.rows[0]);
});

app.use((error: Error, req: Request, res: Response, next: NextFunction) => {
  res.locals.logger.error({ err: error }, "request failed");
  res.status(500).json({ message: "Internal server error." });
});

const server = app.listen(port, "0.0.0.0", () => {
  logger.info({ port, nodeVersion: process.version }, "server started");
});

process.on("SIGTERM", () => {
  logger.info("SIGTERM received, finishing open requests");

  setTimeout(() => {
    logger.error({ shutdownTimeoutMs }, "open requests did not finish in time, exiting");
    process.exit(1);
  }, shutdownTimeoutMs).unref();

  server.close(async () => {
    await database.end();
    await cache.close();
    logger.info("shutdown complete");
    process.exit(0);
  });
});
Appsrc/cache.tsConnects to Redis with the URL from the environment. In Compose that is redis://cache:6379: cache is the service name, which Docker's DNS turns into the cache container's address. Uses the redis package, version 5.
import { createClient } from "redis";
import type { Logger } from "pino";

export async function createCacheClient(logger: Logger) {
  const cacheClient = createClient({ url: process.env.REDIS_URL });
  cacheClient.on("error", (error) => logger.error({ err: error }, "redis connection error"));
  await cacheClient.connect();
  return cacheClient;
}
AppProgram.csJSON logs to standard output. With IncludeScopes, ASP.NET Core adds RequestId to every log line written during a request, and the middleware returns it as X-Request-Id. .NET handles SIGTERM itself: it stops accepting requests and waits for open ones up to ShutdownTimeout, set below Docker's 10 seconds. builder.Logging.ClearProviders();
builder.Logging.AddJsonConsole(options => options.IncludeScopes = true);

app.MapHealthChecks("/health");

app.MapGet("/orders/{orderId:guid}", async (Guid orderId, NpgsqlDataSource database, IConnectionMultiplexer cache) =>
{
    var cacheKey = $"order:{orderId}";
    var cachedOrder = await cache.GetDatabase().StringGetAsync(cacheKey);
    if (cachedOrder.HasValue) return Results.Text(cachedOrder.ToString(), "application/json");

    await using var command = database.CreateCommand("SELECT id, customer_id, total FROM orders WHERE id = $1");
    command.Parameters.AddWithValue(orderId);
    await using var reader = await command.ExecuteReaderAsync();
    if (!await reader.ReadAsync()) return Results.NotFound(new { message = "The order does not exist." });

    var order = new { id = reader.GetGuid(0), customerId = reader.GetString(1), total = reader.GetDecimal(2) };
    await cache.GetDatabase().StringSetAsync(cacheKey, JsonSerializer.Serialize(order), TimeSpan.FromSeconds(60));
    return Results.Ok(order);
});

app.Lifetime.ApplicationStarted.Register(() =>
    app.Logger.LogInformation("Server started on {Urls}", string.Join(", ", app.Urls)));
app.Lifetime.ApplicationStopping.Register(() =>
    app.Logger.LogInformation("SIGTERM received, finishing open requests"));
app.Lifetime.ApplicationStopped.Register(() =>
    app.Logger.LogInformation("Shutdown complete"));

app.Run();
AppCacheSetup.csRegisters one shared Redis connection. In Compose the connection string is cache:6379: cache is the service name, which Docker's DNS turns into the cache container's address. Uses StackExchange.Redis.
using StackExchange.Redis;

public static class CacheSetup
{
    public static IServiceCollection AddCache(this IServiceCollection services, IConfiguration configuration)
    {
        var cacheConnectionString = configuration.GetConnectionString("Cache")!;
        return services.AddSingleton<IConnectionMultiplexer>(_ => ConnectionMultiplexer.Connect(cacheConnectionString));
    }
}
