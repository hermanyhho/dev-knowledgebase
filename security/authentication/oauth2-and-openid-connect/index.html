Security / Authentication

OAuth 2.0 and OpenID Connect

OAuth 2.0 is defined in RFC 6749. OpenID Connect, often shortened to OIDC, is built on top of it. Together they are what "Log in with Google" uses.

What it is

OAuth 2.0 lets an app get an access token to call an API on behalf of a user, without ever seeing the user's password. The user logs in at a separate authorization server, agrees to what the app may do, and the app receives tokens. OAuth on its own answers "what may this app do", not "who is the user".

OpenID Connect adds the "who": an ID token, a JWT that tells the app which user logged in. It also adds a standard discovery document, so an app can find the authorization server's endpoints and keys from one URL.

The login provider can be Google, Microsoft Entra ID, Okta, Auth0 or your own server running Keycloak. The flows are the same for all of them. The tokens are the same kinds as on the access and refresh tokens page, but a separate server issues them.

Main rule: the user types their password only at the authorization server. The client proves each step belongs to the same login with state, nonce and PKCE, and checks the ID token before trusting it.

Which flow to use

Flow (grant type)WhenNotes
Authorization code with PKCEAny app where a user logs in: web, single-page, mobile, desktopThe default. Use PKCE even for confidential clients.
Client credentialsA service calling an API with no user, such as a nightly jobThe service logs in with its own ID and secret. No refresh token.
Device codeDevices without a browser or keyboard: TVs, command-line toolsThe device shows a short code. The user enters it on their phone.
Refresh tokenGetting new access tokens without asking the user againSee the access and refresh tokens page.
Implicit, and resource owner passwordNever in new appsRemoved in OAuth 2.1. Implicit puts tokens in the URL. Password makes the app handle the user's password.

How an ID token differs from an access token

ID tokenAccess token
Meant forThe client: aud is the client IDAn API: aud is the API, such as orders-api
AnswersWho logged in, when and howWhat the caller may do: the scopes
FormatAlways a JWTOften a JWT, but some providers use random values that only they can check
Send it to APIs?NeverYes, in Authorization: Bearer

A common mistake is the reverse: an API that accepts a Google access token as proof of login. That token was meant for Google's APIs, so its audience does not match, and any app the user ever logged into could replay it.

Diagram

Example flow:

Pick a flow and press Play to follow it through the diagram, step by step.

  1. The user clicks "Log in" on the shop. The browser asks the shop web server for /login.
  2. The shop creates random state, nonce and code_verifier values, and saves them in a short-lived session. It computes code_challenge, the SHA-256 hash of the verifier.
  3. It redirects the browser to the authorization server's /authorize URL with the client ID, redirect URI, scopes, state, nonce and code_challenge.
  4. The user logs in there, with a password and maybe a second factor, and agrees to the scopes. The shop never sees the password.
  5. The authorization server redirects the browser back to /callback?code=...&state=.... The shop checks that state matches the one it saved.
  6. Server to server, the shop sends the code, the code_verifier and its client secret to /token. It gets back an ID token, an access token and a refresh token.
  7. The shop checks the ID token: signature, issuer, audience equal to its client ID, expiry, and nonce. Then it starts its own session for the browser. The tokens stay on the server.
  8. When a page needs the user's orders, the shop calls the orders API with the access token.
  1. An attacker catches the authorization code on its way back, for example with a malicious app on a phone that registered the same redirect address.
  2. The attacker sends the code to /token. It does not have the code_verifier, which never left the shop's server.
  3. The authorization server hashes what it received, finds no match with the saved code_challenge, and refuses. Without the verifier, the code cannot be traded for tokens.
  4. The real shop can still trade the code, because codes work once and it holds the verifier. If the attacker had used the code first, the shop's attempt would fail and the user would log in again.
  1. A nightly reporting job has no user. It calls /token with grant_type=client_credentials, its own client ID and secret, and the scope orders:read.
  2. The authorization server checks the job's credentials and that it is allowed that scope. It returns an access token whose sub is the job's client ID. There is no refresh token; the job asks again when the token expires.
  3. The job calls the orders API with the token. The API checks the audience and the scope, as for any other caller.
  1. The user clicks "Log out". The shop ends its own session and deletes the tokens it held.
  2. It revokes the refresh token at the authorization server's revocation endpoint.
  3. It redirects the browser to the authorization server's logout endpoint, so the user is also logged out there. Without this, the next "Log in" would skip the login page.

Problems it solves

  • Apps handling user passwordsThe user types the password only at the authorization server. The shop never sees or stores it.
  • Every app building its own loginOne authorization server handles passwords, second factors and lockouts for every app.
  • All-or-nothing accessScopes limit what each app may do, and the user sees them before agreeing.
  • Knowing who logged in (OIDC)The ID token gives the client a checked user ID and profile in a standard format.
  • Services calling APIs safelyClient credentials give jobs and services their own tokens, with their own scopes.
  • Custom setups for each providerDiscovery documents and standard endpoints let one library work with Google, Entra ID, Keycloak and others.

Problems it introduces

  • Many steps and settingsRedirects, codes, three token types, discovery and keys. Hand-written versions often miss a check, so use a certified library.
  • Dependence on the providerIf the authorization server is down, nobody can log in.
  • Exact settings matterA redirect URI with a wildcard, a missing state check or a skipped audience check each opens a known attack.
  • Tokens in the browserSingle-page apps that hold tokens themselves expose them to injected scripts. A server-side client, like a backend for frontend, keeps them out of the browser.
  • Logout across systemsEnding the app session, the provider session and the refresh token are three separate steps.
  • Provider differencesProviders differ in how they name audiences and scopes, so the same request may need small changes for each one.

Clientshop-web/src/oidcLogin.tsUses the openid-client library, version 6, and express-session with Redis as on the sessions page. authorizationCodeGrant checks state, sends the verifier, and checks the ID token's signature, issuer, audience, expiry and nonce. The tokens stay in the server-side session; the browser gets only a session cookie.
import express from "express";
import * as oidc from "openid-client";
import { Logger } from "pino";

declare module "express-session" {
  interface SessionData {
    pendingLogin?: { codeVerifier: string; state: string; nonce: string };
    user?: { id: string; name?: string };
    tokens?: { accessToken: string; refreshToken?: string; expiresAt: number };
  }
}

const baseUrl = "https://shop.example.com";
const redirectUri = `${baseUrl}/callback`;
const oidcConfig = await oidc.discovery(
  new URL("https://login.example.com"),
  process.env.OIDC_CLIENT_ID!,
  process.env.OIDC_CLIENT_SECRET!,
);

export function oidcRoutes(logger: Logger): express.Router {
  const router = express.Router();

  router.get("/login", async (req, res) => {
    const codeVerifier = oidc.randomPKCECodeVerifier();
    const state = oidc.randomState();
    const nonce = oidc.randomNonce();
    req.session.pendingLogin = { codeVerifier, state, nonce };

    const authorizationUrl = oidc.buildAuthorizationUrl(oidcConfig, {
      redirect_uri: redirectUri,
      scope: "openid profile email orders:read offline_access",
      code_challenge: await oidc.calculatePKCECodeChallenge(codeVerifier),
      code_challenge_method: "S256",
      state,
      nonce,
    });
    logger.info({ scopes: "openid profile email orders:read offline_access" }, "login started");
    res.redirect(authorizationUrl.href);
  });

  router.get("/callback", async (req, res) => {
    const pendingLogin = req.session.pendingLogin;
    delete req.session.pendingLogin;
    if (!pendingLogin) return res.status(400).send("No login is in progress.");

    try {
      const tokens = await oidc.authorizationCodeGrant(oidcConfig, new URL(req.originalUrl, baseUrl), {
        pkceCodeVerifier: pendingLogin.codeVerifier,
        expectedState: pendingLogin.state,
        expectedNonce: pendingLogin.nonce,
        idTokenExpected: true,
      });
      const claims = tokens.claims()!;

      req.session.regenerate(() => {
        req.session.user = { id: claims.sub, name: claims.name as string | undefined };
        req.session.tokens = {
          accessToken: tokens.access_token,
          refreshToken: tokens.refresh_token,
          expiresAt: Date.now() + (tokens.expires_in ?? 0) * 1000,
        };
        logger.info({ userId: claims.sub, scopes: tokens.scope }, "login succeeded");
        res.redirect("/");
      });
    } catch (error) {
      const errorCode = error instanceof oidc.ResponseBodyError ? error.error : (error as Error).name;
      logger.warn({ errorCode }, "login callback failed");
      res.status(400).send("The login could not be completed. Please try again.");
    }
  });

  router.get("/api/orders", async (req, res) => {
    const tokens = req.session.tokens;
    if (!tokens) return res.status(401).end();

    if (Date.now() > tokens.expiresAt - 30_000 && tokens.refreshToken) {
      const refreshed = await oidc.refreshTokenGrant(oidcConfig, tokens.refreshToken);
      req.session.tokens = {
        accessToken: refreshed.access_token,
        refreshToken: refreshed.refresh_token ?? tokens.refreshToken,
        expiresAt: Date.now() + (refreshed.expires_in ?? 0) * 1000,
      };
    }

    const ordersResponse = await fetch("https://orders.shop.example.com/orders", {
      headers: { Authorization: `Bearer ${req.session.tokens!.accessToken}` },
    });
    res.status(ordersResponse.status).json(await ordersResponse.json());
  });

  router.post("/logout", async (req, res) => {
    const refreshToken = req.session.tokens?.refreshToken;
    if (refreshToken) await oidc.tokenRevocation(oidcConfig, refreshToken);

    req.session.destroy(() => {
      const logoutUrl = oidc.buildEndSessionUrl(oidcConfig, { post_logout_redirect_uri: baseUrl });
      res.redirect(logoutUrl.href);
    });
  });

  return router;
}
Machine clientreporting-job/src/clientCredentials.tsNo user and no redirects: the job trades its own credentials for an access token and reuses it until 30 seconds before it expires. Some providers name the API with an audience or resource parameter instead of the scope alone.
import * as oidc from "openid-client";

const oidcConfig = await oidc.discovery(
  new URL("https://login.example.com"),
  process.env.REPORTING_CLIENT_ID!,
  process.env.REPORTING_CLIENT_SECRET!,
);

let cachedToken: { accessToken: string; expiresAt: number } | null = null;

async function getAccessToken(): Promise<string> {
  if (cachedToken && Date.now() < cachedToken.expiresAt - 30_000) {
    return cachedToken.accessToken;
  }

  const tokens = await oidc.clientCredentialsGrant(oidcConfig, { scope: "orders:read" });
  cachedToken = {
    accessToken: tokens.access_token,
    expiresAt: Date.now() + (tokens.expires_in ?? 0) * 1000,
  };
  return cachedToken.accessToken;
}

export async function fetchOrdersForReport(): Promise<unknown> {
  const response = await fetch("https://orders.shop.example.com/orders?placedSince=yesterday", {
    headers: { Authorization: `Bearer ${await getAccessToken()}` },
  });
  if (!response.ok) throw new Error(`The orders API replied ${response.status}.`);
  return response.json();
}
Clientsrc/ShopWeb/OidcSetup.csASP.NET Core's OpenID Connect handler runs the whole login: it creates and checks state and nonce, sends the PKCE values, trades the code and checks the ID token. The cookie handler then keeps the user logged in. SaveTokens stores the tokens in the encrypted, server-issued authentication cookie.
using Microsoft.AspNetCore.Authentication;
using Microsoft.AspNetCore.Authentication.Cookies;
using Microsoft.AspNetCore.Authentication.OpenIdConnect;
using Microsoft.IdentityModel.Protocols.OpenIdConnect;

namespace ShopWeb;

public static class OidcSetup
{
    public static void AddShopLogin(this IServiceCollection services, IConfiguration configuration) =>
        services
            .AddAuthentication(options =>
            {
                options.DefaultScheme = CookieAuthenticationDefaults.AuthenticationScheme;
                options.DefaultChallengeScheme = OpenIdConnectDefaults.AuthenticationScheme;
            })
            .AddCookie(options =>
            {
                options.Cookie.HttpOnly = true;
                options.Cookie.SecurePolicy = CookieSecurePolicy.Always;
                options.Cookie.SameSite = SameSiteMode.Lax;
            })
            .AddOpenIdConnect(options =>
            {
                options.Authority = "https://login.example.com";
                options.ClientId = configuration["OIDC_CLIENT_ID"];
                options.ClientSecret = configuration["OIDC_CLIENT_SECRET"];
                options.ResponseType = OpenIdConnectResponseType.Code;
                options.UsePkce = true;
                options.SaveTokens = true;
                options.MapInboundClaims = false;
                options.CallbackPath = "/callback";

                options.Scope.Clear();
                foreach (var scope in new[] { "openid", "profile", "email", "orders:read", "offline_access" })
                    options.Scope.Add(scope);

                options.Events.OnTokenValidated = context =>
                {
                    context.HttpContext.RequestServices.GetRequiredService<ILogger<OpenIdConnectEvents>>()
                        .LogInformation("Login succeeded for user {UserId}", context.Principal?.FindFirst("sub")?.Value);
                    return Task.CompletedTask;
                };
                options.Events.OnRemoteFailure = context =>
                {
                    context.HttpContext.RequestServices.GetRequiredService<ILogger<OpenIdConnectEvents>>()
                        .LogWarning("Login callback failed: {ErrorType}", context.Failure?.GetType().Name);
                    context.Response.Redirect("/login-failed");
                    context.HandleResponse();
                    return Task.CompletedTask;
                };
            });

    public static void MapShopLoginEndpoints(this WebApplication app)
    {
        app.MapGet("/login", () =>
            Results.Challenge(new AuthenticationProperties { RedirectUri = "/" }, [OpenIdConnectDefaults.AuthenticationScheme]));

        app.MapGet("/api/orders", async (HttpContext http, IHttpClientFactory httpClients) =>
        {
            var accessToken = await http.GetTokenAsync("access_token");
            var ordersApi = httpClients.CreateClient("orders-api");
            ordersApi.DefaultRequestHeaders.Authorization = new("Bearer", accessToken);
            var ordersResponse = await ordersApi.GetAsync("/orders");
            return Results.Stream(await ordersResponse.Content.ReadAsStreamAsync(), "application/json");
        }).RequireAuthorization();

        app.MapPost("/logout", () =>
            Results.SignOut(new AuthenticationProperties { RedirectUri = "/" },
                [CookieAuthenticationDefaults.AuthenticationScheme, OpenIdConnectDefaults.AuthenticationScheme]));
    }
}
Machine clientsrc/ReportingJob/ClientCredentialsTokens.csNo user and no redirects: the job posts its own credentials to the token endpoint and reuses the access token until 30 seconds before it expires. Some providers name the API with an audience or resource parameter instead of the scope alone.
using System.Net.Http.Headers;
using System.Net.Http.Json;
using System.Text;

namespace ReportingJob;

record TokenResponse(string access_token, int expires_in);

public class ClientCredentialsTokens(HttpClient http, IConfiguration configuration)
{
    private string? cachedAccessToken;
    private DateTimeOffset cachedUntil;

    public async Task<string> GetAccessTokenAsync()
    {
        if (cachedAccessToken is not null && DateTimeOffset.UtcNow < cachedUntil.AddSeconds(-30))
            return cachedAccessToken;

        var credentials = Convert.ToBase64String(Encoding.UTF8.GetBytes(
            $"{configuration["REPORTING_CLIENT_ID"]}:{configuration["REPORTING_CLIENT_SECRET"]}"));

        using var request = new HttpRequestMessage(HttpMethod.Post, "https://login.example.com/token")
        {
            Headers = { Authorization = new AuthenticationHeaderValue("Basic", credentials) },
            Content = new FormUrlEncodedContent(new Dictionary<string, string>
            {
                ["grant_type"] = "client_credentials",
                ["scope"] = "orders:read",
            }),
        };

        using var response = await http.SendAsync(request);
        response.EnsureSuccessStatusCode();
        var tokens = (await response.Content.ReadFromJsonAsync<TokenResponse>())!;

        cachedAccessToken = tokens.access_token;
        cachedUntil = DateTimeOffset.UtcNow.AddSeconds(tokens.expires_in);
        return cachedAccessToken;
    }
}
