JavaScript / Modules

CommonJS and ES Modules

The two module systems in JavaScript: require with module.exports, and import with export.

What it is

A module is one JavaScript file with its own scope. Variables declared in it are not visible in other files. A module exports the values other files may use, and imports values from other modules.

JavaScript has two module systems. CommonJS uses require and module.exports. Node.js created it in 2009, because the language had no modules then. ES modules (ESM) use import and export. They became part of the language in ES2015 and work in browsers and in Node.js.

Both are still in use, because hundreds of thousands of npm packages were written in CommonJS before Node.js supported ES modules in 2019.

TermMeaningIn the example
ModuleOne file with its own scope. It exports some values and imports others.src/counter.js
CommonJS (CJS)The original Node.js module system. require loads a file when that line runs.require("../src/counter.cjs")
ES module (ESM)The module system of the language standard. Imports are found and connected before any code runs.import { count } from "../src/counter.js"
module.exportsThe object a CommonJS file gives to every file that requires it. exports points to the same object at the start.module.exports = { count, increment }
SpecifierThe string after require or from. Relative, a package name, or a built-in module."./counter.js", "pino", "node:fs"
Module cacheStores each loaded module under its full path, so each file runs once per process.require.cache
Live bindingAn import that reads the exporting module's variable itself, not a copy of its value.count after increment()
Dual packageA package that ships an ES module file and a CommonJS file. The "exports" field in package.json picks one."import" and "require"
Main rule: write new code as ES modules. CommonJS loads each file when the require line runs and hands back a copy of its exported values. ES modules load and connect every file before any code runs, and imports read the exported variables directly.

Why there are two systems

YearWhat happened
Before 2009Browsers load scripts with <script> tags. All files share global variables. The language has no way to import a file.
2009Node.js starts and uses CommonJS. Files are on a local disk, so loading them synchronously at the require line is fast enough.
2015ES2015 adds import and export to the language. The design must also work in browsers, where files arrive over the network, so loading cannot block.
2017-2018Browsers support <script type="module">.
2019Node.js 13.2 supports ES modules without a flag.
2024-2025Node.js 22.12 and 20.19 let CommonJS code require an ES module without a flag.
2026Node.js 20 reached end of life in April. Both supported LTS versions, 24 (current LTS) and 22 (maintenance LTS), can require ES modules.

How CommonJS loads a file

require is a normal function. It can sit inside an if or a function, and its path can be built at run time. Each call goes through these steps before it returns.

StepWhat Node.js doesWhat it means for you
1. ResolveTurns the specifier into a full path. For a relative path it tries the exact name, then .js, .json, .node, then a folder's index.js. Package names are looked up in node_modules folders, from the current folder upwards.If the path is already in require.cache, steps 2 to 4 are skipped.
2. ReadReads the file from disk synchronously.The thread waits. Fine at startup, slow inside a request handler.
3. WrapPuts the file's text inside function (exports, require, module, __filename, __dirname) { ... }.Each file has its own scope. These five names are parameters, not globals.
4. RunStores the new module in require.cache, then calls the function once.The whole file runs before require returns.
5. ReturnReturns module.exports.Numbers and strings in it are copies taken when the file ran. Later changes to the module's variables do not reach the caller.

Circular requires do not fail. If first.cjs requires second.cjs and second.cjs requires first.cjs, the second file gets first.cjs's module.exports as it is at that moment: partly filled.

How ES modules load a file

Loading has three phases. No code runs until the first two have finished for every file in the graph.

PhaseWhat happensWhat it means for you
1. Parse and loadReads each file, finds its import and export statements without running it, then loads every imported file the same way, until the whole graph is known.Imports are static: a string literal at the top level of the file. They are processed first wherever they are written (hoisted). A missing file fails before any code runs.
2. LinkConnects every imported name to the exported variable in the other module.A misspelled import name fails before any code runs.
3. EvaluateRuns each module's top-level code once, dependencies first.An import is a live binding: the importer sees later changes to the exported variable. The importer cannot assign to it.

Other ES module features

FeatureExampleNotes
Strict modetotal = 5 without a declaration throwsAlways on. this at the top level is undefined.

Dynamic importawait import(`./plugins/${pluginName}.js`)Returns a promise. The path can be computed. Also works in CommonJS files.
import.metaimport.meta.url, import.meta.dirname, import.meta.filenameReplace __filename and __dirname. dirname and filename exist since Node.js 20.11.

JSON filesimport defaults from "./defaults.json" with { type: "json" }The with part is required. JSON modules have a default export only.

How Node.js decides which system a file uses

FileLoaded as
.cjsCommonJS, always
.mjsES module, always
.js with "type": "module"ES module
.js with "type": "commonjs"CommonJS
.js without "type"CommonJS. If the file contains import or export, Node.js 22.7 and later run it again as an ES module. Set "type" so Node.js does not parse twice.

Node.js reads "type" from the nearest package.json: the first one found from the file's folder upwards. For packages, the "exports" field in package.json lists the files other code may load. Conditions inside it choose a file by how it is loaded. Node.js uses the first condition that matches, so order matters.

ConditionMatches when
"import"The package is loaded with import or import()
"require"The package is loaded with require
"types"TypeScript looks for type definitions. Put it first.
"default"Always. Put it last, as the fallback.

Dual package hazard: if your app imports a dual package and one of your dependencies requires it, Node.js loads both files. You get two copies of the package with separate state, and instanceof checks between them fail. Every supported Node.js version can now require an ES module, so a package can ship one ES module file and avoid the problem.

Using one system from the other

CaseCodeWhat you get
import of CommonJSimport counter, { increment } from "./counter.cjs"The default export is module.exports. Named imports work only when Node.js finds the names by reading the source text, for patterns such as exports.name = and module.exports = { name }. Otherwise use the default import.
require in an ES moduleconst require = createRequire(import.meta.url)A require function from node:module, for require.resolve or native addons.
require of an ES moduleconst { formatPrice } = require("./format-price.js")Works without a flag since Node.js 22.12 and 20.19. Returns the module namespace object. A default export is under .default. Throws ERR_REQUIRE_ASYNC_MODULE if the module or anything it imports uses top-level await. Node.js 22 also prints an ExperimentalWarning the first time.
import() in CommonJSconst { settings } = await import("./load-settings.js")Works in every Node.js version, inside an async function. Also works with top-level await.

TypeScript and browsers

TypeScript source always uses import. The module setting in tsconfig.json decides what the compiled JavaScript uses.

Setting or tagWhat it does
"module": "nodenext"Uses the Node.js rules per file: .mts becomes an ES module, .cts becomes CommonJS, .ts follows "type". Relative imports are written with .js, the name of the compiled file.
"module": "commonjs"Compiles every import to require and every export to exports.name =.
"module": "esnext"Keeps import and export. Used with a bundler and "moduleResolution": "bundler".
"verbatimModuleSyntax": trueEmits each import as written and removes only import type. In a file that compiles to CommonJS, import syntax is a compile error.
<script type="module">The browser loads the file as an ES module: own scope, strict mode, runs after the HTML is parsed. Browsers do not support CommonJS.
<script type="importmap">Maps package names such as "order-pricing" to URLs, so the browser can resolve them without a bundler.

Which one to use

SituationUse
New app or serviceES modules, with "type": "module"
New libraryES modules only. CommonJS users on Node.js 22.12 or later can require it, as long as its entry graph has no top-level await.
Library that must support Node.js older than 20.19A dual package, or CommonJS
Large existing CommonJS appKeep CommonJS. New files can be ES modules, because CommonJS can now require them. Convert old files when you change them.
Tests built on jest.mockCommonJS, or move to a test runner with ES module mocking. jest.mock replaces modules through require.

Common errors and what they mean

Error code or nameMessage and causeFix
ReferenceErrorrequire is not defined in ES module scope. The file is an ES module, and require exists only in CommonJS.Use import, or createRequire(import.meta.url).
ReferenceError__dirname is not defined in ES module scope. Same cause: __dirname is a parameter of the CommonJS wrapper.Use import.meta.dirname.
SyntaxErrorCannot use import statement outside a module. A file loaded as CommonJS contains import: a .cjs file, "type": "commonjs", or a browser <script> without type="module".Rename to .mjs, set "type": "module", or add type="module".
ERR_MODULE_NOT_FOUNDCannot find module '/app/src/format-price'. A relative import without the file extension.Write "./format-price.js".
ERR_REQUIRE_ESMrequire of an ES module on Node.js older than 22.12 or 20.19.Upgrade Node.js, or use await import().
ERR_REQUIRE_ASYNC_MODULErequire of an ES module graph that uses top-level await.Use await import(), or remove the top-level await.
SyntaxErrorNamed export 'increment' not found. Node.js could not find that name in the CommonJS file's source text.Import the default export and read the property from it.

Logging module load errors

Diagram

Example flow:

Pick a flow and press Play to follow it through the diagram, step by step.

  1. You run node examples/copied-value.cjs. The file name ends in .cjs, so Node.js uses the CommonJS loader. The "type" field does not matter for .cjs files.
  2. The file calls require("../src/counter.cjs"). require is a normal function, so copied-value.cjs stops at this line until the call returns.
  3. Node.js turns the relative path into a full path, starting from the folder of the calling file. It looks for that path in require.cache. There is no entry yet.
  4. Node.js reads the file's text from disk. The read is synchronous: nothing else runs on the thread meanwhile.
  5. Node.js puts the text inside a function with five parameters. Variables in the file become local variables of that function, so the file has its own scope.
  6. Node.js stores a new module object in require.cache under the full path, then calls the function. The whole file runs now.
  7. counter.cjs sets module.exports = { count, increment }. count is 0 at this moment, so the object holds the number 0. require returns this object.
  8. A second require of the same path finds the cache entry and returns the same object. The file does not run again. Every file that requires counter.cjs shares this one object.
  1. CommonJS side: copied-value.cjs receives the object that counter.cjs put in module.exports. Its count property was copied from the variable when the file ran: 0.
  2. It calls counter.increment(). The variable count inside counter.cjs becomes 1. The property on the exported object is a separate copy, so it still prints 0.
  3. ES module side: live-binding.js imports count from counter.js. Linking connects the name count to the variable inside counter.js. Nothing is copied.
  4. It calls increment(). The variable in counter.js becomes 1. The importer reads that same variable, so it prints 1. This is a live binding.
  5. Imported bindings are read-only. count = 5 in the importer throws a TypeError. Only counter.js can change its own variable, through increment().
  1. You run node src/index.js. The nearest package.json has "type": "module", so Node.js uses the ES module loader for this .js file.
  2. Node.js parses index.js without running it and lists its imports: ./format-price.js and ./counter.js. An import written at the bottom of a file is found here too, so it works as if written at the top.
  3. Node.js loads and parses both files, then their imports, until it knows the whole graph. A missing file fails here with ERR_MODULE_NOT_FOUND, before any of your code has run.
  4. Node.js connects every imported name to the exported variable. A misspelled name, such as formatPrise, fails here with SyntaxError: The requested module './format-price.js' does not provide an export named 'formatPrise'.
  5. Node.js runs each module's top-level code once, dependencies first: format-price.js, counter.js, then index.js.
  6. If a module uses top-level await, the modules that import it wait until its promise settles. Other work on the event loop continues meanwhile.
  1. CommonJS: you run node examples/circular/first.cjs. Its module is in require.cache and it runs. It sets exports.isLoaded = false, then calls require("./second.cjs").
  2. second.cjs is not in the cache, so it is loaded and starts to run. It calls require("./first.cjs").
  3. first.cjs is in the cache, still running. Node.js returns its exports as they are now, without an error. second.cjs sees isLoaded as false.
  4. second.cjs finishes, and first.cjs continues. Anything first.cjs exports after its require line was missing when second.cjs read it. With const { name } = require(...), it stays undefined.
  5. ES modules: first.js imports from second.js, and second.js imports from first.js. Loading and linking work, because linking connects names before any code runs.
  6. second.js runs first, because first.js depends on it. It reads firstLabel, a const that has not been set yet, and throws. Fix: move shared values to a third module, or read them inside a function that runs later.
  1. ES module loading CommonJS: import-commonjs.js is an ES module. Parsing finds import counter, { increment } from "../src/counter.cjs".
  2. The file ends in .cjs, so the CommonJS loader wraps and runs it, as it would for require. Its module.exports goes into require.cache.
  3. The default import is module.exports. Named imports work only if Node.js found the names by reading the file's source text. Here it finds module.exports = { count, increment }.
  4. CommonJS loading an ES module: require-esm.cjs calls require("../src/format-price.js"). On Node.js 22.12 or 20.19 and later, the ES module loader runs the graph synchronously and require returns its namespace object.
  5. Next it calls require("./load-settings.js"). That module uses top-level await, and require cannot wait for a promise. It throws ERR_REQUIRE_ASYNC_MODULE before the module runs.
  6. await import("./load-settings.js") inside an async function works. It returns a promise, so top-level await is allowed. It also works on Node.js versions that throw ERR_REQUIRE_ESM for require.

Problems ES modules solve

  • Errors found lateMissing files and misspelled import names fail before any code runs, not halfway through a request.
  • Two module formats for browser and serverThe same import syntax runs in browsers, Node.js, Deno and Bun.
  • Large bundlesStatic imports let bundlers remove code that nothing imports.
  • Async setup at startupTop-level await loads settings or connects to a database before other modules use them.
  • Stale exported valuesLive bindings show the exporting module's current value.

Problems ES modules introduce

  • Stricter pathsRelative imports need the file extension, and folders need an explicit index.js.
  • Missing CommonJS namesrequire, __dirname and __filename do not exist. Use import.meta and createRequire.
  • Limits when mixingNamed imports from CommonJS work only when Node.js can find them, and require fails on top-level await.
  • Dual package hazardShipping both formats can load two copies of one package.
  • Older toolsSome tools, such as jest.mock, were built around require.

const formattersByCurrency = new Map();

export function formatPrice(amountInCents, currency) {
  if (!formattersByCurrency.has(currency)) {
    formattersByCurrency.set(currency, new Intl.NumberFormat("en-US", { style: "currency", currency }));
  }
  return formattersByCurrency.get(currency).format(amountInCents / 100);
}

ES moduleexamples/load-settings.jsTop-level await, a JSON import and import.meta. Modules that import settings wait until the file read finishes. Because of the top-level await, CommonJS cannot require this file and must use import().
import { readFile } from "node:fs/promises";
import path from "node:path";
import defaults from "../src/defaults.json" with { type: "json" };

const localSettingsPath = path.join(import.meta.dirname, "settings.local.json");

async function readLocalOverrides() {
  try {
    return JSON.parse(await readFile(localSettingsPath, "utf8"));
  } catch (error) {
    if (error.code === "ENOENT") return {};
    throw error;
  }
}

export const settings = { ...defaults, ...(await readLocalOverrides()) };

console.log("loaded", import.meta.filename, "from", import.meta.url);
ES moduleexamples/load-plugins.jsLoads plugins named in an environment variable with import(). The path is relative to this file, not to the folder you started Node.js in. A failed load is logged with the plugin name, specifier and error.code, then the process exits.
import pino from "pino";

const logger = pino();
const pluginNames = (process.env.PLUGINS ?? "").split(",").filter(Boolean);

for (const pluginName of pluginNames) {
  const specifier = `../plugins/${pluginName}.js`;
  let plugin;
  try {
    plugin = await import(specifier);
  } catch (error) {
    logger.fatal({ err: error, pluginName, specifier, code: error.code }, "plugin failed to load");
    process.exit(1);
  }
  plugin.register();
  logger.info({ pluginName }, "plugin loaded");
}
