Event Loop

How JavaScript does many things at once with one thread, in browsers and in Node.js.

What it is

JavaScript runs your code on one thread, one function at a time. Waiting work, such as a timer, a network request or reading a file, is handed to the browser or to Node.js, which wait outside your thread. When the wait is over, they put a callback in a queue.

The event loop is the cycle that decides what runs next. Each turn, it waits until the call stack is empty, then runs every callback in the microtask queue, then takes one callback from the task queue. In a browser, it may also redraw the page between turns.

Promise callbacks and the code after await are microtasks. Timer callbacks, finished network requests and clicks are tasks. That is why a resolved promise always runs before a setTimeout(..., 0) callback.

Main rule: JavaScript runs one piece of your code at a time. Code that runs long without giving the thread back stops everything else on it: timers, other requests, clicks and page updates.

The Node.js loop, phase by phase

Node.js splits the task queue into phases. The Node.js page shows where the loop sits inside Node.js, next to V8 and the thread pool. Each turn of the loop visits them in this order. Between every single callback, Node.js runs all process.nextTick callbacks first, then all promise microtasks.

PhaseRuns
1. TimerssetTimeout and setInterval callbacks whose time has come
2. Pending callbacksSome I/O error callbacks held back from the previous turn
3. PollCallbacks for finished I/O: network, files. Waits here when there is nothing else to do.
4. ChecksetImmediate callbacks
5. Close callbacksclose events, such as a socket closing

Inside an I/O callback, setImmediate runs before setTimeout(..., 0), because the check phase comes before the loop returns to timers. Click "Event loop" in the diagram to see this.

Diagram

Example flow:

Pick a flow and press Play to follow it through the diagram, step by step.

  1. The script starts as the first frame on the call stack and prints 1: script start.
  2. It calls setTimeout(cb, 0). The callback function is stored in the heap, and the timer is handed to the browser or Node.js, which counts 0 ms outside the thread.
  3. setTimeout returns and leaves the stack. The time is up at once, so the timeout callback goes into the task queue. It must wait for its turn.
  4. The script resolves a promise and calls queueMicrotask. Two callbacks go into the microtask queue, in that order.
  5. The script prints 2: script end and finishes. The call stack is now empty, so the event loop can act.
  6. Microtasks come first. The loop moves the first microtask to the stack. It prints 3: promise callback.
  7. The microtask queue is not empty yet, so the loop runs the next one. It prints 4: queueMicrotask callback.
  8. The microtask queue is empty, so the loop takes one task: 5: timeout callback. The functions stay in the heap until the garbage collector frees them.
  1. The script starts on the call stack and prints 1: before.
  2. It calls the async function loadOrders, which goes on top of the stack and prints 2: request sent.
  3. At await fetch(...), the request is handed to the network layer. loadOrders saves its local variables in the heap and leaves the call stack.
  4. The script goes on, prints 3: after and finishes. The stack is empty while the request travels, so the thread can handle other work.
  5. The response arrives. The network layer puts a task in the task queue.
  6. The loop runs that task. It resolves the promise, which puts the rest of loadOrders in the microtask queue.
  7. The loop runs that microtask. loadOrders is back on the stack with its saved variables and prints 4: response arrived.
  1. A Node.js server gets a request for /slow-report. Its handler calls a loop that takes 2 seconds and never awaits, so both frames stay on the stack.
  2. Meanwhile, a /health request, a 100 ms timer and another request arrive. Their callbacks wait in the task queue.
  3. The event loop can only move a task when the call stack is empty. It is not, so every other user waits, even for /health.
  4. After 2 seconds the handler returns and the stack is empty. Only now does /health get its turn, 2 seconds late.
  5. The fix is to give the thread back: split the work into pieces with setImmediate between them, or move it to a worker thread. Click "Task queue" or see the worker file.
  1. The script sets a 0 ms timer. Its callback goes into the task queue.
  2. It calls queueAgainForever, which puts itself in the microtask queue.
  3. The script ends. The loop runs the microtask, and that run puts queueAgainForever in the microtask queue again.
  4. The loop must empty the microtask queue before any task, but it is never empty. The timer callback never runs, and in a browser the page never redraws.

Problems it solves

  • Many waiting operationsOne thread can have thousands of network requests or file reads in progress, because waiting happens outside it.
  • Locks around shared dataTwo pieces of your code never run at the same moment on one thread, so plain objects need no locks.
  • Memory per connectionNo thread per request, so each open connection costs little memory.
  • Unclear order of callbacksThe rules are fixed: plain code, then all microtasks, then one task.

Problems it introduces

  • CPU-heavy work blocks everythingLarge JSON parsing, hashing or long loops delay every other request and timer.
  • One slow handler affects all usersA bug in one route can make the whole service slow, not only that route.
  • Endless microtasksA promise chain that keeps adding work stops timers and, in browsers, page updates.
  • One CPU core per processTo use more cores, run several processes or add worker threads.
  • Unhandled rejectionsA promise error that nobody catches stops a Node.js process by default.

import { readFile } from "node:fs";

readFile(import.meta.filename, () => {
  setTimeout(() => console.log("4: timers phase, next turn of the loop"), 0);
  setImmediate(() => console.log("3: check phase, this turn of the loop"));
  Promise.resolve().then(() => console.log("2: promise microtask"));
  process.nextTick(() => console.log("1: process.nextTick"));

Blockingblocking-server.jsWhile one request for /slow-report runs the loop, every other request, including /health, waits up to 2 seconds. A load balancer may even decide the server is down.
import http from "node:http";

function keepThreadBusyFor(milliseconds) {
  const end = Date.now() + milliseconds;
  while (Date.now() < end) {}
}

http
  .createServer((req, res) => {
    if (req.url === "/slow-report") {
      keepThreadBusyFor(2000);
      return res.end("report done");
    }
    res.end("ok");
  })
  .listen(3000);

Fix: split worksplit-work.jsPrices 1,000 products, then awaits setImmediate, which gives the thread back for one turn of the loop. Other requests and timers run between batches. The total time is about the same, but nobody waits long.
import { setImmediate as waitForNextLoopTurn } from "node:timers/promises";

const batchSize = 1000;

function calculatePrice(product) {
  return Math.round(product.basePrice * (1 + product.taxRate) * 100) / 100;
}

export async function priceAllProducts(products) {
  for (let start = 0; start < products.length; start += batchSize) {
    for (const product of products.slice(start, start + batchSize)) {
      product.price = calculatePrice(product);
    }
    await waitForNextLoopTurn();
  }
}
Fix: worker threadreport-worker.jsThe same file runs twice: once as the main thread, which starts a worker, and once as the worker, which does the heavy work on its own thread and event loop. The main thread stays free and gets the result as a message.
import { Worker, isMainThread, parentPort, workerData } from "node:worker_threads";

function buildRevenueReport(orders) {
  let totalRevenue = 0;
  for (const order of orders) totalRevenue += order.total;
  return { orderCount: orders.length, totalRevenue };
}

if (isMainThread) {
  const orders = Array.from({ length: 5_000_000 }, (_, index) => ({ total: index % 100 }));
  const worker = new Worker(new URL(import.meta.url), { workerData: { orders } });

  worker.on("message", (report) => console.log("report ready", report));
  worker.on("error", (error) => console.error("report failed", error));
  console.log("main thread is free while the worker counts");
} else {
  parentPort.postMessage(buildRevenueReport(workerData.orders));
}
Monitoringevent-loop-delay.jsMeasures how late the loop runs scheduled work. Every 10 seconds it logs the 99th percentile and the maximum, as a warning when the 99th percentile is over 100 ms. unref keeps this timer from holding the process open.
import { monitorEventLoopDelay } from "node:perf_hooks";
import pino from "pino";

const logger = pino();
const loopDelay = monitorEventLoopDelay({ resolution: 20 });
loopDelay.enable();

setInterval(() => {
  const p99Milliseconds = Math.round(loopDelay.percentile(99) / 1e6);
  const maxMilliseconds = Math.round(loopDelay.max / 1e6);
  const level = p99Milliseconds > 100 ? "warn" : "info";

  logger[level]({ p99Milliseconds, maxMilliseconds }, "event loop delay");
  loopDelay.reset();
}, 10_000).unref();
