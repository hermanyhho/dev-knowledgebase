JavaScript / Node

Node.js

A program that runs JavaScript outside the browser. Created by Ryan Dahl in 2009.

What it is

Node.js runs JavaScript on servers, laptops and build machines. It is not a language or a framework. It is a runtime: a program you start with node server.js, which reads your JavaScript and runs it.

It is built from two main parts. V8, the JavaScript engine from Google Chrome, turns your JavaScript into machine code and runs it. libuv, a C library, runs the event loop and does the waiting: network, files, timers. On top sit the core modules, such as fs and http, which give JavaScript access to the operating system.

Your JavaScript runs on one main thread. Network waiting needs no extra threads, because the operating system tells libuv when data arrives. Work that the operating system cannot do without blocking, such as reading files or hashing passwords, goes to a small thread pool inside libuv.

Running Node.js in production

TopicWhat to do
VersionUse an LTS release and pin it in package.json under engines and in the Docker image tag.
Using more than one coreRun several containers or processes, about one per CPU core, behind a load balancer.
Shutting downOn SIGTERM, stop taking new requests, finish the ones in progress, close database pools, then exit.
CrashesLog uncaught exceptions and unhandled rejections, then exit and let the container restart. The process may be in a broken state.
MemorySet --max-old-space-size below the container's memory limit, so V8 cleans up before the container is killed.
Running as rootDo not. The official image has a node user.

Diagram

Example flow:

Pick a flow and press Play to follow it through the diagram, step by step.

  1. A browser connects and sends an HTTP request. The bytes arrive at the operating system's network stack.
  2. The operating system tells libuv that the socket has data. No thread was waiting on this socket.
  3. On its next turn, the event loop passes the bytes to the http core module, which parses the request.
  4. V8 runs your request handler on the main thread.
  5. Your handler writes the response. libuv hands the bytes to the operating system to send. Again, no thread pool is used.
  1. Your code calls await readFile("orders.csv") from node:fs/promises.
  2. Most operating systems have no general non-blocking file API, so libuv gives the read to one of its 4 pool threads.
  3. That pool thread makes a normal, blocking read call. The main thread is not affected.
  4. When the read finishes, the pool thread tells the event loop. The rest of your function continues on the main thread.
  1. Five users log in at the same moment. Your code calls crypto.pbkdf2 five times to check their passwords.
  2. Hashing is slow on purpose, about 100 ms each. Four calls take the four pool threads.
  3. The fifth hash waits for a free thread, so it takes about 200 ms. A file read started now would also wait.
  4. Options: set UV_THREADPOOL_SIZE higher, up to the number of CPU cores, or run more processes. Click "Thread pool" to see the timing program.
  1. V8 reads your JavaScript and first runs it quickly without much optimization.
  2. Functions that run often are compiled again into faster machine code. This is just-in-time compilation.
  3. From time to time, V8 pauses your code to free memory that nothing uses any more. Short pauses are normal. Long ones show up as event loop delay.
  4. If the heap reaches its limit, the process crashes with "heap out of memory". Set the limit with --max-old-space-size, below the container's limit.

Problems it solves

  • Many connections, little memoryOne thread handles thousands of open connections, because the operating system does the waiting.
  • Two languages for one productFrontend and backend can share JavaScript or TypeScript code, types and developers.
  • Slow start for small servicesA working HTTP server is a few lines, and it starts in well under a second.
  • Finding librariesnpm has packages for almost every protocol, database and file format.
  • Locks around shared dataYour code runs on one thread, so in-memory data needs no locks.

Problems it introduces

  • CPU-heavy work blocks the serverReports, image work or big JSON files need worker threads or a different service.
  • One core per processUsing a whole machine needs several processes or containers.
  • A small thread poolFile access, DNS lookups and password hashing share 4 threads by default.
  • Many small dependenciesOne package can pull in hundreds of others. Each is code you run and must keep updated.
  • A crash stops every requestAn unhandled error ends the process, and every request in it.
  • Two module systemsES modules and CommonJS mix poorly, which causes import errors in older packages.

Serversrc/server.jsA complete small service: JSON logs to standard output, a startup log, a clean shutdown on SIGTERM, and exit after an unexpected error so the container restarts.
import http from "node:http";
import pino from "pino";

const logger = pino();
const port = Number(process.env.PORT ?? 3000);

const server = http.createServer((req, res) => {
  if (req.url === "/health") return res.end("ok");
  res.setHeader("Content-Type", "application/json");
  res.end(JSON.stringify({ message: "hello from Node.js" }));
});

server.listen(port, () => {
  logger.info({ nodeVersion: process.version, port, environment: process.env.NODE_ENV }, "server started");
});

process.on("SIGTERM", () => {
  logger.info("SIGTERM received, closing the server");
  server.close(() => {
    logger.info("all open requests finished, exiting");
    process.exit(0);
  });
});

process.on("uncaughtException", (error) => {
  logger.fatal({ err: error }, "uncaught exception, exiting");
  process.exit(1);
});

process.on("unhandledRejection", (reason) => {
  logger.fatal({ err: reason }, "unhandled promise rejection, exiting");
  process.exit(1);
});

Event loopexamples/many-connections.jsAn echo server. Idle connections cost only a little memory each, because no thread waits on them: the operating system tells libuv when one has data. Thousands of open connections still run on one JavaScript thread.
import net from "node:net";

let openConnections = 0;

net
  .createServer((socket) => {
    openConnections += 1;
    socket.on("data", (chunk) => socket.write(chunk));
    socket.on("close", () => {
      openConnections -= 1;
    });
  })
  .listen(4000);

setInterval(() => {
  console.log({ openConnections, heapUsedMegabytes: Math.round(process.memoryUsage().heapUsed / 1e6) });
}, 5000);
Thread poolexamples/thread-pool-limit.jsStarts five slow hashes at once and prints when each finishes. With the default pool of 4, the first four finish together and the fifth about twice as late. Run it again with UV_THREADPOOL_SIZE=8 node thread-pool-limit.js and all five finish together.
import { pbkdf2 } from "node:crypto";

const startedAt = Date.now();

for (let hashNumber = 1; hashNumber <= 5; hashNumber++) {
  pbkdf2("password", "salt", 600_000, 64, "sha512", () => {
    console.log(`hash ${hashNumber} done after ${Date.now() - startedAt} ms`);
  });
}
V8 memoryexamples/memory-usage.jsLogs the V8 heap and the whole process memory every 30 seconds. If both keep growing over hours, something keeps objects alive: a memory leak. heapLimitMegabytes shows the limit set with --max-old-space-size.
import { getHeapStatistics } from "node:v8";
import pino from "pino";

const logger = pino();
const bytesPerMegabyte = 1024 * 1024;

setInterval(() => {
  const memory = process.memoryUsage();
  logger.info(
    {
      heapUsedMegabytes: Math.round(memory.heapUsed / bytesPerMegabyte),
      rssMegabytes: Math.round(memory.rss / bytesPerMegabyte),
      heapLimitMegabytes: Math.round(getHeapStatistics().heap_size_limit / bytesPerMegabyte),
    },
    "memory usage",
  );
}, 30_000).unref();
