NestJS Modules and Providers

How a NestJS app is split into modules, and how Nest creates each class and passes it the objects it needs. Examples use NestJS 12.

What it is

NestJS is a framework for Node.js servers, written in TypeScript. It runs on top of Express by default, or Fastify, and adds a fixed structure: modules, controllers and providers.

A provider is a class, usually a service, that does work for others. You never write new OrdersService(...). You list the class in a module, and write the classes it needs as constructor parameters. At startup Nest reads those parameter types, creates every object in the right order and passes each one its dependencies. This is dependency injection, and the part of Nest that does it is the IoC container.

A module groups the controllers and providers of one feature. A provider is private to its module unless the module exports it, and another module can only use it after importing that module.

TermMeaningIn the example
ModuleA class with @Module() that lists its controllers, providers, imports and exports.OrdersModule
ProviderAnything Nest can create and inject, most often a class with @Injectable().OrdersService
ControllerA class with @Controller() whose methods handle HTTP routes.OrdersController

IoC containerThe part of Nest that creates providers and injects them. IoC means inversion of control: the framework creates your objects.Runs at startup
Injection tokenThe key Nest uses to find a provider. A class is its own token; other providers use a string or symbol.PAYMENT_GATEWAY
DecoratorA function written as @Name() above a class or method. Nest uses decorators to store information about your classes.@Injectable()
ScopeHow long a provider instance lives: the whole app, one request, or one injection.Scope.REQUEST
Main rule: one module per feature. Export only the providers that other modules need, and depend on a token instead of a class when you want to swap the implementation in tests.

What Nest does at startup

StepWhat happens
1. ScanStarting at AppModule, Nest follows every imports list and collects all modules.
2. Read the parametersFor each provider and controller, it reads the constructor parameter types. TypeScript stored them in the compiled JavaScript as design:paramtypes metadata.
3. Check visibilityEach dependency must be a provider in the same module, or exported by an imported module. If not, startup fails.
4. CreateIt creates providers without dependencies first, then the ones that use them. Each default-scope provider is created once.
5. Map routesIt registers each controller method as a route on Express or Fastify, and logs the list.

Provider scopes

ScopeInstancesCost
DEFAULTOne for the whole appNone per request. Use it unless you have a reason not to.
REQUESTA new one for each HTTP requestEvery class that injects it also becomes request-scoped, up to the controller. In a test, two requests created two services and two controllers.
TRANSIENTA new one for each class that injects itNo sharing between consumers

To read per-request data such as the user or the request ID in a default-scope service, pass it as a method argument, or use AsyncLocalStorage instead of a request-scoped provider.

Common mistakes

MistakeWhat you seeFix
The provider is not exported, or its module is not importedStartup fails: Nest can't resolve dependencies of the OrdersService (?)Add it to exports and import the module
Running the code with a tool that drops decorator metadata, such as tsx or esbuildThe dependency is undefined. The first request fails with TypeError: Cannot read properties of undefined.Build with tsc or swc, which write the metadata
Importing a type with import type for a constructor parameterSame as above: there is no class at runtime to readImport the class with a normal import
Two modules that import each otherA circular dependency error at startupMove the shared part into a third module. forwardRef is a last resort.
A request-scoped provider deep in the graphSlower requests: many objects created per requestKeep providers in the default scope

Example flow:

Pick a flow and press Play to follow it through the diagram, step by step.

  1. main.ts calls NestFactory.create(AppModule).
  2. Nest follows the imports of AppModule and finds OrdersModule and PaymentsModule.
  3. The container reads each constructor's parameter types from the metadata that tsc wrote. OrdersService needs PaymentsService; PaymentsService needs PAYMENT_GATEWAY.
  4. It creates the classes without dependencies first: the gateway from its factory, then PaymentsService with the gateway.
  5. Then OrdersService with PaymentsService, then OrdersController. Each is created once and shared.
  6. Nest maps the controller's routes on Express and logs Nest application successfully started.
  1. Someone removes PaymentsService from the exports of PaymentsModule.
  2. OrdersModule still imports PaymentsModule, but now sees none of its providers.
  3. Startup stops: Nest can't resolve dependencies of the OrdersService (?). Please make sure that the argument PaymentsService at index [0] is available in the OrdersModule module.
  4. The ? marks the parameter that failed. Exporting the service again fixes it.
  1. The app is started with tsx src/main.ts to skip the build. tsx uses esbuild, which removes types but does not write decorator metadata.
  2. The container finds no parameter types for OrdersController. It does not fail. It passes undefined.
  3. The app starts. The first request fails with TypeError: Cannot read properties of undefined (reading 'pay') and a 500 response.
  4. Build with tsc, or with swc, which writes the metadata. Node.js type stripping cannot run Nest code either, because decorators with metadata are not erasable syntax.
  1. OrdersService is changed to @Injectable({ scope: Scope.REQUEST }) to read the current user.
  2. OrdersController injects it, so the controller can no longer be shared either. Nest creates both for every request.
  3. Providers that OrdersService uses, such as PaymentsService, keep their default scope. Only consumers are affected.
  4. Measured in a small app: after 2 requests, 2 services and 2 controllers had been created. Pass the user as a method argument instead.
  1. In production, PAYMENT_GATEWAY is a client for the card provider, built from configuration.
  2. The test builds OrdersModule with Test.createTestingModule and replaces the token with overrideProvider(PAYMENT_GATEWAY).useValue(fakeGateway).
  3. The container injects the fake into PaymentsService. Nothing else changes.
  4. The test calls OrdersService and checks what the fake received. No network call is made.

Problems it solves

  • Wiring objects by handNest creates every service in the right order and passes it what it needs.
  • Code that is hard to testA test replaces one provider with a fake and leaves the rest as it is.
  • A large app with no structureModules give each feature a boundary, and exports decide what others may use.
  • Every team doing it differentlyNest projects share one layout, so a developer can move between them.

Problems it introduces

  • Depends on compiler metadataTools that skip decorator metadata, and Node.js type stripping, break injection.
  • Errors at startupA missing export stops the whole app, and the message must be read carefully.
  • More code per featureA module, a controller and a service, each with decorators, for even a small endpoint.
  • Hidden costsOne request-scoped provider can make a chain of classes request-scoped.
Entrysrc/main.tsNestJS 12 is published as ES modules, so the project uses "type": "module" and top-level await. The JSON logger writes one object per line for the log platform. enableShutdownHooks lets providers close connections on SIGTERM.
import { ConsoleLogger } from "@nestjs/common";
import { NestFactory } from "@nestjs/core";
import { AppModule } from "./app.module.js";

const app = await NestFactory.create(AppModule, {
  logger: new ConsoleLogger({ json: true }),
});
app.enableShutdownHooks();
await app.listen(Number(process.env.PORT ?? 3000));
Modulesrc/app.module.tsThe root module lists the feature modules. ConfigModule.forRoot is a dynamic module: a function that returns a module configured for this app. isGlobal makes ConfigService injectable everywhere without importing it again. It comes from the @nestjs/config package.
import { Module } from "@nestjs/common";
import { ConfigModule } from "@nestjs/config";
import { OrdersModule } from "./orders/orders.module.js";
import { PaymentsModule } from "./payments/payments.module.js";

@Module({
  imports: [ConfigModule.forRoot({ isGlobal: true }), OrdersModule, PaymentsModule],
})
export class AppModule {}
Modulesrc/orders/orders.module.tsThe orders feature: its controller, its service, and the module it needs. OrdersService is not exported, so no other module can inject it.
import { Module } from "@nestjs/common";
import { PaymentsModule } from "../payments/payments.module.js";
import { OrdersController } from "./orders.controller.js";
import { OrdersService } from "./orders.service.js";

@Module({
  imports: [PaymentsModule],
  controllers: [OrdersController],
  providers: [OrdersService],
})
export class OrdersModule {}
Controllersrc/orders/orders.controller.tsThe controller only handles HTTP: it reads the route parameter and calls the service. private readonly in the constructor declares the property and assigns it. Nest knows to pass an OrdersService because of the parameter's type.
import { Controller, Param, Post } from "@nestjs/common";
import { OrdersService } from "./orders.service.js";

@Controller("orders")
export class OrdersController {
  constructor(private readonly ordersService: OrdersService) {}

  @Post(":orderId/pay")
  pay(@Param("orderId") orderId: string) {
    return this.ordersService.pay(orderId);
  }
}
Providersrc/orders/orders.service.tsPaymentsService is imported as a normal import, not import type, because Nest needs the class at runtime. The logger adds OrdersService as the context of every line.
import { Injectable, Logger } from "@nestjs/common";
import { PaymentsService } from "../payments/payments.service.js";

@Injectable()
export class OrdersService {
  private readonly logger = new Logger(OrdersService.name);

  constructor(private readonly paymentsService: PaymentsService) {}

  async pay(orderId: string) {
    const payment = await this.paymentsService.charge(orderId);
    this.logger.log({ message: "order paid", orderId, paymentId: payment.id });
    return { orderId, paymentId: payment.id };
  }
}
Modulesrc/payments/payments.module.tsexports is the public part of the module. PaymentsService is exported. The gateway is not: other modules use payments only through the service.

Providersrc/payments/payments.service.tsThe gateway is an interface, which does not exist at runtime, so Nest cannot find it by type. @Inject(PAYMENT_GATEWAY) names the token instead.
import { Inject, Injectable } from "@nestjs/common";
import { PAYMENT_GATEWAY, type PaymentGateway } from "./payment-gateway.provider.js";

@Injectable()
export class PaymentsService {
  constructor(@Inject(PAYMENT_GATEWAY) private readonly gateway: PaymentGateway) {}

  charge(orderId: string) {
    return this.gateway.charge({ orderId, idempotencyKey: `order-${orderId}` });
  }
}
Providersrc/payments/payment-gateway.provider.tsA factory provider. Nest calls the function once at startup with the services listed in inject, and provides what it returns under the token. getOrThrow stops startup if the key is missing.
import type { FactoryProvider } from "@nestjs/common";
import { ConfigService } from "@nestjs/config";

export const PAYMENT_GATEWAY = Symbol("PAYMENT_GATEWAY");

export type PaymentGateway = {
  charge(request: { orderId: string; idempotencyKey: string }): Promise<{ id: string }>;
};

export const paymentGatewayProvider: FactoryProvider<PaymentGateway> = {
  provide: PAYMENT_GATEWAY,
  inject: [ConfigService],
  useFactory: (config: ConfigService): PaymentGateway => {
    const apiKey = config.getOrThrow<string>("CARD_PROVIDER_API_KEY");
    return {
      async charge(request) {
        const response = await fetch("https://payments.example.com/charges", {
          method: "POST",
          headers: { Authorization: `Bearer ${apiKey}`, "Idempotency-Key": request.idempotencyKey },
          body: JSON.stringify({ orderId: request.orderId }),
        });
        return (await response.json()) as { id: string };
      },
    };
  },
};
Testsrc/orders/orders.service.spec.tsThe test builds the real OrdersModule and replaces only the gateway token with a fake. Uses @nestjs/testing and node:test. ConfigModule is added because the real factory provider is still registered before it is replaced.
import assert from "node:assert/strict";
import { describe, it } from "node:test";
import { ConfigModule } from "@nestjs/config";
import { Test } from "@nestjs/testing";
import { PAYMENT_GATEWAY } from "../payments/payment-gateway.provider.js";
import { OrdersModule } from "./orders.module.js";
import { OrdersService } from "./orders.service.js";

describe("when an order is paid", () => {
  it("should charge the gateway once with the order's idempotency key", async () => {
    const charges: { orderId: string; idempotencyKey: string }[] = [];
    const fakeGateway = { charge: async (request: { orderId: string; idempotencyKey: string }) => (charges.push(request), { id: "pay-1" }) };
    const testingModule = await Test.createTestingModule({ imports: [ConfigModule.forRoot(), OrdersModule] })
      .overrideProvider(PAYMENT_GATEWAY)
      .useValue(fakeGateway)
      .compile();

    await testingModule.get(OrdersService).pay("o-1");

    assert.deepEqual(charges, [{ orderId: "o-1", idempotencyKey: "order-o-1" }]);
  });
});
