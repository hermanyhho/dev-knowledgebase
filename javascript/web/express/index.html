JavaScript / Web

Express

A small web framework for Node.js. A request passes through a list of functions, one after another.

What it is

Express is a thin layer on top of the node:http module from Node.js. Node.js parses the HTTP request. Express adds routing, helper methods such as res.json(), and a middleware chain.

A middleware is a function (req, res, next). You register middleware with app.use(), and Express calls them in that order for every request. Each one either sends a response or calls next() to hand the request to the next function. Routes are middleware too: they only run when the method and path match.

Express has no validation, no schemas and no security defaults. You add each of those with a package.

TermMeaningIn the example

express.json()Middleware that reads the request body, parses it as JSON and stores it in req.body.Only for Content-Type: application/json

Main rule: every middleware must either send a response or call next(). Register middleware in the order a request should pass through them, and the error middleware last.

What a middleware function can do

The middlewareWhat happens nextExample
Calls next()Express runs the next middleware or route that matches the path.helmet() sets headers, then calls next()
Sends a responseThe request ends. No later middleware or route runs.Auth replies 401 when the token is missing
Calls next(error) or throwsExpress skips all normal middleware and routes, and runs the next error middleware.express.json() gets invalid JSON
Does neitherNothing else runs and the client gets no answer. The request stays open until the client or the load balancer gives up.A middleware that forgets next()

Why middleware order matters

Express keeps one list of middleware and routes, in the order of your app.use() and app.get() calls. For each request it walks that list from the top. Each mistake below comes from a wrong position in that list.

MistakeSymptomFix
express.json() registered after the routesreq.body is undefined in every handlerRegister body parsers before the routers.
Error middleware registered before the routesErrors get the default Express HTML error pageRegister the error middleware last.
Auth registered before /healthThe load balancer's health check gets 401 and marks the server as downRegister public routes first, or mount auth on /api only.
Request logger registered after a middleware that can end the requestRejected requests have no log line and no request IDRegister the request ID and logger middleware first.
404 handler registered before the routersEvery request gets 404Register it after all routes, before the error middleware.

Why Express is slower than Fastify

The Fastify page explains how its hooks and schemas work.

StepExpressFastify
Finding the routeWalks the middleware and route list from the top and tests each path pattern. More routes means more checks.Looks up the path in a tree built at startup. The cost depends on the path length, not the number of routes.
Writing the JSON responseJSON.stringify on every responseA serializer compiled from the response schema, which is faster and drops fields not in the schema
Validating the requestNot included. Each zod call runs at request time.JSON Schema compiled once at startup
MiddlewareEvery app.use() function runs for every request it matchesHooks run only for the routes in the plugin that registered them

In "hello world" benchmarks Fastify handles about two to three times as many requests per second. In most real APIs, database and network time is larger than this difference. Express is still the most used Node.js framework, with the most examples and middleware.

Running Express in production

TopicWhat to do
Graceful shutdownOn SIGTERM, call server.close(). It stops new connections, waits for open requests, and since Node.js 19 closes idle keep-alive connections. Then close the database pool and exit. Force an exit after about 10 seconds.
Behind a load balancerSet app.set("trust proxy", 1) so req.ip and req.protocol come from the X-Forwarded-* headers of your own proxy.
Keep-alive timeoutSet server.keepAliveTimeout longer than the load balancer's idle timeout. Otherwise Node.js closes connections the load balancer still uses, and clients get 502.
Body sizeexpress.json() accepts 100 KB by default and replies 413 above that. Raise the limit only on routes that need it.
NODE_ENV=productionSet it. Without it, the default error handler sends stack traces to the client.
Slow handlersCPU-heavy code in a handler blocks every other request. See the event loop page.

Diagram

Example flow:

Pick a flow and press Play to follow it through the diagram, step by step.

  1. The client sends GET /api/orders/42 with a token. Node's http module parses the request and calls the Express app with req and res.
  2. pino-http takes the x-request-id header or creates a new ID, sets it on the response, and adds req.log. Then it calls next().
  3. helmet adds security headers to the response. cors and compression do their part. Each calls next().
  4. A GET request has no JSON body, so express.json() reads nothing and calls next().
  5. The auth middleware checks the token, stores the user in req.user and calls next().
  6. The router matches /:orderId and sets req.params.orderId to the string "42".
  7. The handler loads the order and calls res.json(order). When the response is sent, pino-http writes one log line with status 200 and the response time.
  1. The client sends GET /api/orders/42 without an Authorization header. The request gets an ID.
  2. helmet, cors, compression and express.json() each call next(), as in a normal request.
  3. The auth middleware finds no token and calls res.status(401).json(...). It does not call next(), so the router and handler never run.
  4. pino-http still writes the log line, at warn level, because it was registered before auth.
  1. The client sends POST /api/orders with a valid body and token. All middleware call next() and the router picks createOrder.
  2. The async handler awaits orderRepository.insert(). The database is down, so the promise rejects.
  3. Express 5 catches the rejected promise and calls next(error). It skips any normal middleware and runs the error middleware. In Express 4 the request would hang.
  4. The error middleware sets res.err, replies 500 with a general message and the request ID, and hides the database error from the client.
  5. pino-http writes one line at error level, with the stack and the request ID. The error is logged once.
  1. The client sends POST /api/orders with the body {"quantity": 2,. The JSON is cut off.
  2. The Content-Type is application/json, so express.json() reads the body and tries to parse it. Parsing fails.
  3. The parser calls next(error) with status: 400. Express skips auth, the router and the handler, and runs the error middleware.
  4. The error middleware sees error.expose is true, so it replies 400 with the parser's message.
  1. The client sends GET /api/orders/42 with a valid token. The request reaches the auth middleware.
  2. The auth middleware sets req.user but its last line, next(), is missing. It also sends no response.
  3. Express waits. The event loop is not blocked, so other requests still work. This socket stays open until the client or the load balancer times out, often after 60 seconds.
  4. On shutdown, server.close() waits for this request too. That is why the shutdown code forces an exit after 10 seconds.

Problems it solves

  • Raw node:http is low-levelExpress adds routing, route parameters, body parsing and helpers such as res.json().
  • Shared logic per requestLogging, auth and headers live in middleware instead of in every handler.
  • Large codebases need structureRouters split an API into files, each mounted at its own path.
  • Finding help and packagesExpress is the most used Node.js framework. Most problems already have an answer and a middleware.
  • Lost async errorsSince Express 5, a rejected promise in a handler reaches the error middleware.

Problems it introduces

  • No validation or schemasYou add zod or similar yourself, and API docs do not come from the routes.
  • Order-dependent setupA middleware in the wrong place breaks requests without any error at startup.
  • Hanging requestsA middleware that forgets next() leaves the client waiting with no error.
  • Slower than FastifyRoute matching walks a list, and JSON output does not use a schema.
  • No secure defaultsSecurity headers, CORS and rate limits are separate packages you must add.

HTTP serversrc/server.jsThe Express app is a request listener for node:http. On SIGTERM the server stops taking new connections, waits for open requests, closes the database pool and exits. A timer forces the exit if a request never finishes.
import http from "node:http";
import { createApp } from "./app.js";
import { database } from "./database.js";
import { logger } from "./logger.js";

const port = Number(process.env.PORT ?? 3000);
const shutdownTimeoutMs = 10_000;

const server = http.createServer(createApp());
server.keepAliveTimeout = 65_000;
server.headersTimeout = 66_000;

server.listen(port, () => {
  logger.info({ port, nodeVersion: process.version }, "server listening");
});

function shutDown(signal) {
  logger.info({ signal }, "shutting down");

  server.close(async () => {
    await database.end();
    logger.info("shutdown complete");
    process.exit(0);
  });

  setTimeout(() => {
    logger.error("open requests did not finish in time, exiting");
    process.exit(1);
  }, shutdownTimeoutMs).unref();
}

process.once("SIGTERM", () => shutDown("SIGTERM"));
process.once("SIGINT", () => shutDown("SIGINT"));
Middleware ordersrc/app.jsThe whole chain, in the order a request passes through it. The logger is first so every request gets an ID and a log line. /health comes before auth. The 404 handler and the error middleware come last.
import compression from "compression";
import cors from "cors";
import express from "express";
import helmet from "helmet";
import { errorHandler, notFoundHandler } from "./middleware/error-handler.js";
import { requestLogger } from "./middleware/request-logger.js";
import { requireAuth } from "./middleware/require-auth.js";
import { ordersRouter } from "./routes/orders-router.js";

export function createApp() {
  const app = express();
  app.set("trust proxy", 1);

  app.use(requestLogger);
  app.use(helmet());
  app.use(cors({ origin: ["https://shop.example.com"] }));
  app.use(compression());
  app.use(express.json({ limit: "100kb" }));

  app.get("/health", (req, res) => res.json({ status: "ok" }));

  app.use("/api", requireAuth);
  app.use("/api/orders", ordersRouter);

  app.use(notFoundHandler);
  app.use(errorHandler);
  return app;
}

Request IDsrc/middleware/request-logger.jsReuses the proxy's x-request-id when it looks valid, else creates a new one. pino-http stores it in req.id, adds it to every req.log line, and writes one line when the response is finished.
import { randomUUID } from "node:crypto";
import pinoHttp from "pino-http";
import { logger } from "../logger.js";

const validRequestId = /^[\w-]{1,64}$/;

function requestIdFor(req, res) {
  const incomingId = req.headers["x-request-id"];
  const requestId = validRequestId.test(incomingId ?? "") ? incomingId : randomUUID();
  res.setHeader("x-request-id", requestId);
  return requestId;
}

function logLevelFor(req, res) {
  if (res.statusCode >= 500) return "error";
  if (res.statusCode >= 400) return "warn";
  return "info";
}

export const requestLogger = pinoHttp({
  logger,
  genReqId: requestIdFor,
  customLogLevel: logLevelFor,
});
Validationsrc/middleware/validate-body.jsexpress.json() only parses. This middleware checks req.body against a zod schema and replaces it with the parsed data, so unknown fields are dropped. A throw in a middleware goes to the error middleware.
import { HttpError } from "../http-error.js";

export function validateBody(schema) {
  return (req, res, next) => {
    const result = schema.safeParse(req.body);
    if (!result.success) {
      throw new HttpError(400, "The request body is invalid.", result.error.issues);
    }
    req.body = result.data;
    next();
  };
}
Authsrc/middleware/require-auth.jsEnds the request with 401 when the token is missing or invalid. Otherwise it stores the user and calls next(). Mounted on /api only, so /health stays public.
import { verifyAccessToken } from "../auth/access-tokens.js";

export async function requireAuth(req, res, next) {
  const [scheme, token] = (req.get("authorization") ?? "").split(" ");
  if (scheme !== "Bearer" || !token) {
    return res.status(401).json({ error: "The access token is missing." });
  }

  const user = await verifyAccessToken(token);
  if (!user) {
    return res.status(401).json({ error: "The access token is invalid or expired." });
  }

  req.user = user;
  next();
}

Handlerssrc/orders/order-handlers.jsAsync handlers with no try/catch. In Express 5 a throw or a rejected await reaches the error middleware. Route parameters are always strings.
import { z } from "zod";
import { HttpError } from "../http-error.js";
import { renderInvoice } from "./invoices.js";
import { orderRepository } from "./order-repository.js";

const invoiceFormats = ["pdf", "html"];

export const createOrderBody = z.object({
  productId: z.uuid(),
  quantity: z.number().int().min(1).max(100),
});

export async function createOrder(req, res) {
  const order = await orderRepository.insert({ ...req.body, customerId: req.user.id });
  res.status(201).location(`/api/orders/${order.id}`).json(order);
}

export async function getOrder(req, res) {
  const order = await findCustomerOrder(req.params.orderId, req.user.id);
  req.log.info({ orderId: order.id }, "order loaded");
  res.json(order);
}

export async function getInvoice(req, res) {
  const format = req.params.format ?? "pdf";
  if (!invoiceFormats.includes(format)) {
    throw new HttpError(400, "The invoice format must be pdf or html.");
  }
  const order = await findCustomerOrder(req.params.orderId, req.user.id);
  res.type(format).send(await renderInvoice(order, format));
}

async function findCustomerOrder(orderId, customerId) {
  const order = await orderRepository.findForCustomer(orderId, customerId);
  if (!order) {
    throw new HttpError(404, "The order does not exist.");
  }
  return order;
}
Errorssrc/http-error.jsAn error with a status code. expose marks the message as safe to send to the client, the same flag the body parser sets on its own errors.
export class HttpError extends Error {
  constructor(status, message, details) {
    super(message);
    this.name = "HttpError";
    this.status = status;
    this.details = details;
    this.expose = true;
  }
}
Errorssrc/middleware/error-handler.jsFour arguments, so Express treats it as error middleware. Client errors get their message. Every other error gets 500 and a general message, so database details do not reach the client.
export function notFoundHandler(req, res) {
  res.status(404).json({ error: "The route does not exist." });
}

export function errorHandler(error, req, res, next) {
  if (res.headersSent) {
    return next(error);
  }

  // pino-http adds res.err to the request's log line, so the error is logged once, with its request id
  res.err = error;

  const isClientError = error.expose === true;
  res.status(isClientError ? error.status : 500).json({
    error: isClientError ? error.message : "Internal server error.",
    details: isClientError ? error.details : undefined,
    requestId: req.id,
  });
}
